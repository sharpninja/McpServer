# Create a new QBrain plan

Produce a decision-complete proposal where the evidence supports it. Leave genuine blockers visible. Planning is not implementation, approval, or authorization to change QBrain.

Use the user-selected or current authoritative template and schema together. If unavailable, use the repository’s [v0.8 template](../../docs/plans/BDPv4-QBrain-Implementation-Plan-Template.yaml) and [matching schema](../../docs/plans/BDPv4-QBrain-Implementation-Plan.schema.json). Follow the template's agent header; this skill governs the new-plan workflow and Plan mode boundary.

## Plan mode boundary

- Inspect the relevant checkout, instructions, requirements, architecture, tests and approved constraints using read-only discovery. Use the workspace's supported trusted QBrain read path. Do not edit the repo, create TODOs, advance gates, write receipts to QBrain, or start implementation while Plan mode forbids those changes. Do not switch modes yourself or use another tool to evade the boundary.
- Ask the user only for a material decision you cannot resolve from authoritative sources: scope, a public contract, an important tradeoff, or authority to proceed. Present concrete choices and a recommendation when useful. Keep evidence and inference distinct.
- Put the proposal in the host's plan output format. When a file cannot be written, provide the canonical YAML in the plan response or as a clearly labeled handoff for the authorized write step; state where it belongs. Never claim a proposed path, ID reservation, approval, or receipt was persisted.

**Slice forms:** In v0.8 choose one inline `delivery.phases[].defaultSlice` or a nonempty `sliceRefs` list resolving to `delivery.slices`; never both in one phase. Omit the top-level slice list when all phases use defaults. Each definition uses exactly one `sliceRef`: `{ kind: todo, todoId: … }` or `{ kind: task-group, taskGroupId: … }`. Reuse it in phase lists, artifact edges and slice-scoped completion and receipts. Resolve native groups in the current workspace under `metadata.umbrellaTodoId`; reject duplicate, unresolved and cross-plan/cross-workspace identities before readiness. Do not create mirror TODOs. Read v0.7 `todoId`, `sliceTodoIds` and `sliceTodoId` as TODO references in memory; preserve the plan and receipt IDs unless a version conversion is requested.

**Native Task Group execution.** Keep membership, dependencies, assignments and live status in QBrain; keep slice scope, gates and versioned artifacts in the YAML.
- **Before production:** Map cases to ACs. An independent test-owned fake must pass with zero failures and zero skips. Deliberately wrong responses or interactions must be rejected by the same assertions for the intended reason. Preserve both receipts, then bind identical cases, inputs and assertions to production. Design and mock-test members in parallel while Planning. No implementation starts until every member has current reviewed design and all applicable mock evidence, and the selected Task's prerequisites are satisfied. Verification-only Tasks need reviewed criteria and inputs, not a mock suite.
- **At group completion:** Let members satisfy their own gates and reach Success. Require one final HV Task, last and explicitly dependent on every other member. Review exact member evidence with independent agent/model families per the workflow; require AGREE with both scores at least 98 (or the higher configured floor). Keep the group verdict and separate slice/phase HV receipts; none substitutes for another.
- **Declare the gates on each slice:** Every v0.8 implementation slice lists `execution-entry` and `implementation-exit` in its own `gateIds`, for both inline and explicit forms. Keep the chain for slices with execution-entry inputs. Omit implementation gates only for verification-only scope; do not retrofit v0.7 gate lists.
- **Separate planning from execution entry:** At `slice-entry`, verify only design/mock inputs due now; start eligible design and mock work despite unfinished execution prerequisites. Missing actual design/mock inputs still block the affected checks. At `execution-entry`, verify implementation inputs and execution prerequisites; for native Tasks recheck at `Ready -> Started` with the group-wide design/mock barrier.
- **Mixed slices and phase exit:** For a TODO-backed consumer of required native output, derive the group from the consumed artifact version's producer edge. At execution entry require the exact artifact revision/digest and verified group `Completed` with current final HV AGREE; never put the UUID in a legacy TODO dependency. If HV is only pending, an early handoff requires an explicit human-approved, scoped, expiring exception with current evidence for the exact group, TODO, artifact and allowed actions. Failed HV blocks use; no exception bypasses native prerequisites or phase exit. Phase exit requires every native group Completed with verified final HV plus the separate phase review.
- **For parallel execution:** Dispatch only independent Task Groups with prerequisites met; at most one Started Task and one active assignment per group. Before dispatch, assign one integration owner for each shared project file, package pin or generated build file. Separate worktrees, outputs and disposable fixtures, check combined disk needs and allow at most one Nuke invocation per worktree. Log collisions and reruns in the group record. Lead each Task update with the last verified checkpoint, revision, host, receipt and next unmet AC; use those notes to decide whether parallel dispatch should continue. A plan setting cannot override the sequencing contract.

## Build the plan

1. **Ground scope.** Capture the problem, intended users, measurable outcome, exclusions, changed behavior, viability/value and ship boundary. Assign known owners. Pin the governing BDPv4/workspace rules, requirements and source revisions, and current architecture. Link authority instead of repeating it.
2. **Close material design decisions.** Define public contracts and boundaries before scheduling implementation. Identify the versioned Structurizr workspace and required C4 views. Explicitly classify UI impact. For changed UI, plan the required use cases, SVG wireframes and AssetReview storyboards, tracing use-case steps to frames and the owning FR/AC. Missing required artifacts become readiness blockers, not promises of validation.
3. **Sequence the work.** Define phase objectives and bounded slices with verifiable exits. Reuse verified canonical IDs. New artifact and phase IDs may be proposed and checked for collision; a slice uses the actual TODO ID or Task Group UUID. When native Task Groups are not available, use existing TODOs. If no applicable TODO exists, propose an ordinary TODO per independently tracked slice as pending; include its charter, canonical requirement links and actual prerequisites. Leave IDs unbound until an authorized write step outside Plan mode reads the persisted record back. Do not invent an ID or present a placeholder as ready. Map exact artifact versions and their producing/consuming gates; keep live task dependencies in QBrain.
4. **Design the proof.** Trace in-scope FR/TR/TEST, qualified ACs and use cases to slices and tests. Require a passing AC-mapped contract suite against a test-owned fake and an explicit wrong-fake rejection by the same assertions, before production code. Preserve both receipts. Plan to rerun the same cases, inputs and assertions against the real implementation, along with full unit regression separate from integration/human validation and release. Require independent HV AGREE with at least 98 accuracy and 98 completeness at every applicable stage exit, not just overall. State what invalidates evidence and what must be rerun. Keep approval unset until the exact revision is approved.
5. **Verify and hand off.** Parse the YAML with duplicate keys rejected, run the companion schema when available, and independently check ID/link resolution, ownership, completeness and dependency order. Report draft schema validity separately from approval readiness. The canonical draft keeps live completion snapshots and receipt entries empty; state the authoritative tracking source or flag it as pending. Never claim a stage passed without current authoritative evidence.

Report the target path, decisions and rationale, expected artifacts and checks, and unresolved blockers. When mode and permissions later allow, persist the proposed records through the supported QBrain tools, verify their identities, and revalidate the exact plan revision before requesting approval. Do not start implementation merely because the plan was written.

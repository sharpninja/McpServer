## Outcome and scope

Deliver both enhancements through the shared requirements wiki exporter. Define the footer once and show it once on every exported page. Detect shared requirement ID prefixes and export a linked child page for each group within Functional, Technical, and Testing Requirements. Treat the child pages as additional reading views. Keep the full requirement records, existing headings, and inbound anchor targets on the three main pages so existing links and wiki imports continue to work.

Cover the configured McpServer export, its output directory and ZIP, and the existing GitHub publication staging flow. Preserve compatibility with the legacy platform artifacts the exporter currently produces. Scope the change to the wiki format. The plan requires no database schema migration, API shape change, or live deployment.

## Proposed acceptance criteria and test cases

### Footer

- **F1, one source and one visible footer.** Allow an optional workspace-relative Markdown template at `footer.template` in the typed wiki configuration. Set it in McpServer's `docs/wiki.yaml` to `docs/wiki-footer.md`, initially carrying the existing export attribution. Export that content as GitHub's native wiki-wide `_Footer.md`. In the legacy Azure-format output, append the same template in a bounded footer block to each content page. Cover Home, FR/TR/TEST, mappings, matrix, workspace Markdown, DocFX Markdown, and the new group pages. Keep the template out of the page inventory. Preserve sidecars and non-page assets, including `_Sidebar.md`, `.order`, manifests, and optional dump JSON. [GitHub wiki footer behavior](https://docs.github.com/en/communities/documenting-your-project-with-wikis/creating-a-footer-or-sidebar-for-your-wiki)
- **F2, compatibility and validation.** If the footer is undeclared, retain current footer behavior. For an explicit footer, reject missing, empty, non-Markdown, or out-of-workspace template paths, including a path escaping through a symlink or reparse point. Validate before any export file is added, changed, or removed. Reject reserved delimiter text in a configured template and distinguish the managed trailing block from ordinary page content.
- **F3, repeat and round-trip.** Re-exporting a workspace must not stack footers or modify input Markdown. Publication staging must keep the inline Home footer last, after the existing User Documentation section. For the existing inline platform format, remove only the well-formed, exporter-owned trailing footer block before parsing canonical requirement documents. A round-trip of a footer containing headings, checkbox bullets, or requirement-looking text must preserve the same typed records, IDs, acceptance criteria, satisfaction/evidence, and mappings with zero unintended creates, changes, or deletes.

### Requirement groups

- **G1, deterministic grouping.** Enable `requirementGroups.enabled` for McpServer. Derive a prefix from the leading whole hyphen-separated segments of each typed FR, TR, or TEST ID, stopping at the first segment beginning with an ASCII digit. Require the matching type segment and at least one additional nonnumeric segment, with no blank segments. Use ordinal, case-insensitive matching and an uppercase path key. Keep the full original IDs in page content. For example, `FR-MCP-WIKIEXPORT-001` and `FR-MCP-WIKIEXPORT-002` form `FR-MCP-WIKIEXPORT`. Only prefixes shared by at least two distinct IDs of the same type get a child page. Singletons and IDs without a valid prefix stay on the main page. Render group and member ordering consistently regardless of input order. Retain the existing TEST sections and parser-compatible headings.
- **G2, links and content.** Render one full, read-only view for each qualifying group, using the same per-record rendering and mapping context as the parent. Put one link per group on its type's main page, before the requirement records, and a link back on the child. Keep the established parent filename and requirement anchors. A child inherits its parent document's platform selection. Derive its route from the configured parent target and a safe group key. Initially use a sibling file with a parent-prefixed basename, such as `Functional-Requirements--FR-MCP-WIKIEXPORT.md`, so forward and back links work without creating a new directory solely for groups. Present it as a child under the parent in generated navigation where supported. Check links with configured nested or renamed parent targets as well as standard targets.
- **G3, inventory and cleanup.** Feed child pages into platform manifest, link generation, ZIP metadata, and existing contained cleanup from one computed inventory. Validate generated targets against declared documents, generated sidecars, and DocFX targets before writes. Detect basename route collisions where the target platform treats them as collisions. On re-export, remove managed group pages and their navigation links when a group falls below two members, or when grouping is disabled. Preserve other valid export entries and the current containment policy. With absent configuration or omitted grouping settings the exporter retains the established layout and creates no child pages.
- **G4, data fidelity.** A child page contains each member's full rendered requirement, including the details and acceptance criteria already shown on the parent. Imports continue to read the canonical parent pages. Child page bodies, timestamps, and footer content must not create extra requirements or change the authoritative platform when canonical inputs and their timestamps are unchanged. Existing inputs with no child pages remain valid. Preserve the full canonical export when all groups are present, recently removed, or absent.

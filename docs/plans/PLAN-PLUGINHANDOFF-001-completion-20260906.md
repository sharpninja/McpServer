## Hostile-review worker contract

### Public schemas and operations

The only public operation names are `hostile_review_submit`, `hostile_review_status`, `hostile_review_get`, and `hostile_review_query`, with matching REST, typed-client, REPL, Director, and plugin-skill surfaces.

- Submit request fields: `workspacePath` from authenticated context; `targetType`; `mode`; `scopeStatement`; `artifactLinks[]` with type, locator, expected version/hash; `requester` with agent, plugin/source, session ID, and turn ID when available; optional `acceptanceCriteria[]`. The canonical serialized request must not exceed 1,048,576 bytes.
- Submit receipt fields: request ID, queue item ID, `Queued` status, created UTC, artifact identity/hash summaries, diagnostic codes, and effective worker policy version. It contains no resolved artifact text.
- Status request fields: request ID only. `status` is read-only on REST, typed-client, REPL, Director, MCP-tool, and plugin-skill surfaces; command or mutation fields are rejected rather than interpreted.
- Status result fields: request ID, state, attempt count, next-attempt UTC, lease expiry UTC, internal lifecycle-cancellation state when applicable, sanitized last error code, and accepted terminal execution ID when present. Reading status never changes any field.
- Get result fields: normalized request metadata, provenance, executions, findings, recommendations, verdict, request-quality assessment, and diagnostics. It contains no assembled prompt or raw artifact body.
- Query request fields: workspace, model, effort, requesting agent, reviewer agent, target type, artifact type, severity, category, status, created range, offset, and bounded limit. Filters combine with AND.
- Reviewer output schema: `schemaVersion`; request ID; execution ID; verdict restricted to `AGREE|DISAGREE|UNKNOWN`; findings with category, severity, artifact identity, location, violated requirement/AC, evidence summary, and recommendation; request-quality fields for disclosure, scope clarity, objective clarity, confidence, and enough context; diagnostics; model/runtime metadata when actually supplied. Unknown fields or malformed output fail the attempt.

### Ownership, defaults, and states

- A server-owned hosted worker is the only dispatcher. It reads the durable review queue, then calls the existing `IAgentPoolService`; the in-memory pool is an executor, not the queue authority.
- Configuration is `HostileReviewWorkerOptions`: enabled true; explicit agent name `Astra`; required model `gpt-6-astra`; required effort `xhigh`; maximum active queue 200, matching `AgentPoolOptions.MaxQueueSize`; maximum concurrent reviews 1; poll interval 2 seconds; lease duration 5 minutes; renewal interval 60 seconds; maximum attempts 3; retry delay 5 seconds with a 60-second cap; execution timeout 30 minutes; 64 links; 1 MiB per artifact; 8 MiB aggregate input; 2 MiB reviewer output; JSON depth 32. Invalid relationships such as renewal greater than or equal to lease fail startup validation.
- Effective model and effort are verified against the selected pool definition and returned execution metadata before a review can succeed. Missing or substituted model/effort is `ModelUnavailable`, not a silent fallback.
- Durable request states are `Queued -> Claimed -> Running -> Succeeded|Failed|Cancelled`. A transient failure moves `Claimed` or `Running` to `RetryWait`, then back to `Queued` when due. `Cancelled` is reachable only from internal host/workspace lifecycle policy. Terminal request states never leave terminal.
- Each dispatch creates a durable attempt ID and random fence token before pool admission. Durable attempt states are `Claimed`, `AdmissionPending`, `Running`, `Succeeded`, `Failed`, `Interrupted`, `Orphaned`, or `Cancelled`. `ReviewExecution` has a distinct execution ID, and the process-local AgentPool job ID is recorded as non-authoritative audit metadata when available.
- Claim is one atomic compare-and-swap over nonterminal request status, due time, lease expiry, attempt count, state version, and fence token. Renewal succeeds only for the current owner and fence. The attempt number is allocated durably before enqueue, so at most three pool admissions can be initiated for one request.
- The existing `IAgentPoolService` remains backward-compatible and in-memory. Add only an internal process-singleton `IHostileReviewDispatchCorrelation` with atomic `TryReserve(attemptId)`, `AttachPoolJob(attemptId, poolJobId)`, `TryGet(attemptId)`, and `Remove(attemptId)`; it is not a public API and is never treated as durable. The worker reserves before enqueue. Within one live process, retry or polling for an attempt sees either the reservation or attached job and never enqueues that attempt twice; an unresolved reservation is fenced and classified `PoolAdmissionOutcomeUnknown`, not blindly resubmitted.
- There is no exactly-once or durable pool-admission guarantee. A crash can occur after the model starts but before the pool job ID or result is durably observed. After process restart, an expired `Claimed`, `AdmissionPending`, or `Running` attempt whose in-memory job cannot exist is durably closed as `Orphaned` with `PoolStateLostOnRestart`; if the request is still eligible and below the attempt bound, a new attempt with a new fence is queued. This is bounded at-least-once model execution, so more than one model execution is possible.
- Completion acceptance requires request ID, attempt ID, fence token, unexpired ownership, and current state version. The first valid completion atomically creates the one accepted terminal result. Stale, orphaned, late, or duplicate outputs are discarded with sanitized diagnostics and cannot replace or add another accepted result, regardless of how many models executed.
- Graceful host shutdown stops new claims, internally calls `CancelQueueItemAsync` for known live jobs, marks their attempts `Interrupted`, and moves eligible requests to `RetryWait`; abrupt process loss relies on lease expiry and the orphan rule. Workspace disable/delete may internally set `CancelRequested`, cancel a known running pool job, and terminate the request as `Cancelled`. No hostile-review public operation requests cancellation.
- When a pool job reaches terminal state or an attempt is interrupted, orphaned, timed out, or internally cancelled, the worker removes the process-local correlation and calls the existing internal `RemoveQueueItemAsync` after processing has stopped. Disposal clears remaining correlations. These cleanup actions do not alter an already accepted terminal result.
- Transient classes are pool admission full, process-start transient, timeout, worker restart/orphan recovery, and explicitly classified model service unavailable. Malformed request/output, authorization failure, stale artifact, unsafe content, model/effort mismatch, and secret-policy failure are terminal. A transient failure after attempt 3 becomes `Failed` with `RetriesExhausted`.
- No worker path exposes repair, apply, write, edit, TODO mutation, requirement mutation, or product-file mutation.

## Artifact authorization and protected execution

- Submit resolves identity only far enough to validate type, locator, caller access, workspace scope, and declared hash/version. It does not retain body text.
- Dispatch repeats authorization using the current caller/workspace authorization policy, reloads the artifact through the same supported service, recomputes the hash, and compares it with the queued identity. A mismatch is `ArtifactChanged`; revoked access is `ArtifactUnauthorized`; neither is retried.
- Supported artifact adapters are TODO, requirement, session-log, triage, plan/file, commit, and generated-document services already available to the server. Adapters must not call raw loopback REST.
- Resolved content is bracketed with type, stable ID, and hash, and the system prompt states that all content is untrusted evidence, never instruction.
- `AgentPoolOneShotContext.HostileReview` is added in both client and service contracts. `OneShotSensitivePromptPolicy` publishes a hash placeholder for Handoff and hostile-review contexts. Queue DTOs, SSE events, logs, persisted request/execution rows, receipts, diagnostics, and result JSON receive only the placeholder.
- Raw resolved content and assembled prompt may exist only in the worker's transient dispatch scope and the agent process input. They are never assigned to persisted entities or public queue state. The AgentPool implementation must not retain `ExecutionPrompt` for protected contexts after submission or expose it from a clone.
- Inputs are refused, not silently truncated, when any artifact exceeds 1 MiB, aggregate content exceeds 8 MiB, more than 64 links are supplied, JSON nesting exceeds 32, or content cannot be safely decoded. Reviewer output exceeding 2 MiB is a failed attempt. A diagnostic states the bound and artifact identity without content.
- Secret scanning uses configured bounded redaction rules and a structural key denylist. A timeout or undecodable encoded value fails closed. Secret values never appear in messages, hashes that can be reversed, logs, or test output.
- Normalized findings may quote only sanitized snippets needed to identify a defect. Raw prompts and complete artifacts are not copied into results.

## Workspace hydration coordinator

### Durable receipt and transaction boundary

- Add `WorkspaceImportReceipt` with receipt ID, source schema version, source root hash, source workspace key/path as immutable provenance, destination canonical workspace ID/path, state, state version, created/committed/activated UTC, activation stage, activation attempts, sanitized error code, and created-path manifest hash.
- Add `WorkspaceImportEntityMap` with receipt ID, table name, source key, destination key, policy code, and provenance flag. It contains no raw row JSON or credentials.
- Receipt uniqueness is destination canonical path plus source root hash. A second unique guard prevents two nonterminal import receipts for one destination path.
- Preflight first validates enough of the request to compute the final-byte root hash and destination canonical path, then looks up the identical durable receipt before active-workspace duplicate rejection or fresh-import filesystem-collision rules. An `Activated` receipt returns idempotent success without reapplying fresh-import preconditions. `CommittedPendingActivation` or `ActivationFailed` resumes its first incomplete activation stage. A different hash for the same destination returns conflict.
- For a genuinely fresh import, preflight validates schema, table manifest, relationships, bounds, destination containment, reparse components, and only the specific service-owned generated/output paths required by import and activation. The existing repository root may be nonempty. Git metadata, source, documentation, build artifacts, and all other repository/user files are outside import ownership and must remain byte-for-byte untouched.
- The coordinator, not the controller, owns import coordination. It calls a transaction-aware workspace registration path that reuses `WorkspaceService` validation but does not perform its current post-save projection/event work.
- Every fresh import stages decoded and validated receipt-owned artifacts beneath `<workspace>/.mcpServer/imports/<receiptId>`. Staging never writes a marker or another generated output into its final path.
- One EF transaction creates or revives the destination `WorkspaceEntity`, hydrates all accepted rows, inserts entity maps, and moves the receipt to `CommittedPendingActivation`. A thrown exception or cancellation before commit rolls back the workspace and every domain row.
- Projection, `InitAsync`, marker creation, process start, and change notification run after commit as ordered idempotent activation stages. Each stage records completion before the next. No `Created` response or notification is emitted until all required stages succeed.
- Failure or cancellation after commit leaves the receipt recoverable. It does not delete committed data, fabricate rollback, or claim filesystem/process atomicity. Repeating the same request resumes the first incomplete stage.
- Activation may create only a service-owned path proven absent at stage preflight, or update a path previously created by the same receipt when its current hash matches the receipt manifest. The manifest records canonical path, ownership, created/updated disposition, and final-byte hash. An unknown or pre-existing marker/file is never replaced. A fresh-import collision is an explicit precommit diagnostic when knowable before commit; a race or stage-only collision becomes a postcommit recoverable `ActivationFailed` diagnostic.
- Concurrent identical imports produce one commit and one replay receipt. A concurrent conflicting import produces conflict. Soft-deleted workspace revival is allowed only inside the winning transaction and only when the path/hash policy permits it.

## EF dump/import portability matrix

### Column policies

- `ROOT`: create or revive exactly one destination workspace. Set `WorkspaceId` and `WorkspacePath` to the destination canonical path. Recompute destination machine-local fields. Do not import source enabled/running state until activation policy permits it.
- `COPY`: export only source-workspace rows plus required parent/child closure. Remap every operational `WorkspaceId`, workspace path, owner/actor workspace key, primary key, foreign key, and join key. Preserve semantic IDs only when their documented uniqueness permits it; otherwise derive a deterministic destination ID and record the pair in `WorkspaceImportEntityMap`.
- `COPY-SANITIZE`: apply `COPY`, then sanitize every textual scalar and recursively inspect recognized JSON or bounded encoded text before canonical serialization.
- `HISTORY`: preserve immutable timestamps, model names, verdicts, audit descriptions, source identities, original workspace path fields, and source semantic meaning after sanitization. Historical values are non-authoritative and never used for destination authorization, routing, execution, replay, or ownership.
- `INERT`: import for history and relationship fidelity, but clear lease/owner/job/session/process callbacks, set enabled false or destination-safe equivalent, set restart policy to `never`, and transition replayable state to `ImportedInert`. Preserve the source state in import provenance. No startup service may select `ImportedInert`.
- `SHARED-CLOSURE`: include only a host-global row required by a source-workspace row. Match by documented stable key and `skip-if-exists` only when canonical content is equivalent; otherwise diagnose conflict. Never include unrelated memberships, proxies, products, credentials, or secrets.
- `OMIT-SECRET`: never export live API keys, authorization/cookie values, connection strings, credential material, credential-store records, or unrelated host configuration. Required destination credential references become `[REQUIRES-DESTINATION-CONFIGURATION]` with the feature disabled and a diagnostic.
- Database-generated numeric keys and sequences are regenerated. Their child FKs use the entity map. Composite and string keys are preserved only when workspace scoping makes them safe; collisions are diagnosed, never silently renamed.
- Operational identity columns include `WorkspaceId`, destination `WorkspacePath`, `OwnerWorkspaceId`, workspace-valued `AddedBy`, `EffectiveWorkspacePath`, `CanonicalWorkspaceId`, `GlobalWorkspaceId`, active proxy/agent ownership, executable paths, routing keys, and replay keys. These contain destination values only.
- Explicit historical provenance includes import receipt source fields, entity-map source keys, `TriageReports.OriginalWorkspacePath`, sanitized historical audit payloads, and sanitized Handoff source locators. These may retain source identity and are excluded from operational old-ID assertions.
- Fields named or structurally equivalent to `*Json`, `HeadersJson`, `BodyBase64`, prompt, seed, command, endpoint, stdout, stderr, output, details, evidence, notes, dialog, response, and error use `COPY-SANITIZE`. Base64 is decoded only within bounds; unsafe binary is omitted with a diagnostic.

## Outbound dump confidentiality and integrity

- Sanitization is an export projection. Stored Session Logs, audit rows, and domain records are not mutated.

- Per-table hashes cover each final canonical table byte sequence. The root hash is computed from the final sorted `tableName:hash` list after all exclusions and redactions. Import verifies those exact final bytes.
- Import verifies structure and relationships against the exported projection. It never compares sanitized output with or writes back to the source database.

## Proposed representation and grammar

Versioned project records use canonical string keys. Existing standalone entities, numeric DTOs, providers and historical migrations retain their contracts. The new versioned project client/route DTOs carry canonical strings and explicit origin-scoped legacy references; they never cast a tagged string to Int64 or allocate a different machine-local numeric surrogate to masquerade as the same public identity. Compatibility with numeric callers is a capability boundary, not an implicit lossy conversion. An older caller that cannot handle versioned identities must receive the plan's unsupported-capability result before a mutation. Legacy originals remain readable through the versioned resolver using their original typed value and origin when needed. Final route/DTO names and capability negotiation are shared with the Ph7 typed-contract design before this B output is accepted.

A generated canonical string is `<family>-<tag>-<sequence>`. The family is an explicit registry value or a validated TODO/memory category prefix; the tag is exactly two uppercase ASCII letters/digits; the sequence is positive Int64, invariant decimal, formatted with a minimum width of three. Values 1, 42, 999, 1000 and Int64.MaxValue render as 001, 042, 999, 1000 and 9223372036854775807. Zero, a sign, whitespace, non-ASCII digits, exponent notation, overflow and extra leading zeroes are rejected. Parsing requires both the syntax and numeric/canonical reformat check; a permissive regex alone is insufficient. Tags LA and LG are fixture inputs only, never silent enrollment of these hosts.

Registry families proposed for independently generated authored entities:

- TODO execution and triage producers: `EXEC-TODO` and `BUG-TRIAGE`. Other explicit generated TODO requests retain their validated semantic prefix. Human-assigned TODO IDs are a separate reservation path.
- Requirements: `FR-MCP`, `TR-MCP`, `TEST-MCP` for generated records. Existing approved/user-provided requirement IDs remain exact human identities. Acceptance-criterion descriptive IDs stay unchanged; independently generated AC row identity uses `REQ-AC`.
- Memory: `MEMORY-<category>`; Workspace versions use `MEMORY-VERSION`; explicitly authored portable links use `MEMORY-EDGE`. Automatic co-retrieved edges and embedding/index state remain outside project history.
- Use-case graph: `UC`, `ACTOR`, `UC-FLOW`, `UC-STEP`, `UC-EXTENSION`, `UC-SPECIAL`, `UC-FR-LINK`. The actor/use-case association remains a composite of canonical parent IDs.
- TODO children: `TODO-LIST`, `TODO-TASK`, `TODO-NOTE`, `TODO-COMPLETED-GROUP`, `TODO-COMPLETED-ITEM`; the requirement-link key remains a composite of canonical parents/kind. The document metadata singleton remains keyed by ProjectId and its existing singleton discriminator.
- Portable banned-item rows: `PROJECT-BANNED`. Portable project configuration is keyed by the already-established immutable ProjectId.
- Explicit session promotion: `SESSION-SNAPSHOT` is the new immutable snapshot identity. Complete promoted graph child keys are scoped to snapshot plus original row kind/key, preserving graph references and original session/request IDs as data. Promotion is not another continuous audit writer. Repeating a promotion requestId returns its existing snapshot.

The registry is not an invitation to rename every existing record. A legacy canonical string is preserved unless an actual collision requires an individually reviewed mapping. Its display/human ID can remain the original string. All source rows retain typed originals in the immutable migration manifest. Numeric legacy keys become exact invariant decimal strings only as a lossless representation step in the new schema; collision resolution uses reviewed aliases, never unchecked concatenation or guessed equivalence.

## Allocation, retry and restore

Use the unversioned control store with a unique `(ProjectId, CreatorTag, EntityKind)` allocator row and a checked Int64 high-water value. A new allocation durably increments that row and records the allocation request receipt in one control-store transaction before returning the ID. Concurrent requests serialize through provider-supported atomic update/optimistic concurrency and unique constraints, not a process lock alone. Retrying the same allocation request returns its recorded ID. A failed subsequent project-content transaction consumes its number; it never rolls the counter back. Content creation itself is idempotent by its captured identity/request, with the project write gate and domain constraints. No atomic cross-store transaction is claimed.

Branch creation, rollback, merge, deletion and restore do not decrease allocation state. A restored writer remains unable to allocate under the old tag until its authoritative high-water is established; if that cannot be proved, enroll a fresh never-reused tag. Reading and recovery remain possible while creation is refused. Re-enrollment does not rewrite existing records. Exhausted sequences or tag space require an explicit enrollment/capacity resolution; no wraparound or random fallback is permitted. Phase0 safe refusal is a local test-owned observation with no issuance/reuse, not a new public endpoint or allocator-specific HTTP code. The existing typed-contract owner maps later public outcomes under the locked envelope; absence of a new public endpoint is not a Ready blocker. The current allocator seam and native recipe are documented in 2026-11-19-federation-task004-readiness.md.

The enrollment registry binds immutable NodeId to a tag that is never reassigned. Replicated records preserve origin tag, NodeId and sequence. Do not infer that ownership from user-supplied text with a matching suffix. Published records must validate against registered provenance, family and allocation receipts as applicable; migration imports use their reviewed manifest rather than inventing allocation receipts for historical rows.

## Human identity, aliases and relationships

Human IDs retain their exact canonical legacy syntax/bytes. Global uniqueness within a project/entity kind is provided by the approved hub reservation `(ProjectId, EntityKind, HumanId)` and idempotent requestId. Two simultaneous distinct requests yield one 201 and one 409 human_id_reserved; retrying the winner yields its same reservation. Offline creation uses the tagged provisional canonical ID and retains the requested human label. Publication without reservation returns 409 human_id_unreserved and preserves the local record. A reviewed alias does not destructively rename the record or rewrite history.

A permanent alias key is `(ProjectId, OriginNodeId, EntityKind, LegacyId)` with an exact typed legacy value represented without precision loss. Keep source type alongside the invariant value in the import manifest; do not conflate string `007`, numeric 7 and string `7` without an explicit reviewed rule. The resolver validates project access before existence disclosure. An unqualified identity with multiple targets returns 409 ambiguous_legacy_id; the caller supplies origin context. A differently keyed requirement or child is not assumed to be distinct work. Duplicate candidates retain normalized title/description/dependency evidence and require explicit review.

Map parent keys before children and verify every foreign/soft reference against its reviewed canonical target. Composite relationship keys use those mapped parent identities and remain unique in their declared scope. Preserve optional null references. Requirement/AC IDs and content links are not blanket-renumbered, and descriptive AC identity is not replaced by its database surrogate. Historical commit, PR, session, memory and document text stays byte-identical. Link resolution applies aliases at read time.

## Parsers, sorting, display and tests

Central family parsers supply all versioned services, typed clients, REPL/MCP wrappers, handoff validation, session context extraction, requirement links, plugin validation and traceability tooling. Each consumer must support old approved IDs and new generated IDs explicitly. Mode and provenance determine interpretation; suffix shape alone does not. Length/index/collation limits are measured in B1/B2 before adoption. Compare registered prefixes and tags ordinally; sort sequence numerically, so 999 precedes 1000. Do not present tag order or allocated sequence as global chronological order. Display canonical ID with optional unchanged human/legacy alias and visible origin; preserve canonical strings in machine output and copy actions.

Required mock assertions before B4 is Ready (existing receipts and the checkpoint below cover subsets; coverage is cumulative): every registered family and boundary grammar; exact legacy preservation; both creators at sequence1; concurrent allocation; retry after lost reply; failure after allocation; branch revert after42; unsafe restore/fresh tag; Int64 boundary refusal without reuse; numeric DTO/capability rejection without mutation; scoped same-ID/different-entity alias collision with every relational reference; ambiguous unqualified lookup; similar different IDs without automatic merge; concurrent human reservations and winning retry; offline unreserved publication retaining the local row; plugin diagnostics without mutation; numeric sequence sorting and byte-exact history. Scripted fakes must reject wrong/missing/duplicate observations for these assertions. Real disposable adapters later bind the same assertions to all four control providers and the project engine on both hosts.

B4 design/mock readiness requires complete current-definition design, finite consumer dispositions and discriminating mock evidence; the checkpoint companion supplies additive numeric/canonical DTO, safe local allocator refusal, full reference-manifest and source-consumer binding dispositions. Parent integrated review and paired-host evidence determine Ready. Actual allocator/import/parser/provider execution belongs after the group implementation barrier opens and remains required for B-output acceptance. No production entity, DTO, parser, allocator, enrollment, requirement or existing ID is changed by this design.

The source review establishes these concrete compatibility boundaries:

- Requirements REPL, requirement recovery (REPL and service), TODO REPL/service, handoff draft validation and session TODO context have separate validators. Several accept only three terminal digits. A tagged sequence 999 can pass a multi-segment validator while 1000 fails. Single-area handoff/session validators reject the extra segment. Broad requirement shapes elsewhere can accept both without establishing provenance or canonical numeric formatting. A global regex relaxation would leave these behaviors inconsistent.
- REPL and document-service requirement metadata readers take area/subarea by segment position. For `TR-MCP-LA-001`, LA would be exposed as subarea. TEST wiki grouping stops on a digit-leading segment, so alphabetic and digit-leading tags group differently. Versioned metadata must come from the parsed registered family, separately from creator provenance.
- RequirementsService fallback extraction uses unanchored single-area three-digit patterns. It can miss qualified IDs or extract a shorter prefix. Build traceability shorthand and document matrix expansion use three-digit endpoints and Int32; the latter slices three characters from an endpoint. Whole-token canonical IDs and any later approved range form need separate handling. No implicit range crosses a creator tag.
- Triage and memory legacy generators scan existing rows, parse Int32 suffixes and emit minimum-width three-digit IDs. These remain standalone behavior. They cannot become versioned allocators by allowing an extra regex segment; versioned allocation uses the proposed durable control-store family/tag counter and request receipt.
- Use-case client parameters, service DTOs and ASP.NET route constraints are numeric. This includes optional actor references and special-requirement, extension-point and link keys. Validators alone cannot make these surfaces carry canonical strings. Additive versioned DTO/route/capability disposition remains open, with existing standalone numeric contracts preserved.
- Requirement/TODO key and link annotations use 128 characters, with workspace components up to 1,024. The recovery and session-context validators also impose 128. Source annotations and the InMemory model do not establish actual Dolt composite-index byte limits, collation or provider behavior. Those remain B1/B2 integration evidence.
- GitHub `ISSUE-{number}`, operational session/request IDs, CQRS correlation IDs, numeric session-promotion source references and failsafe filename suffixes retain their current meanings. Timestamp millisecond regexes in the retired Node runtime are false project-identity matches. Do not convert them to tagged authored IDs.
- Canonical marker/handoff templates, interface/command documentation and TODO schema projections need coordinated version-aware documentation. YAML changes use full object mutation. Ingested copies are refreshed through their owning workflow; existing Node code is changed only to retire it. This review changes none of those sources.

Remaining closure includes numeric DTO/caller graph, all installed plugins and UI/copy surfaces on both hosts, every ordering use (distinguishing presentation order from deterministic serialization), all key/reference length and collation limits, the two shared-contract dispositions above, complete discriminating mocks and real disposable bindings. No B4 acceptance or implementation permission follows from this source review.

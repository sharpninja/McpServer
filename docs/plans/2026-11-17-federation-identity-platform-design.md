The exact transitive EntityFramework.Storage version, assets and package hashes are recorded by the B5 API receipt. These mixed patch versions are observed inputs, not a compatibility claim or authorization to upgrade. Use net10.0 assets; preserve the repository's dependency pins and warning gates.

Current source `IdentityServerExtensions.cs` registers SQL Server-backed ASP.NET Identity and in-memory identity resources, API scopes/resources and clients. Core AddIdentityServer also supplies default in-memory persisted-grant and pushed-authorization-request stores. `IdentityServerConfig.cs` has shared sample clients, not per-node federation enrollment. The embedded authentication strategy uses JWT bearer validation. Those are source-level observations; no live DI configuration or database was inspected here. Do not reuse sample credentials as federation secrets.

## Supported stores and data ownership

Use Duende's existing `AddConfigurationStore` and `AddOperationalStore` extension points in the disposable B5 issuer, retaining `McpIdentityDbContext` for the current human identity model. The EF extension replaces persisted-grant, device-flow, signing-key, server-session and pushed-authorization-request stores and adds the token-cleanup host. Its existing `ConfigurationDbContext` owns client/resource definitions; `PersistedGrantDbContext` exposes PersistedGrants, DeviceFlowCodes, Keys, ServerSideSessions and PushedAuthorizationRequests. All are protected operational identity state, never project-versioned content. This corrects the earlier B2 denominator: the seven ASP.NET Identity entity types are not the entire IdentityServer persistence model.

Run the disposable issuer against isolated provider databases via the repository's supported provider registrations, with additive context-specific migration histories. No live database, historical migration or default local authentication mode changes. Capture each actual EF relational model, provider version, table/key/index manifest and store resolution before claiming compatibility. Do not claim that the in-memory model inventory proves relational support. The existing integrated human store's SQL Server requirement must be explicitly represented on Linux as well as Windows; a LocalDB fallback is not a Linux hosting solution. Required dependency/licensing and concrete provider-host decisions remain part of B1/B5 acceptance.

Protected storage includes node client-secret hashes, API-resource introspection credential hashes, grant payloads and signing keys. Grant persistence may include serialized claims and other sensitive fields. Backups include both Duende contexts, human identity state and data-protection/key material required for restored service reads. Dedicated fixture stores, authority URL, audience and project scope remain separate from live settings. A database failure must fail closed rather than falling back to in-memory grants.

## Issuance, introspection and revocation

Enrollment binds `fed.node.{NodeId}` to the operator-approved single authenticated owner and authorized project/action scopes. Client credentials identify the node, not the human. A Duende Client uses ClientCredentials and `AccessTokenType.Reference`; it is not the shared sample client. Scopes and owner/project membership follow the canonical federation contract. The standard token endpoint issues the reference access token. The fixture retains the token only in process-private memory and passes safe fixture aliases through test interfaces; no bearer, client secret or grant Data value enters an assertion diagnostic, TRX, argv, audit payload, source file or receipt.

The gateway authenticates to `/connect/introspect` as the dedicated API resource using protected backend credentials, checks activity, expected issuer/audience, node-client ownership, project/action scope and current branch membership, then authorizes the operation. Use the already-supported protocol/HTTP client; do not add another auth product or translate a reference token into a JWT for local validation. No positive introspection cache is enabled, including a prior request's success. A successful initial check is insufficient: publication acceptance rechecks immediately at the guarded public-ref boundary. Unreachable identity service yields the existing 503 identity_unavailable and leaves the public ref unchanged.

Operator revocation durably disables the node's Duende Client and removes its persisted reference grants through `IPersistedGrantStore.RemoveAllAsync` with a ClientId/type filter. Confirm both states by independent reads. The default reference-token implementation delegates to IPersistedGrantStore, and token validation checks the enabled client. Individual `/connect/revocation` only permits a token's owning client to revoke it; a response to an unrelated client is not proof that fleet revocation occurred. Do not substitute an unsupported administrative use of that endpoint. The fixture uses the supported server-side store boundary with explicit authorization, retaining the existing node-control API design.

Repeat introspection of the same token after revocation and after issuer restart. It must be inactive; new issuance for a disabled client fails. An unrelated authorized node remains active. An issued reference grant must survive a normal issuer restart before revocation. Denied fetch/publication and commit-boundary revocation preserve the public ref and local work. Offline local edits continue to use local identity authorization without contacting the remote issuer; they confer no backend SQL/remote publication rights.

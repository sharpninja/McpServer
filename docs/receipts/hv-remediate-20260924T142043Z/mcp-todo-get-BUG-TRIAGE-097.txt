(1) Invoke-ReplFailsafeDrain walks the queue oldest-first (file names are UTC-stamped so a name sort is chronological), re-issues each record's captured method and params, and deletes a record only after its submit succeeds; replay is idempotent because client.SessionLog.SubmitAsync is an upsert keyed by sessionId plus requestId. (2) Safety: a record the backend rejects stays on disk with an incremented drainAttempts counter and the walk continues, so one poison record cannot dam the queue; unreadable or malformed records are moved to failsafe/quarantine with a sibling reason file and never deleted; a record that burns the attempt budget is quarantined rather than retried forever; a transport failure aborts the pass without consuming attempts so an outage cannot quarantine good turns. (3) Trigger: the drain fires once per process from the first successful backend call rather than at bootstrap, because bootstrap only proves marker freshness, not reachability, and draining there would recurse. Opt-out via MCP_FAILSAFE_DRAIN_DISABLED=1. New verbs workflow.failsafe.drain and workflow.failsafe.status. (4) mcp-status.ps1 now counts the queue: pendingCount previously reported 0 while 33 records sat on disk, and the document adds pendingTurnCount, failsafeDir, failsafeCount, failsafeQuarantineCount.

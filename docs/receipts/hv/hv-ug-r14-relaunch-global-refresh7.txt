        One rule set, consolidated on 2026-11-06 at the operator's request from eight earlier Global memories of the two lab stores (listed under "Sources").         ## 1. Code documentation: every code change


        1.1. Every code change carries proper XML documentation that describes the affected code.


        1.2. That documentation includes a dated change log entry listing the associated canonical requirement ids and descriptive acceptance-criterion ids, plus what changed and why.


        1.3. Maintain purpose, behavior, parameters, returns and exceptions, as applicable.


        1.4. Preserve earlier change log entries.


        1.5. Verify every id against the canonical workspace records. Do not invent traceability or imply acceptance.


        1.6. Where XML documentation is unsupported, use the language's native documentation comments with equivalent dated requirement, acceptance-criterion and change fields.

        1.8. Workspace guidance and examples: AGENTS.md and .cursor/rules/code-documentation-traceability.mdc.


        ## 2. Test runs: targeted after an edit, full gate set once at phase exit


        2.1. After an edit, a BDPv4 mock gate or binding runs only the changed test classes, through the Nuke target TestGroups (TR-MCP-NUKE-020), never raw dotnet test.


        2.2. The command: ./build.ps1 TestGroups --test-groups "<test project>:<Class>[,<Class>...]" ["<project>:<Class>..." ...] --test-run-id <run id>


        2.3. TestGroups writes one TRX per project under TestResults/<run id>/groups/<project>/<project>.trx.


        2.4. It selects the named classes whatever their category, but excludes cases tagged for the other platform (Platform!=Windows on Linux, Platform!=Linux on Windows).


        2.5. It fails on an unknown project, a group that selects no case, a named class that ran no case, or any failed or skipped case.

        ## 3. Windows paths


        3.1. Use forward slashes in Windows paths (for example F:/GitHub/vice-sharp and C:/msys64/usr/bin/bash.exe), including paths handed to MSYS2 tools such as gcc, and in scripts, configs and generated build or link arguments.


        ## 4. Unit tests and integration tests


        4.1. Unit tests and integration tests live in separate projects and are correctly tagged.


        4.2. Unit tests exercise code in isolation, using controlled mocks or fakes as needed.


        4.3. Any test that depends on the environment is an integration test, and is never classified or run as a unit test.


        4.4. Apply this distinction to test-project ownership, category tags, Nuke groups and gates, and reported test evidence, across workspaces.


        4.5. Preserve BDPv4's green, discriminating mock gates before production changes.


        ## 5. Emulators


        5.1. When the work that needs an emulator is complete, shut the emulator down to a known state and freeze it.


        5.2. Restore it from that frozen state only when active work needs it.


        5.3. Never leave an emulator running idle and consuming resources after its work is complete.


        ## 6. Git worktrees


        6.1. Create git worktrees inside the owning repository's workspace directory, never as sibling directories beside it. Example: TruckMate worktrees belong under F:/GitHub/TruckMate/.worktrees/<name>. This applies to every repository.


        ## 7. NuGet warnings


        7.1. NuGet warnings may never be ignored.


        7.2. Do not suppress NU1902, NU1903 or any other NuGet warning, downgrade an enforced warning gate, disable NuGet audit, or use a local or bootstrap exception to bypass them.


        7.3. Repair the dependency issue within the authorized scope, or report the exact affected dependency and the scope decision it needs.


        7.4. The operator explicitly rejected a local-only advisory warning override for the pinned FeatureFlags tool bootstrap.

        8.1. Acknowledge your mistakes, state the rule you broke, and account for the wasted usage and time.


        8.2. State the specific action and its consequence.


        8.3. Give measured usage and elapsed time when available, and keep measured facts apart from estimates and unavailable figures.

        # HV rules: hostile-validation rules for every agent and every HV round


        One rule set, merged on 2026-11-06 from MEMORY-PROCESS-010 (version 2) and MEMORY-PROCESS-013 (version 1), reformatted and refined at the operator's request. The operator's words are quoted under "Sources" at the end. "Task" means one task of the plan under review (in McpServer, one implementation task of the plan's TODO). "Change under review" means the commits or edits the HV round reviews. A requirement is "in flux" when a change under review adds, changes or implements it.


        ## 1. Verdicts and scores


        1.1. Every HV round returns an overall verdict, AGREE or DISAGREE, with an accuracy score and a completeness score. The overall verdict is AGREE only when both scores are 98 or more.


        1.2. Every HV round also returns a verdict for each task it adjudicates (rule 3.2): AGREE or DISAGREE, with that task's own accuracy and completeness scores. A task's AGREE needs both of its scores at 98 or more.


        1.3. The per-task verdicts are the operator's own gates. They are not extra approval gates added by an agent.


        ## 2. Marking tasks completed, and regressions


        2.1. A task that clears its own HV AGREE is marked completed in the plan and in its TODO, through the agent's plugin. The completion cites that round's request JSONL, its response JSONL and the session-log turn that holds the verdict.


        2.2. A task without its own AGREE stays open, whatever the overall verdict.


        2.3. A completed task is not adjudicated again as an incomplete task. It is checked only for regression, when rule 3.3 selects it. A regression is any finding that would invalidate a completed task. A task with a regression is reopened, because no done state may stand while a failure is outstanding, and it stays open until a later round clears it again.


        2.4. Every regression is called out in the review summary, by task, with the finding and the requirement it touches.


        2.5. Per-task verdicts keep each round tied to the plan's tasks, which helps against scope creep.


        ## 3. Review scope: the requirements matrix


        3.1. The reviewer builds and keeps, and returns with its verdict, a matrix of: the requirements of each task, and the requirements of each change under review. The matrix shows which requirements are in flux and which tasks share them.


        3.2. An open task with at least one requirement in flux is adjudicated in full and gets its own verdict and scores (rule 1.2).


        3.3. A completed task that shares a requirement in flux gets regression attention only (rule 2.3). Its result is either "no regression" or a regression finding.


        3.4. A task with no requirement being adjudicated in this round is not reviewed, unless the operator requests a holistic review. This holds for open tasks as well as completed ones: an open task out of scope stays open for that round. For example, an HV midway through a plan, such as a phase gate, still sees requirements and tasks of other phases; they are out of scope for that review. The matrix still lists them, marked out of scope.


        ## 4. What every HV request contains


        4.1. Every task of the plan under review, each with a fixed number and its state (open or completed), and the changes under review.


        4.2. The requirement to return the matrix (rule 3.1), a verdict and both scores for each task adjudicated in full (rule 3.2), a regression result for each task selected for regression (rule 3.3), and the regressions called out in the summary (rule 2.4).


        4.3. Rule 6 (infrastructure failures), stated explicitly.


        4.4. Complete paired request and response JSONL, and the complete verdict artifacts, are kept for every round.


        ## 5. Interpreting findings


        5.1. Reason about the context and the underlying failure pattern of each finding. Do not merely patch the cited line or satisfy the reviewer's wording.


        5.2. Understand the affected user outcome and the claim the evidence is meant to support.


        5.3. Verify each finding against authoritative sources.


        5.4. Examine related instances and the end-to-end chain among requirements, design, implementation, tests, evidence, documentation, publication and actual deployment, as applicable.


        5.5. Check whether a proposed fix and its tests address the underlying class of failure without introducing new gaps.


        5.6. Keep observed facts apart from inference, unverified claims and unresolved decisions.


        5.7. Preserve full review receipts, and report every FAIL and every UNKNOWN.


        5.8. Apply the existing plan and review rules. Do not invent additional approval gates, and do not treat passing a replacement check as proof of the user outcome.


        ## 6. Infrastructure failures


        6.1. Infrastructure failures have no bearing on HV AGREE when sufficient review evidence is present. Judge the requested product, plan, requirements, code, tests and retained evidence on their merits.


        6.2. MCP availability, live memory-loading failures, triage submission, session-log persistence or readback, and other infrastructure failures must not by themselves force DISAGREE, lower a score or block acceptance when the needed evidence is otherwise available.


        6.3. Record infrastructure failures separately, as operational issues. Use the supported failsafe and retry persistence without delaying the substantive verdict.


        6.4. If a failure actually prevents access to evidence needed for a specific criterion, name that missing evidence and the affected criterion honestly. Never invent a PASS or an AGREE.


        6.5. Rule 6 supersedes older profile or template rules that made infrastructure persistence or live memory loading a prerequisite for HV AGREE.

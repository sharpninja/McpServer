Confirmed material findings during round 1, still subject to the remaining propagation and source checks:

- F01: The live flush prose promises a maximum interval, but StreamReviewerOutput only tests that interval after a new line (amendment 1395, 1425-1437). A small line followed by silence never triggers an append. FR-MCP-HVPIPE-008-AC001 and AC003 reject this trace. The activity and sequence need a timer-triggered flush independently of line arrival.
- F02: WatchHvNotifications persists its cursor and inbox in two files (1471), while its diagram claims one atomic replacement (1480). A crash after cursor advancement loses the notification. A fast completion can also be consumed before SubmitHvFromPlugin records its returned request in submitted (1453, 1461), then permanently ignored. UC-HV-07 (2200) promises exactly-once model delivery, contrary to the at-least-once rule and with no atomic delivery acknowledgment. The design needs a single recoverable cursor/inbox state and submission reconciliation, explicit deduplication and honest delivery guarantees, plus crash and fast-completion criteria.
- F03: UpdateHvReviewerCommand promises automatic NONCE after a configuration change (632), but HvWorkerHost requests NONCE only at startup (1372-1389). The claim path consumes only ProbeRequestedUtc (941), which update does not set. The promise needs a durable configuration-change probe request and polling/restart coverage.
- F04: A probe started for configuration A can finish after PATCH changes the reviewer to configuration B, then CloseHvRunOutputCommand unconditionally marks B Online (632, 1016). No captured reviewer configuration version exists on HvRun (484-490), nor does the probe close compare one. Readiness must bind to the configuration actually probed; add a stale-probe race criterion.
- F05: FailHvRunCommand always calls the review-request-only HvRetryDecision (1045-1067, 1346), although a Probe has no HvRequestId (484) and a failed launch or nonzero probe exit uses this same command (1395). The probe failure and shutdown outcomes require an explicit branch, with offline/incident and retry semantics tested.
- F06: V-6 accepts a reviewer turn containing only the compact hv_verdict (1283, 553). It does not require the entire result or a closed Chore turn, as P-06 and the brief require (544). A persisted summary-only or open turn can pass finalization. Verification and negative criteria must check the complete result and required terminal state.
- F07: HvEvidence stores the result document with only responseLog removed (494), while that document contains evidence.result.sha256 (562), and its Sha256 hashes the decompressed stored bytes (494). No exclusion/projection defines a hashable payload without its own hash. Define one canonical stored payload and add its digest to the returned envelope, with a named hash/round-trip case.
- F08: FileHvIncidentCommand calls the writing triage service before AuditLedgerGuard (1156, 1163-1171), contrary to the hard-stop rule that no HV unit writes while the ledger is unavailable (369, FR-MCP-HVPIPE-018-AC002). Its diagram also puts Filed and notification writes after an edge labeled committed. The guard and audited triage write need an enforceable ordering/transaction boundary, and the diagram must put local outcome and notification inside the transaction.

All eight are implementer edits under already settled requirements. No new operator decision is needed to correct these contradictions. The 63 records and 114 acceptance criteria compare equal field by field; there are 21 mapping groups represented by 42 store edges. The 78 probe files match the manifest. No product file or store record has been changed by this review.

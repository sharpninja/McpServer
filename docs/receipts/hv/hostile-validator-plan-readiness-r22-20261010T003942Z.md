### F-R22-02: separate Copilot/Cline arrivals can share a nonce

**Plan locations:** D1 lines 29 and 78-79; Copilot host row line 86; classic Cline row line 89; FR-MCP-SESSIONTURN-001-AC003 line 195; P0.2 line 170; A3 RED line 579; A9 adoption line 591.

**Exact defect:** Copilot derives `cp-` + SHA-256(`sessionId` LF `timestamp` LF `prompt`), with a Unix-millisecond timestamp. Classic Cline derives `cl-` + SHA-256(`taskId` LF `timestamp` LF `prompt`). Distinct user messages with the same host-session/task id, timestamp value and identical prompt have identical nonce inputs. The server must merge them under AC002, so they become one turn, contrary to D1 and AC003's two-turn guarantee at any interval. D11's one registered Copilot hook prevents duplicate hook commands; it does not distinguish two real messages. P0.2 probes two deliveries of *one* Copilot message, while A3 tests two separate payloads whose event id or timestamp differs. Neither checks equal timestamp and text for distinct events.

**Evidence and what-if:** Two Copilot UserPromptSubmit arrivals in the same millisecond, each with `sessionId=S`, `timestamp=T`, `prompt=P`, produce equal SHA-256 input by the plan's formula. AC002 requires the same requestId for that nonce. The plan identifies no stable per-message ID or durable arrival sequence for that case. The same counterexample applies to Cline if a task contains two such arrivals with equal timestamp precision. This is an internal counterexample, independent of current plugin implementation.

**Change to PASS:** Lock a traceable, durable per-arrival identity and replay rule for these hosts, or apply D6 `turn_logging_unsupported` when the host cannot distinguish separate events. State the selection in the host rows and P0.2 disposition, strengthen AC003, add same-session/same-timestamp/same-text distinct-event RED cases in A3/A9 and the corresponding TEST statements, and update the feature matrix, TODO and handoff. A hash of the same fields is insufficient. **Implementer edit; no new operator decision** because D1 requires distinct turns and D6 already authorizes unsupported capability. If the author proposes weakening D1 or promising support without a distinguishable event, that would require an operator decision between the existing D1 guarantee and that relaxation; this review does not authorize the relaxation.

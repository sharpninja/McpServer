## New findings

### R3-M1 — Medium — Arch §3 vs Arch §10 and §4 step 6; B5/B9
**Defect:** Arch §3 says exactly one host-local server process owns writes. It says the server's per-(project, branch) write gate serializes leases, fences, edits, preview validation and Dolt commit.

The sync worker's own mutations of the live branch are not listed among the operations the gate serializes. Those mutations are:
- the dirty and lease check,
- merging into the live branch, and
- moving the live branch head.

Arch §10 then permits a fallback when SQL privileges cannot be restricted: it allows "isolate the worker service/process and SQL access". That fallback contradicts the exclusive-writer rule. If the worker runs as a separate process with its own write-capable SQL session, it sits outside the gate. §4 step 6's phrase "expected-head/fencing checks" protects the head through compare-and-swap. It does not protect the working set.

**Consequence:** A time-of-check/time-of-use race. An edit can be admitted between the worker's clean-branch check and its live-branch move. The incoming merge could then be applied over that draft, or strand it. This would break the operator's rule against implicit or destructive changes to working data.

**Minimal correction:** Add to Arch §3:

> "Sync-worker mutations of a live branch (dirty/lease check, merge into live, head move) run under that branch's write gate holding a fenced lease. If B5 isolates the worker into a separate process, that process holds remote credentials and integration-branch rights only, and requests live-branch moves through the owning server's gate API. The exclusive writer lock therefore still covers every live-branch write."

Also:
- Add "worker live-branch mutation path" to B5 and B9.
- Add test `IncomingMergeCannotRaceAdmittedEdit` to P6 and FR-189.

# Federation architecture: independent nodes with Dolt history

Author: Codex. Date: 2026-11-10. Status: proposed architecture for the requested new plan; no implementation or deployment performed. Supersedes the forwarding-first federation completion draft for the new versioned federation mode. Existing DirectProxy behavior remains a separate supported feature.

## 1. Authority and scope

The operator requires LAB-OMARCHY as hub, independent local work on every system, two-way synchronization, two-character creator tags in new IDs, branches in the initial release, and mandatory review of merge conflicts. Pull requests are out of scope. Local **version-history commits**, never ordinary edits or SQL saves, trigger synchronization. Nodes poll a durable hub control table periodically or on demand. A hub request must never implicitly commit a user's working changes.

The operator additionally requires Dolt as the **fourth supported database**, retaining SQLite, PostgreSQL and SQL Server, with appropriate schema migrations and a separate data migration tool from all three original providers. This document adopts that planning direction. The exact maintained EF Core provider/package version and pinned Dolt image must pass the compatibility gate before implementation dependencies are installed. Dolt's relational cell/schema merge is the proposed interpretation of Git-style merging; literal line-level text merging is not claimed.

The three-system example uses H = LAB-OMARCHY, A = PAYTON-LEGION2, and B = NODE-B (illustrative second node, not a discovered host). All three run the same application services and local commit/sync worker. The hub additionally hosts the shared remote and control table. This is eventual consistency, not a distributed transaction across all three hosts.

## 2. Topology and storage boundaries

  subgraph H[LAB-OMARCHY: hub and working node]

    HR[Shared project remote: committed history]
    HP --> HW

    HS <--> HR
    HS <--> HC
  end
  subgraph A[PAYTON-LEGION2: node A]

  BS <-->|Dolt committed history| HR
  AS <-->|Poll requests and report outcomes| HC
  BS <-->|Poll requests and report outcomes| HC

Every host uses a local Dolt SQL-server process/container; .NET reaches it through a MySQL-protocol EF provider and its driver selected in P0, subject to compatibility and license review. Dolt is a separate database engine, not an extension installed in an existing MySQL database. It does not wrap arbitrary SQL Server/PostgreSQL/SQLite storage.

For versioned projects, use one Dolt repository/database per logical project on each host. This makes clone/fetch boundaries match project authorization and prevents a project clone from carrying unrelated projects. Local directory paths map to an immutable ProjectId; paths are not distributed identity. The provider resolver must support project-specific routing for enrolled projects; default provider behavior remains unchanged for other workspaces.

The hub's shared remote is a **separate repository/database from the hub's working copy**, optionally served by the same Dolt process. No user edits the shared remote's working set. This matters because a push to a live SQL-server branch can fail when that branch has uncommitted changes. The hub's own draft work must not block A and B from exchanging commits.

Keep host configuration, credentials, enrollment, control requests, receipts, local audit tables and ID-allocation state in a separate unversioned control store. It may use any supported provider, including a separate Dolt database that is never published. Do not merely hide these rows with filters or `dolt_ignore` inside a repository that will be cloned. Existing FR-MCP-AUDIT-001 requires permanent local audit history; preserve it.

Versioned project data includes TODOs, requirements and mappings, use cases, workspace-scoped memories, portable project configuration and explicitly promoted sanitized session-log snapshots. Continuous session-log capture writes local operational storage, without an editing lease; promoting a snapshot is an explicit versioned edit visible in commit preview. Automatic writers must not modify versioned working sets. P0 classifies every entity, relationship, writer and auto-updated column as project-versioned, local-operational, derived or explicitly excluded; no unclassified writer/table is permitted. Global memories, machine paths, tokens and host-specific agent/runtime configuration remain local. Derived search indexes, caches and projections live outside versioned databases and rebuild after accepted head changes. Source-code Git repositories and filesystem assets retain their existing Git/file workflows.

Context topology is explicit: original providers and standalone Dolt keep the full `McpDbContext` and existing/baseline migrations. Versioned mode uses a Dolt-only project context plus a control context with additive migrations for each of the four providers. P0's relationship manifest names every cross-database reference, replacing impossible database FKs/joins with stable soft references and application validators. Historical migration files are never edited; new additive migrations are allowed where the manifest requires.

## 3. Local edits, commits and branch ownership

Ordinary business reads/writes always execute locally. Saving creates durable local working changes but neither publishes them nor creates a version commit. The server exposes status, diff and commit preview. An explicit commit includes ProjectId, branch, expected head, expected working-set fingerprint, author, message and request id. The preview identifies exactly which working changes will be committed. A changed fingerprint rejects the request for a new preview.

One editing owner per project/branch working set is the initial policy. A durable branch lease, with fencing token checked by every mutating service, prevents one agent's commit from accidentally including another agent's unfinished work. Other sessions may read or use a different branch. Expired ownership with dirty data requires explicit takeover review; no automatic discard or commit. This policy applies to the hub too. A future finer-grained staging UX is not needed for this release.

Connections and DbContexts are bound to ProjectId and branch for their entire lifetime; never change a shared connection's branch underneath an active request. Pools must not leak branch/session state. APIs, search, caches and plugin context include branch identity. A branch switch does not switch the source-code Git branch unless separately requested.

Exactly one host-local server process owns writes to each project database, enforced by an exclusive process/storage ownership lock and server-only credentials. Its per-(project,branch) write gate serializes lease issuance/takeover, fence checks, edits, preview-hash validation and Dolt commit. Expiry denies new commands; an already admitted transaction holds the gate through completion, and takeover waits. Process death rolls back uncommitted SQL work before a replacement writer opens. There is no claimed atomic transaction between control storage and Dolt. Use a Dolt-provided working-set hash, verified in P0, not a custom approximate hash. Put the unique commit requestId in a commit trailer; recover lost replies by finding that ID in retained Dolt history and returning the same hash. Never issue a second commit merely because the operational receipt is missing.

After a successful version commit, the local worker records publication intent. Because a version commit and an operational ledger write may not share a transaction, startup/reconnect scans compare local branch history with durable publication receipts and reconstruct missing intents. Repeated scans must not create extra commits. Existing imported commits do not count as newly authored commits for echo scheduling.

Sync-worker mutations of a live branch, including its dirty/lease check, merge into live and head move, run under that branch's write gate holding a fenced lease. Temporary integration may run against a captured snapshot outside the gate, but final application reacquires the gate and rechecks head, working-set fingerprint and editing ownership. If B5 isolates the worker into another process, it holds remote credentials and integration-branch rights only; it requests live-branch moves through the owning server's gate API. Every live-branch write remains covered by the exclusive writer lock.

New record IDs contain the assigned two-character creator tag plus a durable nonreused sequence. Proposed tag alphabet: uppercase ASCII letters/digits. Actual host tag assignments require registration before first tagged creation. The allocator is outside branches so branching or reverting cannot reuse an ID. Restored/cloned writers must prove a safe high-water mark or enroll with a fresh never-reused tag. Replication preserves IDs. Legacy collision resolution uses an explicit mapping and rewrites all references together; equal old IDs are not proof of shared identity.

P0 must lock the exact grammar per entity family, distinguish system-generated and human-assigned IDs, and enumerate validators, traceability tooling, plugin regexes, sort and display rules. Existing canonical requirements and legacy IDs remain valid. No blanket renumbering of the 48 newly registered planning records is intended.

## 4. Publication and synchronization protocol

Use Dolt for object transfer, ancestry, diff, branch creation and merge. Do not implement a competing event-replay database, merge engine or reliable messaging broker.

The shared remote keeps named public branches and private upload refs. A node may upload only its authenticated project-scoped candidate namespace. The hub publication API owns advancement of public branch heads; ordinary node/plugin credentials must not bypass it. Before accepting a candidate it verifies project membership, ancestry, schema compatibility, constraints and domain invariants. The candidate must be a descendant of the expected published head. Use Dolt fast-forward protection plus one durable fenced publisher per project/branch; never force-push a public branch. A stale expected head returns `head_changed`; the node fetches and reconciles again.

This candidate-upload/accept step is **not a PR workflow**: no PR entity, reviewer assignment, approval voting or forge. It is a guarded publication boundary. P0 must demonstrate that the chosen remote transport can enforce these permissions, including direct remote calls; SQL branch permissions alone are not assumed to protect remotesapi. If the transport cannot provide this boundary, select a supported isolated transport arrangement and review it before implementation, rather than exposing writable public refs.

Normal worker sequence:

1. Authenticate, read current published heads, and retrieve its pending control requests. Also inspect unpublished local commits, even if no control request exists.
2. Fetch committed history into remote-tracking refs. Fetching does not commit or overwrite local drafts.
3. If the target local branch is dirty or has an active edit lease, record `waiting_local_work`. Keep the prior readable local state. The user may finish and commit, explicitly discard with normal safeguards, or work on another branch; sync chooses none of these for them.
4. On a clean branch, use a temporary integration branch based on the current local head. Fast-forward if possible; otherwise use Dolt's merge. Preserve the old live branch until the candidate passes review/validation.
5. If Dolt reports conflicts or validation detects a domain violation, persist `needs_review` with base/local/incoming heads and affected entities. Nothing silently wins. Independent projects and branches continue.
6. For a valid clean merge, move the local live branch using expected-head/fencing checks. Publish any new local/merge commits through candidate upload and the hub acceptance API. If the hub advanced, repeat from fetch without creating duplicate effects or force-pushing.
7. Persist receipt with resulting local/published heads, refresh branch-scoped derived indexes and report the outcome. A receipt proves this synchronization target was reached, not that every other node is already current.

Both directions are node-initiated. H's local worker uses the same authenticated remote endpoint, never a file:// URL into a repository served by a running SQL server. No inbound connection to A or B is required. Successful publication advances each subscriber's desired state. Periodic remote-head reconciliation repairs a missed control-store update. Correctness does not depend on an atomic transaction across Dolt and the control database.

## 5. Hub control table

Implement the logical queue as **one durable state row per subscription**, not a command-message broker. Initial polling default: every 30 seconds with up to 20 percent jitter; also poll immediately on reconnect and explicit sync. Local version commits wake the worker immediately. Backoff transient network failure exponentially from 1 second to a 60-second cap, with cancellation; P0 locks final settings against measured behavior.

`SyncSubscription`: unique key `(NodeId, ProjectId, Branch)`; PublishedHead, PublishedGeneration, DesiredGeneration, SyncRequestedUtc, NodeAcceptedHead, NodeReportedGeneration, Outcome, LastSeenUtc, WorkerEpoch and ErrorCode. Publication advances PublishedGeneration and DesiredGeneration. Explicit on-demand requests advance DesiredGeneration even when the published head has not changed; timestamps are informational, never ordering authority. Poll returns authorized rows with an unsatisfied desired generation or a visible blocked outcome. Locally unpublished commits independently wake the worker even if every row is satisfied.

The authenticated worker claims a monotonic WorkerEpoch on reconnect/restart; reports compare epoch and the generation actually observed. A late old-epoch report is rejected. A report for generation g can record its outcome without clearing desired generation g+1. A completed report requires NodeAcceptedHead to include the target and records a durable operation receipt; retries of the same report return that receipt. A transient failure remains unsatisfied with node-local retry scheduling. `waiting_local_work`, `needs_review`, `incompatible_schema` and `denied` are visible non-success outcomes, not completed requests. Do not add per-message leases, acknowledgement deletion or coalescing machinery to this state table.

The hub verifies claimed ancestry against remote objects and the recorded publication receipt for the observed target generation. A node-attested accepted head absent from the remote is provisional until its ancestry is uploaded or published; it cannot complete the subscription generation on assertion alone. Local status may still report that local integration succeeded.

The hub owns a row for each subscribed node, including its own local workspace worker. A committed change is not considered delivered to a node until its recorded accepted head includes the target commit. This permits a later merge commit to satisfy an earlier target without pretending head strings must be equal.

## 6. Conflict review and branches

A review item records project, branch, stable conflict id, common ancestor(s), local head, incoming head, candidate branch, conflict cells/schema, validation failures, author identity, decision and resulting merge commit. The server exposes structured diff/history and resolution preview. A human or explicitly authorized agent selects a resolution; apply requires unchanged source heads and reruns constraints/domain validation. A stale review is refreshed, not applied blindly. Retain `review/<conflictId>` and candidate refs locally and on the remote until a durable resolution receipt permits release under P0's retention policy; control-table references alone are not GC roots.

Sharing `feature/search` publishes that branch; it does not merge it into `main`. A and B can independently check out the same feature history. Merging feature into main is a separate explicit command with expected heads, normal review rules and a new version commit. Protected-branch rights govern who may perform it. Branch deletion/rename requires explicit authorization and rejects active/pending-review references; initial release does not force-delete published history.

Clean Dolt merges remain subject to application rules. Two independent edits to different fields can merge mechanically yet violate a cross-row invariant. Treat that outcome as review-required and keep the valid live head. Deletes, delete/update conflicts, schema conflicts and legacy-ID collisions are included.

## 7. Server and plugin interfaces

Implement a typed federation client and equivalent REST, MCP and REPL surfaces; every first-party plugin exposes the same contract through its existing audited wrapper. New names below are planned interfaces, not existing capabilities:

- `federation.status(projectId, branch)` returns local head, published head as last observed, observed time, dirty state, ahead/behind counts, last commit time, waiting-local-work age, incoming target, connectivity, review count and operation status. `branch.list` shows the same freshness indicators. Flag stale branches at a configurable threshold; never automatically delete or rebase them. Never call a stale observation globally synchronized.
- `federation.diff(projectId, branch, from, to)` and `federation.history(...)` support preview without mutation.
- `federation.commit(projectId, branch, expectedHead, expectedWorkingSet, leaseToken, message, requestId)` creates a local version commit and pending publication intent. Reply distinguishes `committed_locally` from `published`.
- `federation.sync(projectId, branch, requestId)` schedules/wakes work and returns OperationId; `federation.operation.get(operationId)` returns durable status. Cancellation stops waiting/work safely without claiming already-published commits were undone.
- `federation.branch.list/create/select/merge` use explicit project/branch contexts and expected heads. Branch selection is session-scoped and survives plugin reconnect only after server revalidation.
- `federation.conflicts.list/get/preview/resolve` retain the full review evidence and reject stale input.
- Administrative `federation.enroll`, `subscriptions`, `control.poll`, `control.report`, `publication.accept`, `migration.plan/run/resume/verify/cutover/status` are permission-separated from ordinary editing.
- `federation.maintenance.preflight`, `federation.maintenance.attest` and `federation.maintenance.status` expose the same permission-separated maintenance service to deployment tooling and plugins. They enumerate drafts/branches, bind readiness to a maintenance epoch and inventory fingerprint, and report blockers before a binary swap.

Use existing normalized error envelopes with stable codes: `head_changed`, `working_set_changed`, `branch_busy`, `waiting_local_work`, `needs_review`, `incompatible_schema`, `unsupported_contract`, `unauthorized_project`, `lease_lost`, `remote_unavailable`, `migration_verification_failed`. Public DTOs and APIs require XMLDocs and OpenAPI documentation. Plugin bootstrap advertises capabilities and server contract version; old plugins fail clearly on unsupported commands without falling back to arbitrary SQL or shell access. Local request authorization uses existing local identities; hub revocation is enforced on reconnect and does not retroactively erase offline work.

Audit identifies the real agent/user and records preview, commit, publication, incoming acceptance, review, migration and source references. Replicating data does not execute original business commands again. GitHub actions, email and other external effects require their existing explicit commands and durable effect IDs; importing an effect record never sends it again.

Commit preview runs the existing sanitizer and selected secret-detection facility over promoted snapshots and the versioned diff; detected secrets block commit. Deleting or reverting a record does not erase earlier versions. A disclosure incident requires credential rotation, removal/revert of live content and, only under separate explicit operator approval, coordinated history rewriting plus re-cloning all subscribers. Normal synchronization never force-pushes as an incident shortcut. P0 locks the detector and history-retention policy; do not claim existing sanitization finds every possible secret.

## 8. Fourth database provider and schema migration

Current source evidence: `McpDatabaseProviderFactory` registers SQLite/PostgreSQL/SQL Server strategies; `McpDatabaseProviderKind` and `McpDbContextFactory` need a Dolt case. Storage targets net10.0 and central EF Core packages are 10.0.0. A .NET 9 example is not proof of EF10 compatibility.

Add canonical provider `dolt`, `DoltMcpDatabaseProviderStrategy`, configuration validation, design-time connection resolution, runtime health/provider diagnostics, and dedicated `QBrainAi.Storage.DoltMigrations` assembly with its own snapshot and baseline. Do not run SQL Server/PostgreSQL/SQLite migration SQL on Dolt. Preserve existing providers, names, defaults and historical migration files; additive migrations are permitted where the approved context manifest requires. Add Dolt to package/build/deployment/test discovery and database administration UI/CLI selections. Runtime and design-time model options must match.

P0 selects a maintained EF10-compatible MySQL provider after executing real schema/query/transaction tests against a pinned Dolt image. Do not silently downgrade EF, install a prerelease provider, or write a bespoke EF provider if compatibility fails; report concrete alternatives for the operator. Test collations/case sensitivity, maximum index/key lengths, decimal precision, UTC timestamps, GUID/binary/text/JSON mappings, identity generation, optimistic concurrency, FK/delete semantics, raw SQL, query translation, migrations and parameterization. SQLite-specific search SQL must use a provider-compatible derived-index path rather than fail on Dolt.

Project-versioned and control contexts have separate migration histories. **Never run EF migrations at startup against a versioned project database.** Only the hub maintenance role applies project migrations on `maintenance/schema-<version>`, commits schema and migration-history rows together, validates and publishes the schema commit. Subscribers obtain schema changes through history exchange after their binaries advertise support, never by independently executing the same migration. Worker-to-hub protocol versions are negotiated separately from plugin capabilities; unsupported contracts return `unsupported_contract`.

Use compatible expand changes first. Contract changes wait for every enrolled subscriber/branch covered by the upgrade to acknowledge, or for explicit de-enrollment and a recovery plan for its unpublished work. An offline node cannot be magically quiesced: it may continue its supported local work, while the hub refuses incompatible publication. After binary upgrade, old-schema unpublished commits and feature branches merge the designated schema head through normal review and validation. P0 proves this path on representative schema changes. Do not point an old binary at an unsupported schema or silently discard old-schema commits. Control/standalone databases retain their ordinary controlled migration path.

Choose the **pre-upgrade draft-disposition policy** for this release: before replacing the binary, enumerate every local project branch, require drafts to be explicitly committed or otherwise resolved by their owner, and fetch the designated schema head. A dirty branch blocks the upgrade without touching its draft; no automatic commit/discard. Each branch stays closed to domain writes until the local sync worker merges the designated schema head into it (history merge, never local EF migration execution) and validation passes. A catch-up conflict opens needs_review for that branch only; other integrated branches reopen. The new EF model does not serve an unsupported old-schema branch; history/diff/review use the schema-aware maintenance surface. Retain old binaries/backups until verification. Unpublished commits survive in history; this policy does not assume simultaneous N/N-1 EF model compatibility.

Contract readiness is an authenticated node-attested inventory of **all** local branches, including unpublished ones, with each head and expand-schema ancestry, bound to a maintenance epoch and inventory fingerprint. A missing/offline attestation or a branch lacking the expand head blocks the contract step unless explicitly de-enrolled with recovery disposition. After attestation, branch creation/restore from an old schema is fenced until the transition finishes; historical branches may remain readable through compatible tooling but cannot become writable without catch-up. The hub cannot infer unpublished branch readiness from its remote alone.

## 9. Data migration tool

Deliver `qbrain database migrate` (planned CLI surface) with commands `plan`, `run`, `resume`, `verify`, `status`, `cutover` and `abort`. REST/plugin administration wraps the same application service. Source providers are SQLite, PostgreSQL and SQL Server; target is Dolt. Source access is read-only, and a source backup/snapshot is required. The command accepts secret references, never prints credentials, and does not write connection strings into receipts.

`plan` inventories source schema/version, projects, tables, relationships, provider-specific values, local-only data, legacy pending federation records and identity collisions. It emits an immutable manifest with MigrationId, source fingerprint, target/schema version, transformation rules and per-table counts. A dry run validates mappings and target compatibility without copying project rows or changing routing. Unmapped tables, lossy conversions and ambiguous legacy identity mappings block the run.

Migration has two explicit modes. **seed** is selected exactly once per ProjectId: it creates an isolated target, applies the initial project schema and imports the approved seed snapshot to establish C0. **join** clones that published C0, imports the joining host's mapped legacy differences onto `migration/<tag>/<MigrationId>` as an ordinary descendant commit, and uses the normal merge/review/publication path to join main. Never independently create three unrelated root histories and assume they will merge. The identity manifest accounts for each source row as already identical in C0, an explicitly mapped delta, a deliberate reviewed deletion or a local-only/excluded record. Absence on a joining source alone is not permission to delete a seed row.

Mapped deltas distinguish **new identity** inserts from **legacy divergence**, where the same mapped identity has different seed/join content. Every legacy divergence requires a recorded per-row review decision (keep seed, take join or manual value) in the immutable transformation manifest and audit **before the join commit is created**. This is required even when Dolt would fast-forward or merge cleanly: a common root created during migration does not prove that earlier independent edits were intentional overwrites. Unreviewed divergence blocks import/commit and is surfaced as needs_review. A reviewed manifest is versioned by hash; changing a decision creates a new manifest revision and cannot silently resume an earlier transformation.

Divergence is evaluated over B2-classified versioned columns after canonical normalization. Review decisions may be authored as explicitly scoped rules by entity and column class that expand to an enumerated per-row list in the manifest; there is no wildcard default. Operational timestamps/counters excluded by B2 do not generate artificial project-content conflicts.

Both modes create isolated targets and copy parent/child graphs in dependency order using stable keyset pages. Bulk copy is not a replay of business commands. Preserve IDs, relationships, timestamps, versions, soft deletes and complete sanitized session graphs through explicit promotion. Local audit remains local in control storage or a retained readable source archive according to the manifest. Credentials and source-host operational actions are not activated on the destination.

Use a quiesced source snapshot for initial release. No custom CDC or live dual-write is introduced. Each target batch transaction records its MigrationId/table/key range in a target-local journal; resume verifies that journal and source fingerprint before continuing. A copied batch with a lost acknowledgement is recognized, not inserted twice. Changed source snapshot or changed transformation manifest requires a new migration, not a blind resume.

`verify` compares counts and canonical typed row hashes by project/table, checks FK graphs and explicit excluded-row accounting, validates ID maps and sequence high-water marks, performs representative server reads, and verifies the initial Dolt commit. Canonical hashing specifies null, UTF-8 text, decimal scale/value handling, UTC precision and binary encoding; raw provider serialization is not a comparison standard. Verification failures name the project/table/key and preserve both sides.

`cutover` requires a successful verification receipt matching the exact frozen source and target heads; stops the affected workspace, switches its provider mapping atomically, rebuilds derived state and runs smoke checks before reopening writes. Abort before cutover leaves the source active and retains diagnostics. If writes have occurred after cutover, returning to the source requires an explicit reconciliation/export plan; never silently lose Dolt-only commits. Source databases/backups are retained, not dropped. Each node's divergent legacy data is inventoried independently; do not assume cloning the hub can replace it safely.

For join mode, verify binds to the immutable migration-branch commit and proves C0 is its ancestor. The destination workspace remains closed to writes until that commit has been integrated into local main through required review and validation. The cutover receipt records source snapshot, transformation manifest, migration commit, resulting local main head and published target observation. Verify both imported-source accounting at the migration commit and final-domain invariants at the main head; do not compare a post-merge head to a pre-merge verification hash as if they were identical.

An automated reverse migration from Dolt to original providers is out of scope. Cutover approval explicitly records that rollback after new writes requires manual reconciliation or a separately approved recovery tool.

# Three-system federation walkthrough and requirements

Author: Codex. Date: 2026-11-10. Proposed behavior for [the new architecture](2026-11-10-federation-dolt-architecture.md), not a report of deployed behavior. H=LAB-OMARCHY, A=PAYTON-LEGION2, B=illustrative NODE-B. Project Atlas and symbolic commit names C0/A1/B1/H1/M1 are examples, not real records or hashes. The hub has a local working copy and a separate shared committed-history remote.

## Standard workflows

### U01: enroll and start the same project

H registers Atlas with immutable ProjectId and an initial approved C0. A and B enroll with distinct immutable node tags, map their own filesystem paths to Atlas, receive authorized subscriptions and clone C0. Each can now read and edit locally. An existing nonempty node database is inventoried/migrated, never overwritten by the clone. Server: enrollment, project identity, initial snapshot, scoped credentials. Plugins: discover/select project and branch; show local/remote heads. Requirements: FR-MCP-176,182,185,187.

### U02: node A edits, then commits

A edits a TODO. Its local draft survives restart, but H and B remain at C0 and no sync is triggered. A previews and explicitly commits A1; this wakes synchronization. After validated publication, the hub remote is A1 and H/B receive control requests. Their workers fetch and accept A1 on clean branches; their local reads now include the TODO. Server: explicit commits, publication and control generation. Plugins: diff/commit/status; distinguish local commit from publication. Requirements: FR-MCP-174,175,178,179,183,189.

### U03: work directly on the hub

H edits in its local working copy while A and B continue independently. H commits H1 and its normal worker publishes it to the shared remote; A/B receive requests. H's uncommitted draft before H1 neither travels nor prevents A/B publication because the hub remote is a separate repository. Requirements: FR-MCP-174,175,178,184.

### U04: simultaneous clean edits on all three systems

Starting at C0, A commits a title edit A1, B commits an unrelated description edit B1, and H commits a separate requirement H1. A publishes first. B fetches A1, Dolt merges A1+B1 into M1, validation passes and M1 publishes. H fetches M1, merges H1 into M2 and publishes. A/B accept M2. Every original commit remains an ancestor. A publication race returns head_changed and repeats fetch/merge; no force push. This assumes nonconflicting cells and valid domain relationships. Requirements: FR-MCP-178,181,188.

### U05: conflicting edits to the same field

A and B both change one requirement's priority from the same base to different values and commit independently. A publishes A1. B receives A1 while holding B1; merge reports a conflict. B retains its last valid local state, and H/A retain A1. B's plugin displays base/local/incoming values and requests review. A reviewed resolution creates M1 including both histories, passes validation and publishes; H/A then accept it. Changed heads invalidate an old resolution. Delete/update and schema conflicts use the same visible review boundary. Requirements: FR-MCP-180,181,183.

### U06: hub unreachable, then reconnect

The hub connection fails. H, A and B still execute local business operations and make H1/A1/B1 commits. A/B record pending publication; they do not return queued-only results for local business writes. On reconnect they authenticate, reconcile remote heads and process requests plus their own unpublished commits. Merge/review follows U04/U05. An empty hub queue does not strand local commits. No automatic hub failover is claimed. Requirements: FR-MCP-174,175,178,179,181,185.

### U07: incoming commit while node B has a draft

B has uncommitted edits at C0. A publishes A1; B polls and fetches history, but records waiting_local_work instead of committing, discarding or overwriting its draft. B's user finishes the draft and explicitly commits B1 (or separately chooses another authorized disposition). Then reconciliation proceeds. Fetch succeeded does not mean the branch was synchronized. Requirements: FR-MCP-175,180,183,189.

### U08: divergent feature work and deliberate merge

A creates feature/search from C0 and commits F1. Publication shares feature/search; main remains C0 on all systems. B selects feature/search to inspect or continue it and commits F2. H can review the branch data. An authorized explicit merge into main creates M1 and triggers normal publication. Branch selection is per session, never a process-wide switch. No PR is created. Requirements: FR-MCP-177,180,183,189.

### U09: lost response or crash during synchronization

A publishes A1 but loses the success response. H has A1 and unsatisfied subscription state. A restarts, checks remote ancestry and its request receipt, and recognizes publication without creating A2 or repeating an external business action. A missed hub state update is repaired by head-generation reconciliation. A new worker epoch rejects stale reports from the old worker. Reporting generation g must not clear desired g+1. Requirements: FR-MCP-179,181,188.

### U10: migrate an existing project

The migration tool plans SQLite, PostgreSQL or SQL Server sources, inventories local-only versus shared data, detects legacy-ID collisions and checks the Dolt schema. Exactly one seed establishes C0 per project. Other nodes clone C0 and import their frozen legacy differences on migration branches descended from C0, then merge/review them normally. Verification accounts for source rows already in C0, mapped deltas and explicitly reviewed exclusions/deletions. A failed verification leaves the original provider active. No unrelated root histories or implicit deletion of seed rows are allowed. Requirements: FR-MCP-182,184,186,187.

Same-identity rows with different legacy contents require a recorded keep-seed/take-join/manual-value review before the join commit, even if Dolt would merge cleanly. Verify the immutable migration commit and the reviewed main result; keep destination writes closed until integration and verification finish.

### U11: node running an older schema/application

H's maintenance role publishes a supported schema upgrade. B advertises an older capability and records incompatible_schema; it does not apply it or claim to be current. B may continue supported local work while publication is held. After binary upgrade, B merges the schema head into unpublished work and feature branches through review/validation. Nodes never independently run EF migrations on versioned project startup. Incompatible contract changes wait for subscriber acknowledgement or explicit de-enrollment/recovery. Requirements: FR-MCP-181,183,186.

Before swapping B's binary, its owners explicitly commit or resolve all drafts and the schema head must be available locally; otherwise upgrade waits without touching drafts. B attests every local branch, including unpublished ones. Maintenance preflight gates deployment. Each branch reopens only after its local worker merges the designated schema history and validation passes; a catch-up conflict blocks that branch only. The new EF model never edits an unsupported dirty working set or independently executes project migrations.

### U12: two agents on one host

Two plugins select Atlas/main on A. Only the editing lease owner may mutate its working set. The other agent reads or selects a separate branch. The first agent's commit preview binds to its expected working-set fingerprint; takeover cannot silently absorb its draft. Plugin reconnect revalidates the lease and context. Requirements: FR-MCP-177,183,189.

using Microsoft.EntityFrameworkCore;

namespace QBrainAi.Support.Mcp.Storage.Database;

/// <summary>
/// Resolves provider aliases to canonical strategies and applies provider-specific
/// <see cref="McpDbContext"/> configuration.
/// </summary>
public static class McpDatabaseProviderFactory
{
    private static readonly IReadOnlyList<IMcpDatabaseProviderStrategy> s_strategies =
    [
        new SqliteMcpDatabaseProviderStrategy(),
        new PostgreSqlMcpDatabaseProviderStrategy(),
        new SqlServerMcpDatabaseProviderStrategy(),
    ];

    /// <summary>Gets the canonical provider names accepted by the factory.</summary>
    public static IReadOnlyCollection<string> SupportedProviders =>
        s_strategies.Select(x => x.CanonicalName).ToArray();

    /// <summary>
    /// Resolves the requested provider alias to the canonical provider strategy.
    /// </summary>
    /// <param name="providerName">Requested provider value from configuration or tooling.</param>
    /// <returns>The matching provider strategy.</returns>
    public static IMcpDatabaseProviderStrategy ResolveStrategy(string? providerName)
    {
        var normalized = providerName?.Trim();
        if (string.IsNullOrWhiteSpace(normalized))
            normalized = "sqlite";

        var strategy = s_strategies.FirstOrDefault(candidate =>
            candidate.Aliases.Any(alias => string.Equals(alias, normalized, StringComparison.OrdinalIgnoreCase)));

        if (strategy is null)
        {
            throw new InvalidOperationException(
                $"Unsupported MCP database provider '{providerName}'. Allowed values: {string.Join(", ", SupportedProviders)}.");
        }

        return strategy;
    }

    /// <summary>
    /// Builds a resolved provider option set using the selected provider strategy.
    /// </summary>
    /// <param name="providerName">Requested provider value from configuration or tooling.</param>
    /// <param name="connectionString">Resolved provider connection string.</param>
    /// <param name="migrationsAssembly">Optional migration assembly override.</param>
    /// <returns>A normalized provider option set.</returns>
    public static McpDatabaseProviderOptions CreateOptions(
        string? providerName,
        string connectionString,
        string? migrationsAssembly = null)
    {
        var strategy = ResolveStrategy(providerName);
        return new McpDatabaseProviderOptions(
            strategy.Kind,
            strategy.CanonicalName,
            connectionString,
            string.IsNullOrWhiteSpace(migrationsAssembly) ? strategy.DefaultMigrationsAssembly : migrationsAssembly);
    }

    /// <summary>
    /// Applies the resolved provider configuration to an EF Core options builder.
    /// </summary>
    /// <param name="optionsBuilder">Options builder to configure.</param>
    /// <param name="providerOptions">Resolved provider settings.</param>
    public static void Configure(DbContextOptionsBuilder optionsBuilder, McpDatabaseProviderOptions providerOptions)
    {
        ArgumentNullException.ThrowIfNull(optionsBuilder);
        ArgumentNullException.ThrowIfNull(providerOptions);

        ResolveStrategy(providerOptions.ProviderName).Configure(optionsBuilder, providerOptions);
    }
}

using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Design;
using QBrainAi.Support.Mcp.Storage.Database;

namespace QBrainAi.Support.Mcp.Storage;

/// <summary>
/// Design-time factory for <see cref="McpDbContext"/>.
/// Used by EF Core tooling (dotnet-ef) to create a context instance at design time.
/// </summary>
public sealed class McpDbContextFactory : IDesignTimeDbContextFactory<McpDbContext>
{
    private const string DefaultSqliteConnectionString = "Data Source=mcp_design_time.db";
    private const string DefaultPostgreSqlConnectionString = "Host=localhost;Port=5432;Database=mcp_design_time;Username=postgres;Password=postgres";
    private const string DefaultSqlServerConnectionString = "Server=(localdb)\\MSSQLLocalDB;Database=mcp_design_time;Trusted_Connection=True;TrustServerCertificate=True";

    /// <inheritdoc />
    [UnconditionalSuppressMessage(
        "Trimming",
        "IL2026:Members attributed with 'RequiresUnreferencedCodeAttribute' require dynamic access otherwise can break functionality when trimming application code",
        Justification = "This factory is only for EF Core design-time tooling; trimmed runtime hosts do not invoke it.")]
    public McpDbContext CreateDbContext(string[] args)
    {
        var providerName = GetArgumentValue(args, "provider")
            ?? QBrainAi.Common.AgentCli.ProductEnvironment.GetLegacy("MCP_EF_PROVIDER")
            ?? "sqlite";
        var connectionString = ResolveConnectionString(providerName, args);
        var migrationsAssembly = GetArgumentValue(args, "migrations-assembly")
            ?? QBrainAi.Common.AgentCli.ProductEnvironment.GetLegacy("MCP_EF_MIGRATIONS_ASSEMBLY");
        var providerOptions = McpDatabaseProviderFactory.CreateOptions(providerName, connectionString, migrationsAssembly);

        var optionsBuilder = new DbContextOptionsBuilder<McpDbContext>();
        McpDatabaseProviderFactory.Configure(optionsBuilder, providerOptions);
        return new McpDbContext(optionsBuilder.Options);
    }

    private static string ResolveConnectionString(string providerName, string[] args)
    {
        var explicitConnectionString = GetArgumentValue(args, "connection")
            ?? QBrainAi.Common.AgentCli.ProductEnvironment.GetLegacy("MCP_EF_CONNECTION_STRING");
        if (!string.IsNullOrWhiteSpace(explicitConnectionString))
        {
            return NormalizeSqliteConnectionString(providerName, explicitConnectionString);
        }

        return McpDatabaseProviderFactory.ResolveStrategy(providerName).Kind switch
        {
            McpDatabaseProviderKind.Sqlite => NormalizeSqliteConnectionString(
                providerName,
                GetArgumentValue(args, "sqlite-data-source")
                    ?? QBrainAi.Common.AgentCli.ProductEnvironment.GetLegacy("MCP_SQLITE_DATA_SOURCE")
                    ?? DefaultSqliteConnectionString),
            McpDatabaseProviderKind.PostgreSql => QBrainAi.Common.AgentCli.ProductEnvironment.GetLegacy("MCP_POSTGRES_CONNECTION_STRING")
                ?? DefaultPostgreSqlConnectionString,
            McpDatabaseProviderKind.SqlServer => QBrainAi.Common.AgentCli.ProductEnvironment.GetLegacy("MCP_SQLSERVER_CONNECTION_STRING")
                ?? DefaultSqlServerConnectionString,
            _ => throw new InvalidOperationException($"Unsupported MCP database provider '{providerName}'."),
        };
    }

    private static string NormalizeSqliteConnectionString(string providerName, string connectionString)
    {
        if (McpDatabaseProviderFactory.ResolveStrategy(providerName).Kind != McpDatabaseProviderKind.Sqlite)
        {
            return connectionString;
        }

        return connectionString.Contains('=', StringComparison.Ordinal)
            ? connectionString
            : $"Data Source={connectionString}";
    }

    private static string? GetArgumentValue(string[] args, string key)
    {
        if (args.Length == 0)
        {
            return null;
        }

        var prefix = $"--{key}=";
        for (var index = 0; index < args.Length; index++)
        {
            var arg = args[index];
            if (arg.StartsWith(prefix, StringComparison.OrdinalIgnoreCase))
            {
                return arg[prefix.Length..];
            }

            if (string.Equals(arg, $"--{key}", StringComparison.OrdinalIgnoreCase) && index + 1 < args.Length)
            {
                return args[index + 1];
            }
        }

        return null;
    }
}

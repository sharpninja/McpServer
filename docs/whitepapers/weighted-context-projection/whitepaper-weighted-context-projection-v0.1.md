## Executive summary

Long-horizon agent sessions fail more often from **context loss under host auto-compaction** than from raw model capability limits **(operational observation; not a measured benchmark claim)**. Plugin hooks can inject memories and react to compact events, but they do not own the host transcript. Cross-session MCP memory (the `memory_*` tools — remember / recall / explore / consolidate / promote, named in full in point 5 below) is necessary and already shipping, yet it is the wrong primary store for *turn-by-turn task state*. Whitespace-token estimator benches (including `memory-bench-whitespace`) are **not** provider-metered savings proof and must not be rehabilitated as such.

This whitepaper proposes **Weighted Context Projection**:

1. An append-only **SessionLog** holds the durable transcript (turns are never permanently deleted).
2. Each turn receives a **relative weight** for how much it advances **current work toward completion**.
3. A live **`contextProjection`** under a hard token budget expands pinned / high-weight turns, summarizes mid-weight turns, and omits low-weight turns while keeping them recoverable.
4. Reweighting can **re-admit** a previously omitted turn from SessionLog into the projection.
5. MCP memory tools (`memory_remember` / `memory_recall` / `memory_explore` / `memory_consolidate` / `memory_promote`) bridge durable cross-session facts so the projection stays small. Where this paper uses the shorter verb forms, they are shorthand for those tool names.
6. Prefer an **outer orchestrator** that assembles the projection and invokes frontier models via **sessionless CLI oneshots**, so host auto-compaction is unnecessary for the *model-facing* context—when we own assembly. The deployment alternatives and their trade-offs are analyzed in IMPL §6.

The design goal is operational continuity after reproject (or after a host compact fallback), not token-savings theater. Success is: the agent continues the task without the operator re-pasting lost constraints.

Joint value across a pair of turns, link revalidation, plan-level scope and progress, and Hostile Validation outcome records are specified in §14 through §24. Those sections are design. They are not measured efficacy, and they are not a claim that operational Perplexity HV has run.

## 1. Problem

### 1.1 The real friction is compaction / context loss

Operator workflows that span dozens to hundreds of turns accumulate tool traces, dead ends, corrected plans, and quiet constraints (“never push to main”, machine paths, standing prefs). Host environments eventually compact. Compaction is typically **lossy and irreversible from the model’s point of view**: the full turn text leaves the live window; a summary may or may not preserve what mattered for *task progress*.

That is the failure mode this paper addresses. It is not “we estimated fewer whitespace tokens.”

### 1.2 What already shipped (and what it is not)

Three capabilities already exist. What matters for this paper is that none of them is the projection engine it proposes.

**A durable cross-session memory layer.** Workspace-scoped tools persist facts, decisions, preferences, procedures, and entities across sessions. A typed write path carries title, type, tags, confidence, and provenance, alongside a thinner compatibility CRUD surface for plain records; retrieval, exploration, promotion between layers, consolidation of near-duplicates, and revert are all present. Each of the eight official host plugins injects the required-memory block at host-supported request boundaries. This layer holds standing truth that should outlive any one session. It does not answer which turns of the *current, unfinished* task still deserve space in the live window.

**An operator-facing memory management surface.** A separate Viewer provides human inspect-and-edit CRUD over those memory records. It is a management view over the memory layer—not SessionLog, and not a projection engine. It is orthogonal to the scoring and packing this paper describes.

**Plugin hooks, unevenly distributed.** Claude / Grok / Copilot expose more hook points than Codex / Cline / OpenCode today. Injection and reaction points include `UserPromptSubmit`, `PreCompact`, and `PostCompact`, where the host exposes them. Hooks inject and react; they do **not** own the full host transcript and do **not** prevent the host from compacting. That asymmetry is why IMPL §6 treats plugin-only deployment as interim hardening rather than an end state.

### 1.3 Estimator benches are not savings proof

The multiturn estimator bench (`memory-bench-whitespace`) measures proxy token counts under controlled whitespace / message-shape assumptions. It is useful for relative plumbing checks. It is **not** provider-metered billing evidence. This whitepaper deliberately refuses to cite estimator deltas as token-savings proof. Any later cost claim must use provider-reported usage or an equivalent metered path.

### 1.4 Design gap

Memory alone stores facts. Compaction alone discards history. Neither continuously answers: *given the current unfinished work, which past turns still deserve tokens in the live window—and which can be stubbed until needed again?*

## 2. Background: MCP memory vs SessionLog vs UI

| Layer | Durability | Granularity | Primary job | Compaction relationship |
| --- | --- | --- | --- | --- |
| MCP Memory (002) | Cross-session | Facts / notes / promoted items | Standing prefs, constraints, machine truths | Injected into prompts; shrinks need for long projection |
| SessionLog (extend existing `sessionlog_*`) | Session-durable, append-only | Full turns (request + intermediates + response) | Truth store for reweight / re-admit | Survives host compact; projection is derived |
| Manager Memory UI | Operator-facing CRUD | Memory records | Human inspect / edit | Orthogonal to projection algorithm |
| Host transcript | Ephemeral / host-owned | Whatever the IDE keeps | Live chat UX | Subject to auto-compact; not authoritative |

**Principle:** SessionLog is the append-only ledger. On the paths the current services use, append-only is application-enforced by convention and a guard test above the database, not by the schema (§6). MCP already ships **`sessionlog_*` APIs** for session/turn logging; this design **extends** that ledger with weight / pin / projection metadata—it is not a wholly greenfield store. Memory is the cross-session digest. Projection is the ephemeral, budgeted view assembled for the model. UI is for humans.

## 3. Design principles

1. **Never permanently delete turns from SessionLog.** Omission from the projection is not deletion. Content survival on the paths the current services use is application-enforced by convention and a guard test above the database, not by the schema. The projection inherits that convention (§6).
2. **Weight relative to current work progress**, not raw self-information, recency alone, or “interestingness.”
3. **Hard token budget** on the live projection. Soft targets without enforcement invite drift.
4. **Re-admit is first-class.** If a quiet constraint suddenly matters, the scorer must be allowed to pull the full turn back from SessionLog.
5. **Pins beat scores, and they beat stubbing.** Explicit operator, system, or acceptance pins stay expanded until unpinned. An `invalidates` edge or an introduced-harm verdict attaches a marker beside the expanded pin. It does not stub or omit the pin (§6.2). Unpinned targets of those events are marked stubs.
6. **Memory bridges the long tail.** Standing facts leave the projection via the MCP memory write path (`memory_remember`) rather than forever occupying mid-tier summary slots.
7. **Own assembly when possible.** If the orchestrator builds the prompt, host auto-compaction becomes optional for *model-facing* context—not for host UI chrome.
8. **No fake metrics.** Do not claim savings from estimators; measure continuation quality and budget adherence.

## 4. Architecture

### 4.1 Components

```
Operator / Host UX
       |
       v
+------------------+     append      +---------------+
|  AgentInvoker    | --------------->| SessionLog    |
|  (CLI / hooks)   |                 | (append-only) |
+--------+---------+                 +------+--------+
         |                                  |
         | projection                       | turns + metadata
         v                                  v
+------------------+  weights/pins   +------------------+
| ContextProjector | <---------------| TurnValueScorer  |
+--------+---------+                 +------------------+
         |
         | standing facts
         v
+------------------+
| MemoryBridge     | ----> MCP memory_remember / memory_recall / REQUIRED MEMORIES
+------------------+
         |
         v
+------------------+
| CompactFallback  |  (PreCompact hooks when host still owns transcript)
+------------------+
```

- **SessionLog:** Durable transcript built on existing MCP `sessionlog_*` APIs, extended with weight / pin / projection metadata. Stores full turn payloads plus that metadata.
- **TurnValueScorer:** Assigns relative weights (and optional rationales) for advancing *current* work.
- **ContextProjector:** Builds `contextProjection` under budget: expand / summarize / omit.
- **MemoryBridge:** Promotes durable facts out of the turn stream into MCP memory.
- **AgentInvoker:** Invokes frontier agents (prefer sessionless CLI oneshot); otherwise injects into host.
- **CompactFallback:** When stuck inside a host that will compact anyway, use PreCompact to dump / reweight / inject a projection stub.

### 4.2 Core data fields

Per turn (illustrative schema; Phase 1 formalizes):

| Field | Intent |
| --- | --- |
| `turnId` | Stable identity in SessionLog |
| `sessionId` | Session scope |
| `payload` | Full request + intermediates + response (or content-addressed blob ref) |
| `weight` | Independent scalar relevance score ∈ [0, 1] for unfinished work. Not a normalized distribution: weights do not sum to 1 across a session, so `Δweight` hysteresis thresholds (§6.1) and the density packing in §6 compare absolute values. | `pin` | Boolean / pin class (operator, system, acceptance) |

## 5. Scoring model

### 5.1 What “relative weight” means

Weight answers: **If we are trying to finish the current unit of work, how much does this turn still matter in the live window?**

That question is relevance. It is not a progress count. This paper does not define a second numeric "progress." The only progress quantity that may revise `weight` is the authoritative plan-level series in §19.1, and only by the revision rules in §19.5. A progress floor applies only while §19.5 still calls the contribution active. A finished contribution keeps its audit credit and loses the floor on the next snapshot, without a verdict that calls the credit false. Pending intent, an actor's claim, and the "progress narrative" label below are not that quantity and MUST NOT be treated as inputs to packing.

Examples of high weight:

- Current plan and acceptance criteria still open.
- Unresolved blocker with exact error text needed for the next fix.
- Operator constraint that has not been externalized to memory yet.
- Latest tool result that the next action depends on.

Examples of low weight (omit or stub):

- Explored-and-abandoned dead ends whose conclusions are captured elsewhere.
- Verbose successful tool dumps superseded by a later concise status.
- Social / meta chatter with no residual task dependency.

Mid weight: progress narrative worth a summary (“tried A, failed for reason R, switched to B”).

### 5.2 Scorer v1 (rules) vs v2 (judge)

**v1 — deterministic / heuristic rules (Phase 4 start):**

- Boost: pinned, open TODOs, files still in active edit set, last N turns, turns cited by current plan, turns containing unmet constraints.
- Penalize: turns fully superseded by a later turn’s explicit “supersedes turnId”, pure ack turns, huge tool payloads already summarized into memory.
- Hysteresis applies only to discretionary score-driven `projectionState` changes. Require `|Δweight|` of at least the §6.1 threshold before such a change. Hysteresis MUST NOT block a mandatory override (pin, budget demotion, invalidation, introduced-harm).

**v2 — LLM / learned judge:**

- Periodic or per-turn judge prompt: given goal + recent projection + candidate turn stubs, re-score candidate turns under budget. The judge emits one `∈ [0, 1]` score per turn (see §4.2). Those scores are not a normalized distribution: normalization would make one turn's score depend on unrelated turns and break `Δweight` hysteresis. Independent outputs do not mean the judge ignores the other stubs in the same prompt. Noticing a relation among those inputs is contextual inference. Writing the scalar does not persist that relation and does not co-admit the turns. Persistence and co-admission are §15 and §16.1.
- Still write results back to SessionLog; never delete.
- Keep the §6.1 split: hysteresis on discretionary score changes, mandatory overrides above them.

### 5.3 Reweight triggers

Preferred: **after each turn**. Acceptable: at compact gates / budget pressure / operator “reproject” command. Continuous reweighting is the intended mechanism that makes host auto-compaction *unnecessary for model-facing context* when assembly is owned externally **(design intent until Phase 2 demonstrates it)**.

## 6. Projection algorithm

Informal algorithm under hard budget `B`. The authoritative order is §6.1. This list is that procedure with the packing rule written out. Link admission and introduced-harm (steps 3 and 4 of §6.1) run before the density packing in step 5 here.

1. Load SessionLog turns for `sessionId` plus standing memories from MemoryBridge.
2. **Charge the fixed prefix against the budget first.** Compute `B_turns = B - tokens(system prefix) - tokens(standing memories)`, where the standing memories are those listed in `standingMemoryIds[]`. Standing memories are model-facing and therefore consume `budgetTokens` exactly as turns do; IMPL §6's stable-prefix guidance makes them cheap to cache, not free to send. Fail closed: if `B_turns <= 0`, surface error / demote or consolidate standing memories via `consolidate` / ask operator—do not silently overflow `B`.
3. Mark active pins `expanded` (§6.2). Fail closed: if pins alone, including their mandatory markers, exceed `B_turns`, surface error, force memory promotion, or ask the operator. Do not silently drop pins, and do not treat hysteresis as a reason to drop them.
4. Refresh weights. The refresh may change `weight`. It MUST NOT by itself change `projectionState`. State changes follow §6.1.
5. Allocate the remaining `B_turns` by **value density**, not raw weight, over turns not already forced by a mandatory override:
   - Compute `density = weight / max(tokenEstimate, 1)` for each non-pinned turn.
   - Sort by `density` descending (stable tie-break: `weight` descending, then recency, then `turnId`).
   - **Demote** unpinned turns whose payloads no longer fit, lowest density first. A demotion caused by a new pin, a mandatory marker, a joint link endpoint, or the live result is a budget demotion even when weight is unchanged (§6.1).
   - **Do not expand** an omitted or summarized turn only because residual capacity grew (a pin was removed, a neighbor was demoted, or a render shrank). Expansion requires a discretionary score change that clears hysteresis and cooldown, or a mandatory link or harm rule that already named that turn. Unused residual budget stays unused.
   - For a turn already authorized to be summarized, attach `summaryText`, charged at the stub's own `tokenEstimate`.
   - Omit the rest; record `omittedTurnIds`. Introduced-harm and invalidation markers are not omitted to free that room (§6.3).

   **Why density and not raw weight:** sorting by weight alone lets a single high-weight, high-token payload (e.g. a 40k-token tool dump scored 0.9) consume the budget ahead of many smaller turns of nearly equal weight—including exactly the low-verbosity constraint turns §10.2 exists to protect. Density packing is the standard greedy approximation for a hard-capped budget; raw weight survives as the tie-break so that equal-cost turns still order by task relevance.
6. Emit `contextProjection` with `generation++`.
7. On a later pass, re-admit an omitted turn only through §6.1. A discretionary re-admit requires the weight rise to clear hysteresis and requires cooldown to allow it. A mandatory override does not wait on either. Demotion of some other turn, when the budget requires it, is a budget demotion under §6.1 even if that other turn's weight did not change.

### 6.1 Ordered transition and re-admit cooldown

One procedure produces the next `projectionState`. It separates **mandatory overrides** from **discretionary score changes**. This section is the cooldown contract previously cited as §10.1. There is no §10.1. References to a cooldown spec resolve here.

**Generation snapshot.** Generation G freezes a snapshot before judgments, admission, or packing. The frozen inputs are: endpoint seal sequences, the tombstone set for every turn id in the turn set, effective edge transitions, scorer weights, pins, the authoritative progress vector (§19.1), active warning ids (§20.4), the turn set, and the rendered payload versions this call would send. Every decision in G reads that snapshot. Appends during G (new transitions, spills, weight writes, reseals, superseding verdicts, tombstones) are durable immediately.

**Commit point.** G is abortable until transport handoff. The final read of tombstones, seals, evidence watermarks, and superseding verdicts, and the handoff of the assembled bytes, are one critical section under `sendFence`. A mutation of those inputs takes the same fence. It cannot commit after the final read and before handoff. Exactly one of handoff or mutating commit wins. If the mutation wins, do not hand off; abort G and retry on a new snapshot. If handoff wins, the mutation has not committed and is visible at the next generation. After handoff, the generation is published and an in-flight call is not rewritten. Each tool-loop model call is its own generation and its own fence. Packing MUST NOT mix edges, weights, or deletion visibility from after the fenced epoch with payloads from before it.

**Required traces.** Tombstone-before-send: both endpoints are live at freeze, one is tombstoned before the fence, the handoff is refused, and the linked content is not issued. Reseal-before-send: same refusal. Concurrent supersession: a verdict that wins the fence aborts the handoff; a verdict that loses the fence waits for the next generation. Interrupted generation: the process stops before handoff, nothing is published, and a cursor already appended (§18.4) remains. After-read-before-handoff: the test injects a tombstone after the final read is attempted and before handoff. The published call MUST NOT contain that tombstoned endpoint. Either the tombstone waits until after handoff, or the handoff is cancelled. A committed tombstone followed by a handoff of the pre-tombstone bytes is non-conforming.

Mandatory overrides MUST be applied when their trigger is true even if `weight` is unchanged, even if `|Δweight|` is below the hysteresis threshold, and even if the turn is inside re-admit cooldown. Discretionary score changes MUST NOT be applied unless hysteresis and cooldown both allow them.

**Hysteresis threshold.** A discretionary `projectionState` change requires `|Δweight| ≥ 0.05`, where `Δweight` is the current weight minus `weightAtLastStateTransition`. That field is the weight stored when `projectionState` last changed, including a mandatory change. It is not the previous generation's weight. The threshold is absolute, on the independent scalar in §4.2. Provisional, operator-adjustable, and MUST be fixed before Phase 4 can pass or fail (IMPL §8). The edge confidence band and its clock are §18.3, not this threshold.

**Order inside a generation.** Weights are refreshed first (§6 step 4). Then, in this order:

1. **Prefix.** Compute `B_turns` (§6 step 2). If `B_turns ≤ 0`, fail closed. No turn-state change substitutes for that failure.
2. **Pins.** Every turn with an active pin is `expanded` (§6.2). If those pins, with mandatory markers, exceed `B_turns`, fail closed.
3. **Link admission and invalidation** (§16.1), for edges that are still eligible on this snapshot (§18.2). A suspended edge does not admit. This step runs before discretionary packing. The final assembly, not only the admit bit, must satisfy §16.1. A target that is present only because of the edge is dropped with its source when the pair does not fit, except an `invalidates` pair, which fails closed under §6.2 rather than dropping a pin or a required marker. A target that is independently retained (pin, score, live result, or another edge in the closure) stays. If its required source does not fit, `invalidates` fails closed, and every other type attaches the dependency-gap marker instead of omitting the source in silence. An unpinned `invalidates` target already in the assembly is forced to the marked stub. A pinned target stays `expanded` and receives the invalidation marker. Depth, cycles, dedup, and cap charging are §16.1. Depth truncation uses that same final rendering. A required source past `Dep` is not a silent omission and is not an audit-only `depth-capped` record. `invalidates` fails closed. Every other type attaches the dependency-gap marker on the retained endpoint, including an endpoint that entered the closure only as a source. Sending that endpoint with the further source absent and with no marker is non-conforming.
4. **Introduced-harm** (§6.2, §20.4). An unpinned introduced-harm turn is forced to the marked stub. A pinned introduced-harm turn stays `expanded` and receives the harm marker.
5. **Discretionary score changes.** Apply a score-driven expand, summarize, or omit only when `|Δweight|` meets the threshold, cooldown allows the change, and the turn is not held by steps 2-4.
6. **Pack.** Spend residual budget by value density (§6 step 5) on turns that steps 2-4 have not already forced. Packing MAY demote an unpinned turn whose weight did not change when a new pin, a mandatory marker, a joint link endpoint, a live result, or discretionary summary growth consumes budget. That demotion is a **budget demotion**, it is allowed during cooldown, and the trace records `budget-demotion` plus `pressureSource` (§6.1). Pins are not the demotion candidates. Packing MUST NOT expand a turn solely because capacity became available. Expansion is a discretionary score change (step 5) or a mandatory admission already decided in steps 3-4. Residual budget that no authorized expansion uses stays unused.
7. **Emit** `contextProjection` and increment `generation`.

**Unchanged-weight demotion under new pins.** When a pin is added, or an active pin's rendered size grows, packing MUST demote unpinned content as far as required even if those weights are unchanged and even if those turns are inside cooldown. Pins are not the demotion candidates. If every unpinned turn has been omitted or stubbed and the assembly is still over `B`, fail closed.

**Invalidation during cooldown.** An `invalidates` admission, a reseal that voids a judgment (§18.2), a tombstone, an evidence change that voids a judgment (§18.2), or an introduced-harm verdict MUST still be applied while cooldown is open. Cooldown blocks only discretionary score-driven flips: omitting or summarizing a turn because its weight fell, or expanding it because its weight rose. It does not block steps 1-4 or a budget demotion.

**Re-admit cooldown.** When a turn is re-admitted to `expanded` by a discretionary score change, set `lastReAdmitGeneration` to the current `projectionGeneration`. Until `projectionGeneration ≥ lastReAdmitGeneration + C`, the projector MUST NOT omit or summarize that turn solely because its weight fell or failed hysteresis. Provisional **`C = 2`** generations. Operator-adjustable, and MUST be fixed before Phase 4 can pass or fail. Cooldown does not grow `B` and does not override steps 1-4 or a budget demotion. A budget demotion during cooldown MUST be recorded and MUST NOT reset `lastReAdmitGeneration`. A mandatory stub of an unpinned turn (invalidation or introduced-harm) ends the expanded re-admit early, MUST be recorded as a mandatory override, and is not a cooldown violation.

Edge admission uses the same constant `C` for discretionary confidence flips (§18.3). Mandatory edge invalidation does not wait on `C`.

The projection trace names two layers. Evaluators of §9.1 read these fields and no other source.

Turn-layer causes, one primary cause per turn whose projection state or tail membership changed: `score` (discretionary), `pin`, `invalidation`, `introduced-harm`, `budget-demotion`, `warning-retirement`, `link-admit`, `link-withdraw`, `link-degrade`, `link-reconfirm`. Link admission, withdrawal, degradation, and reconfirmation are mandatory at the turn layer even when the edge-layer decision was a discretionary confidence flip.

Edge-layer causes, one primary cause per admission-bit change: `edge-score` (discretionary confidence), `edge-invalidation`, `edge-suspend`, `edge-reconfirm`, `edge-degrade`, `edge-budget`. `edge-score` maps to turn cause `link-admit` or `link-withdraw`. `edge-degrade` and `edge-budget` map to `link-degrade`. `edge-suspend` and `edge-invalidation` map to `link-withdraw`. `edge-reconfirm` maps to `link-reconfirm`.

Each changed turn stores `turnCause` and `originCause`. `turnCause` is the immediate turn-layer cause above. `originCause` is `edge-score` when that turn-layer cause came from a discretionary confidence flip. It is the mandatory edge cause when the turn-layer cause came from `edge-invalidation`, `edge-suspend`, `edge-reconfirm`, `edge-degrade`, or `edge-budget`. When the change did not come from an edge, `originCause` equals `turnCause`.

The state-flip numerator (metric 2) counts only a `projectionState` change whose `turnCause` is `score`. Its denominator stays the previous active set. A rendered rewrite that leaves `projectionState` and tail membership unchanged does not enter that numerator. The token-replacement numerator (metric 3) counts absent previous-tail tokens whose effective `originCause` is `score`, `edge-score`, or `summary-rewrite`, including tokens removed from other turns because a discretionary summary grew. Mandatory safety withdrawals, pin changes, marker removal, and phase-boundary flushes stay outside that numerator and are reported in `mandatory-token-count`. A `budget-demotion` whose every `pressureSource` is mandatory stays outside the numerator. A `budget-demotion` whose only `pressureSource` is discretionary does not. When the same packing step has both, metric 3 counts only the discretionary share defined below, floored once on that step's total `R`. The edge-flip numerator counts only `edge-score`. A trace that keeps `turnCause` and drops `originCause` is non-conforming. IMPL §8 Phase 1 records state causes and rendered-change events.

**Rendered-change events.** A state or membership cause is not the only trace event. Whenever a rendered segment in the variable tail differs from the previous published snapshot, including when `projectionState` and tail membership stay the same, the trace MUST record one `rendered-change` event for that turn. Discretionary rewriting of a retained summary without that event is prohibited. The event binds `previousRenderId` and `currentRenderId` (the renderer and tokenizer versions of the sent segment) and lists the removed tokens. Each removed span stores `{spanId, tokenCount, originCause}`. Evaluators MUST use those spans. They MUST NOT reuse an earlier state-transition cause to explain the new text. A missing event for a changed render is non-conforming, and those tokens MUST NOT be treated as mandatory or as outside the metric.

**Mixed spans in one retained turn.** One primary `turnCause` MUST NOT cover every removed token. Spans are partitioned. A discretionary summary rewrite is `originCause` `summary-rewrite` and counts in the metric 3 numerator. A mandatory marker that leaves the same segment is a separate span with the mandatory origin (`warning-retirement` or the marker's own cause) and counts only in `mandatory-token-count`. If any removed span is discretionary, the generation is not `mandatory-only`.

**Pressure inheritance.** One packing step is one demotion batch and one accounting group. Every `budget-demotion` in that step stores the same `pressureSource` list. Each entry is `{sourceId, originCause, tokenDelta}` for one growth or new admission that consumed budget in that packing step. One entry is the single-source case. Displaced tokens on other turns keep `turnCause` `budget-demotion`. Discretionary sources are `summary-rewrite`, `score`, and `edge-score`. Mandatory sources are pin growth, a live tool result, a mandatory marker, and an invalidation that must fit. Let `R` be the sum of previous-tail tokens removed by every budget demotion in that packing step. `R` is not a per-turn total and is not recomputed per demoted turn. Let `M` be the sum of `tokenDelta` on mandatory entries. Let `D` be the sum of `tokenDelta` on discretionary entries. The floor formula applies only when both `M` and `D` are greater than 0. The mandatory share is `floor(R * M / (M + D))`, taken once for the accounting group, and goes only to `mandatory-token-count`. The discretionary share is `R` minus that floor and goes to the metric 3 numerator. Span conservation: the mandatory share plus the discretionary share equals `R` exactly. Per-turn spans may record how those two shares are laid out, and the spans must sum to the two shares. Flooring each demoted turn's own removed-token count and summing those floors is non-conforming, including when the per-turn floors still add up to `R`. Any remainder token from the single floor therefore counts in metric 3. When `D` is 0 and `M` is greater than 0, the mandatory share is all of `R`. When `M` is 0 and `D` is greater than 0, the discretionary share is all of `R`. If `M + D` is 0, the demotion names no pressure and is non-conforming. Assigning all of `R` to the pin, or all of `R` to the summary, is non-conforming when both `M` and `D` are positive. Metric 2 still ignores the demotion: only a `projectionState` change whose `turnCause` is `score` enters that numerator. Pins stay expanded. Harm and invalidation stay markers.

### 6.2 Pins, invalidation, and introduced-harm

Precedence, highest first. A lower rule MUST NOT override a higher one. §16.1 and §20.4 restate this rule; they do not define a second one.

1. **Budget fail-closed.** If the mandatory set exceeds `B`, do not drop a member of that set to make the invariant look true. Surface an error, force memory promotion, or ask the operator (§6 step 2 and step 3).
2. **Active pins stay expanded.** An operator, system, or acceptance pin stays `expanded` until unpinned. An `invalidates` edge that names the turn does not stub it. An introduced-harm verdict on the turn does not stub it, omit it, or suspend the pin. Principle 5 is this rule. Pre-admission (§6.3) does not stub, truncate, or omit the pin when that expanded payload already contains a live tool result. Those bytes stay in the pin and are counted once.
3. **Markers are mandatory on those pins.** A pinned `invalidates` target MUST carry the invalidation marker beside the expanded payload: the result is obsolete, and which edge says so. A pinned introduced-harm turn MUST carry the harm marker beside the expanded payload: the approach, that HV judged it introduced a regression, the checkable referent (§20.1), and an explicit statement that the payload is not the recommended next action. The marker is charged against `B`. If the pin plus its marker does not fit, rule 1 applies.
4. **Unpinned mandatory stubs.** An unpinned `invalidates` target that is already in the assembly, and an unpinned introduced-harm turn, MUST be `summarized` with the same marker. They MUST NOT stay `expanded` and MUST NOT be silently `omitted` (omission would leave the failed approach available to retry with no marker).
5. **Discretionary scores sit underneath.** Weight changes, hysteresis, and cooldown (§6.1) do not move a turn that rules 1-4 have fixed.

`introduced-harm` and `invalidated` are annotations, not values of `projectionState`. A revealed regression (§19.2) is not introduced-harm and does not force rule 3 or rule 4.

**Warning retirement.** Rules 3 and 4 and the mandatory set in §6.3 apply to markers whose `warningState` is `active` (§20.4). `repaired` and plan retirement do not need a replacement warning. Consolidation and standing-memory transfer retire a marker only when this sent assembly contains an adequate replacement. Adequate means the sent text, not merely an id, states the prohibited approach or obsolete result, whether the meaning is harm or invalidation, a checkable referent, and that the content is not the next action. An id-only replacement is non-conforming and does not retire the individual marker. If that replacement leaves the prefix or loses any of the four fields, the individual marker is active again before send. The verdict row stays. Retirement does not unpin, and it does not relabel a true introduced-harm verdict as false. Active markers, including a reactivated marker, stay spill-protected. A history of resolved regressions that would not fit in `B` as raw markers MUST still be able to send after true retirements, while any marker that is still active remains in the mandatory set. Pins stay expanded.

### 6.3 Tool-loop budget

The budget invariant below applies at **every model invocation** a deployment issues, not only when `contextProjection` is first assembled. That includes every call in a tool loop: the initial prompt and every later call that carries a new tool result, a continuation, or a reprojected tail.

Live tool results and in-progress dialog are charged at their own `tokenEstimate` for the active renderer (IMPL §5.1). They are not free because the turn is unfinished.

**Pre-admission of live tool results.** This step runs after warning reactivation and before spill. It decides whether a live tool result may join the mandatory set. It does not spill, it does not truncate a pin, and it does not drop an active introduced-harm, invalidation, or dependency-gap marker. It does not re-enter link admission or discretionary packing. The decision is part of the rendered payload version this generation sends.

The rule applies only to live tool results. The user turn this call exists to deliver stays in the mandatory set. This rule does not slice it, omit it, or replace it. Which in-progress dialog items count as those tool results, and how the renderer produces `tokenEstimate` before the seal, remain IMPL §10 question 7.

A call with no live tool result skips this step. Let `M_fixed` be the active renderer's token sum of the distinct mandatory segments, each counted once: the system prefix; standing memories; each active pin in expanded form, including the marker beside that pin; every active introduced-harm, invalidation, or dependency-gap marker that is not already inside one of those segments; and the user turn this call exists to deliver, when that user turn is not itself a live tool result under test. Shrinkable residual facts on an unpinned marked stub are not part of `M_fixed`. The pre-admission ceiling is `C_pre = B - M_fixed`. This ceiling is the residual mandatory budget after those segments. It is not a fraction of `B`. Pins stay expanded in `M_fixed`. Harm and invalidation stay markers.

**Already inside `M_fixed`.** Before the ceiling test, classify each live tool result against the sealed rendering of `M_fixed`. Retention is by identity: the same `turnId` and tool-call index rendered as payload inside an `M_fixed` segment. An id-only citation is not retention. A fuzzy match is not retention. The usual segment is the expanded pin of the in-progress turn (§6.2 rule 2). That pin stays expanded. Pre-admission does not stub, truncate, or omit it to remove the overlap.

Let `E_proven` be the measured token count of this result's rendered bytes inside that sealed rendering. A count exists only when the renderer measures it. Seeing the result's identity inside the segment is not a count. Tokens in a measured `E_proven` are counted once, inside `M_fixed`. They are not charged again as a separate live-tool payload, and an omission marker does not cover those measured bytes. `C_pre` already excludes them, so the ceiling test does not subtract them again.

Full retention requires proof that the entire result is already in that rendering: `E_proven` equals `E`, and every rendered byte of the result is inside the segment. Then `E_abs` is 0. Skip the ceiling test. Emit no omission marker. Do not append a second copy. The pin stays expanded.

A measured subset is an integer `E_proven` with `0 ≤ E_proven < E`. Then `E_abs` is `E - E_proven`. The retained span stays. The ceiling test applies only to the absent span. Its charged size is `max(E_abs, 1)`. Any omission marker for that span uses `estimate=<E_abs>` and `scope=absent-remainder`. When the renderer proves the result is absent, `E_proven` is 0 and `E_abs` is `E`. The ordinary ceiling test below applies to the whole payload.

An unmeasurable split is not full retention. If the result's identity occurs inside an expanded pin or another `M_fixed` segment and the renderer cannot measure `E_proven`, no retained length is proven. Do not set `E_abs` to 0. Do not skip the omission marker. The unproven count is `E` when `E` is an integer, because an unmeasured length is not subtracted. Do not admit those unproven bytes as a second payload. Take only the marker branch below, with `estimate=<E>` and `scope=unproven-remainder`. When that marker's own `tokenEstimate` fits in the remaining ceiling, admit the marker. When it does not fit, fail closed under step 3. The pin stays expanded. The call does not go out with those unproven bytes unmarked.

If `C_pre < 0`, `M_fixed` already exceeds `B`. Admit no additional live tool payload and admit no omission marker. Fail closed under step 3 below. Spill cannot reduce `M_fixed`, so spill is not run to change this outcome. Each live tool result is still appended to SessionLog in full. This refusal is the fixed mandatory set exceeding `B`. It does not attach an omission marker to bytes already inside an expanded pin.

Otherwise consider every live tool result that is not proven fully retained, in ascending `turnId`, breaking ties by ascending tool-call index. Proven full retention (`E_proven` = `E`) is not in this loop. An unmeasurable split is in this loop. The remaining ceiling starts at `C_pre`. For a result with `E_proven` = 0, let `E` be its payload `tokenEstimate` when the renderer has produced an integer, and let the charged size be `max(E, 1)`. The ordinary marker records that raw `E`. A missing estimate on a proven-absent result has no charged size. It does not admit the payload at cost 0, and the marker's `estimate` field is `-1`. For a measured partial result, the charged size is `max(E_abs, 1)` and the marker records `E_abs`.

An unmeasurable split does not take the payload-admission branch. Its unproven count is `E`. Render the omission marker with `scope=unproven-remainder` and let `K` be that marker's own `tokenEstimate`. When `K` is less than or equal to the remaining ceiling, admit the marker and subtract `K`. When `K` exceeds the remaining ceiling, admit neither a second payload nor the marker and fail closed under step 3. Do not invoke the model with the unproven bytes unmarked.

For every other result in this loop, admit the tested span only when a charged size exists and that charged size is less than or equal to the remaining ceiling. That span then joins the mandatory set once, and the charged size is subtracted from the remaining ceiling. In every other case, do not admit the tested span. Render the omission marker from the remaining ceiling before the marker is charged, and let `K` be that marker's own `tokenEstimate`. When `K` is less than or equal to the remaining ceiling, admit the marker and subtract `K`. The tested span stays out of the mandatory set. When `K` exceeds the remaining ceiling, admit neither the tested span nor the marker and fail closed under step 3. Do not invoke the model with that absent span unmarked, even when `M_fixed` alone is within `B`. Results and markers already admitted stay. Do not drop a pin or an active warning marker to make the marker fit. Do not emit a marker for a result whose full retention was measured.

The omission marker is one line. It is not a summary, a head, or a tail of the payload:

`[wcp:live-tool-omitted turnId=<turnId> toolCallId=<toolCallId> reason=exceeds-pre-admission-ceiling estimate=<E> ceiling=<remaining> retained=sessionlog]`

`turnId` and `toolCallId` are the canonical identifiers. A field that contains whitespace or `]` is written as `-`. A missing `toolCallId` is `-`. `estimate` is the integer `E`, or `-1` when no estimate exists. `ceiling` is the remaining ceiling before this marker is charged. `reason` is the literal `exceeds-pre-admission-ceiling`. `retained` is the literal `sessionlog`. The marker text is not truncated. That line is only for a result with measured `E_proven` = 0. When the marker covers a measured absent remainder and `E_proven` is positive, use the same fields, set `estimate` to `E_abs`, and add `scope=absent-remainder` immediately before the closing bracket. When the retained length is not measured, use the same fields, set `estimate` to the unproven count `E`, and add `scope=unproven-remainder` immediately before the closing bracket. A marker without `scope` claims the whole payload is proven absent. Emitting that claim while any measured byte of the payload remains in the sealed assembly is non-conforming. Emitting no marker for an unmeasurable split is non-conforming.

The full payload bytes are appended to SessionLog before the test. Refusal is a projection decision. It is not deletion. The unsent bytes are not part of this call's token sum and are not a `pressureSource` `tokenDelta`. The admitted marker, when it consumes budget, is the mandatory live-tool-result source already named in §6.1. `floor(R * M / (M + D))` is unchanged.

The marker is not an empty tool success. The same generation does not re-issue the tool call to replace the marker with the same payload. A later generation may send the stored bytes only by passing this same test. Head/tail slices, cross-generation chunking, and operator-gated truncation of the payload are outside this rule.

When the assembly after pre-admission cannot fit in `B`:

1. **Spill unmarked content first.** Omit or stub unpinned turns that are not active introduced-harm warnings and not active invalidation targets, lowest density first. A spill is a budget demotion (§6.1). It is allowed during cooldown. Record it. This step MUST NOT omit an active introduced-harm marker, an active invalidation marker, or an active dependency-gap marker (§16.1). Retired markers are not in this protection. Spill does not pull a refused live tool payload back into the mandatory set, and it does not truncate that payload.
2. **Shrink marked stubs to the marker.** An unpinned active introduced-harm or invalidation stub may lose residual payload facts. It MUST keep the marker: the approach or the obsolete result, the verdict or the edge, the checkable referent, and that the payload is not the next action. The active marker stays while the call is issued.
3. **Fail closed.** If the mandatory set still cannot fit, do not invoke the model. The same refusal applies when a live tool result has a positive measured `E_abs`, or an unmeasurable split, and pre-admission admitted neither that unproven span nor an omission marker for it, even if the other mandatory segments fit in `B`. Skipping the marker is required only when full retention was measured (`E_proven` = `E`). That measured result is already in the sealed assembly inside `M_fixed`. An unmeasurable split is not that case. The mandatory set is the system prefix, standing memories, active pins with their markers, each absent live-tool span that passed pre-admission or that span's omission marker, the user turn this call exists to deliver, and every active introduced-harm, invalidation, or dependency-gap marker §6.2 and §20.4 require in this assembly. A refused absent span is not a member of this set. Bytes already counted inside an expanded pin are not a second member. A warning retired only by a replacement is active for this call when that replacement is absent or inadequate in this assembly. Reactivation happens before pre-admission, before spill, and before this check. Surface an error or ask the operator. Do not drop pins, do not truncate pinned content, do not omit those active markers, and do not send an over-budget prompt. Do not fail closed in order to keep a retired marker. Do not send the prompt by leaving an unproven live-tool span unmarked. A span whose retained length was measured inside an expanded pin is not unproven. An unidentified subset with no measured retained length is unproven.
4. **Ownership.** The component that issues the call is the component that enforces this (risk 4). A deployment that claims the invariant MUST be able to measure each outgoing prompt and refuse the call. A CLI-owned inner loop whose intermediate model calls the orchestrator cannot measure is not a conforming claim of this invariant. The Phase 2 declaration (IMPL §8.1) records that gap as a fail for the budget gate, not as a silent pass.

**Budget invariant:** `tokens(system prefix) + tokens(standing memories) + tokens(expanded) + tokens(stubs) + tokens(mandatory markers) + tokens(admitted live tool payloads and omission markers on this call) ≤ B`, at every issued model invocation. Refused payload bytes are outside that sum. Only a measured retained length is excluded from a second charge in the live-tool term. An unmeasurable split does not move the unproven bytes into that exclusion. An omission marker is counted in the live-tool term and is not also counted in `tokens(mandatory markers)`. The §9.1 budget-adherence metric and the IMPL §8 Phase 1 adherence report both measure this full sum, not the turn portion alone.

Worked pre-admission cases. Marker charges below are illustrations for these numbers, not fixed constants. A real call uses the rendered marker's own `tokenEstimate`. In the ordinary cases the renderer has measured `E_proven` = 0. `B = 100` and `M_fixed = 40` gives `C_pre = 60`. A live tool payload with `E = 80` has charged size 80, which is over ceiling. Illustrative `K = 25` satisfies `25 ≤ 60`, so the call sends the ordinary omission marker. The 80 payload tokens stay in SessionLog and are not sent. Pins stay expanded. `B = 100` and `M_fixed = 90` gives `C_pre = 10`. A payload with `E = 50` is over ceiling. `25 > 10`, so the call is refused even though `M_fixed` alone fits. The result is not sent unmarked.

Overlap acceptance case. `B = 1000`. An expanded pin is 800 tokens and already renders this live tool result, `E = 600`. Other `M_fixed` segments are 100 tokens. `M_fixed` = 900, with the 600 counted inside the 800 and not added again. `C_pre` = 100. Illustrative `K = 60`. The renderer has measured `E_proven` = 600, so `E_abs` = 0. The call sends no `[wcp:live-tool-omitted …]` line and does not charge `K`. The sealed mandatory total stays 900. The pin stays expanded. The 600 tokens appear once. The non-conforming reading admits the marker because `600 > 100` and `60 ≤ 100`, and the assembly is then about 960 tokens while still containing the payload the marker calls omitted.

Unmeasurable-split acceptance case. Same budget shape, without a measured retained length. `B` = 1000. `M_fixed` = 900, including an expanded pin that contains some unidentified subset of this live tool result. `E` = 600. The renderer does not measure how many of those 600 tokens are inside the pin. `C_pre` = 100. Illustrative `K` = 60. The unproven count stays 600. That count is over ceiling, so the payload is not admitted again. `60 ≤ 100`, so the call sends `[wcp:live-tool-omitted … estimate=600 … scope=unproven-remainder]`. The sealed total is 960. The pin stays expanded. The non-conforming reading treats identity presence as full retention, sends no marker, and leaves the unproven bytes unmarked at a total of 900. If the rendered marker's own `tokenEstimate` exceeds the remaining ceiling, the call is refused instead. It is still not treated as full retention.

**Recoverability invariant:** For every omitted turn, SessionLog still has the bytes (or blob). Projection never claims deletion.

This is **an existing property of the durable store rather than an aspiration of this design**, but the enforcement is narrower than earlier revisions of this paper claimed, and the boundary has to be stated to be useful. On the **tracked save path**, deletes of durable records are converted to tombstones rather than executed, and an attempt to physically delete one throws rather than proceeding. Writes and field-level updates on that path are mirrored into an append-only audit ledger carrying before-and-after snapshots, which is what makes original writes and additive changes reconstitutable.

What that does **not** amount to is a database-level prohibition. The guard inspects tracked change entries, so set-based deletes and raw `DELETE` statements never reach it; today's recoverability rests on the service layer not issuing them, protected by a test asserting that the session-log service source contains no bulk-delete call, rather than on the database refusing them. A second limit: the ledger covers the tracked path, not the bulk tombstone and revival operations, which update rows directly — so deletion *events* go unrecorded even though those operations only flip deletion metadata and never touch stored content.

So the invariant the projection may safely inherit is: **content survives deletion on every path the current services use, enforced by convention and a guard test above the database, not by the schema.** That is enough for this design, which needs omitted turns to remain readable and never claims a complete deletion history. It is not enough to describe recoverability as structurally guaranteed, and a projection built on a future code path that bypasses the tracked save would not inherit it at all. IMPL §3.2.1 records both mechanisms.

Two consequences the design must respect:

- **Re-admit of an omitted turn is safe by construction** (step 7 above), because omitted turns are never deleted. Re-admit of a *tombstoned* turn is a different matter: recovery reads must bypass the default visibility filters, and no restore operation is exposed on the session-log tool surface today. Any design that depends on reviving deleted turns is depending on unbuilt work.
- **The enforcement is not visible in the data model's type definitions,** which makes it easy to audit incorrectly and conclude the ledger is mutable. An earlier review of this paper did exactly that, and a later one then overstated the correction in the opposite direction. Both errors came from reading one part of the write path and generalizing.

The specific classes, methods, guard behavior, and ledger contract that provide these guarantees are identified in the companion implementation note. This paper states the property; that note states the code.

**Budget adherence:** Local token estimates may drive packing. They are engineering controls, not published savings metrics.

## 7. Related work

Map each cited line of work to **shared ideas** vs **what it misses** relative to task-progress relative weights + re-admit from a full log.

### 7.1 Research

**MemGPT** ([arXiv:2310.08560](https://arxiv.org/abs/2310.08560))  
Shares: tiered memory; explicit main context vs external context; paging.  
The §8 columns have fixed meanings. **Durable full turns** asks whether original message bytes remain in a durable store after they leave the prompt. It does not ask whether those bytes are still resident in the prompt. **Hard budget projection** asks whether the bytes sent to the model are held to a hard token ceiling. It does not ask whether the system then refuses the call or pages and continues.  
Main context holds system instructions, working context (core memory), and a FIFO queue. External context has two persistent stores: recall storage keeps the conversation history, including messages evicted from that queue, and archival storage is a database the agent reads and writes (Packer et al., arXiv:2310.08560). Overflow evicts queue messages into recall storage and replaces them in the prompt with a recursive summary so generation can continue. That eviction is how the ceiling is met. It is not the durability score and it is not the budget score.  
Durable full turns is **Yes**. Recall storage retains the evicted conversation messages, and archival storage retains inserted documents. The round-7 **Partial** label is withdrawn. It scored prompt residency (the FIFO plus a recursive summary) on a column that asks about the durable store.  
Hard budget projection is **Yes**. The context window is a hard token ceiling. The round-7 **Soft** label is withdrawn. It scored the paging-and-continue policy on a column that asks whether the ceiling is hard. WCP's Yes is a fail-closed ceiling. MemGPT's Yes is a hard window met by eviction into recall storage. Both ceilings are hard. The enforcement methods differ, and that difference is stated here rather than by a Soft cell.  
Misses: weights are not framed as relative task-progress toward completion; the in-prompt recursive summary is lossy as a prompt view, which is not a durability finding; and the paper does not tie re-admit to an append-only session ledger for operator agent work.

**Selective Context** ([arXiv:2310.06201](https://arxiv.org/abs/2310.06201))  
Shares: prune low-value tokens to fit budgets.  
Misses: self-information / efficiency pruning ≠ task-progress weights; no durable SessionLog re-admit loop for agent tooling traces.

**Recursively Summarizing** ([arXiv:2308.15022](https://arxiv.org/abs/2308.15022))  
Shares: rolling summary as memory under length pressure.  
Misses: summaries are one-way compressible history; weak story for re-expanding original turns when weights change.

**A-MEM** ([arXiv:2502.12110](https://arxiv.org/abs/2502.12110))  
Shares: agentic memory as linked notes; evolution of memory structure.  
Misses: note graphs are not the same as weighted projection over a full append-only turn log with hard live-context budgets.

**PACE — Predictive Adaptive Context Extraction** ([ACL 2026](https://aclanthology.org/2026.acl-long.1252/))  
Shares: next-step utility; multi-granularity context; adaptive pressure for long-horizon agents—treated here as the closest research cousin on *predictive relevance for the next action* **(author judgment, not a citation rank claim)**.

**HiGMem** ([arXiv:2604.18349](https://arxiv.org/abs/2604.18349)) — *accepted to Findings of ACL 2026; camera-ready, code public*  
Shares: event summaries with expand-to-underlying-turns; hierarchical recoverability. Strongest empirical result among the memory-system citations here: best F1 on four of five LoCoMo10 question categories, and adversarial F1 from 0.54 to 0.78 over A-MEM while retrieving an order of magnitude fewer turns.

**G-Long** ([arXiv:2606.13115](https://arxiv.org/abs/2606.13115))  
Shares: graph structure + attention-aware importance scoring for long-term dialogue memory.  
Misses: importance from summarizer attention ≠ relative weight for unfinished engineering work; no SessionLog/CLI assembly story.

**Adaptive context compression** ([arXiv:2603.29193](https://arxiv.org/abs/2603.29193))  
**Provenance caveat:** two-author v1 preprint, no accepted venue, no comments/page-count field, and cross-listed under cs.CV rather than cs.CL. Weight it accordingly against the peer-reviewed entries above; it is retained for idea coverage (banded compression under a dynamic budget), not as evidence.  
Shares: turn importance scores; retain / summarize / drop bands; dynamic budget.

## 9. Evaluation plan

Measure what matters. Do **not** lead with whitespace estimator deltas.

### 9.1 Primary success metrics

1. **Post-reproject (or post-compact fallback) task continuation** without operator re-paste of constraints, paths, or acceptance criteria.
2. **State-flip rate.** Denominator: turns that were `expanded` or `summarized` on the previous published snapshot (the previous active set), not every turn loaded for the session. If the denominator is 0, do not compute a rate. Record `empty-denominator`. The gate passes for this metric. Numerator: turns in that set whose `projectionState` changed for discretionary turn cause `score` (§6.1). Every other turn-layer cause is mandatory, including `pin`, `invalidation`, `introduced-harm`, `budget-demotion`, `warning-retirement`, `link-admit`, `link-withdraw`, `link-degrade`, and `link-reconfirm`. Those are counted in `mandatory-transition-count` and are outside the numerator. An edge-layer `edge-score` decision is still mandatory at the turn layer once it is recorded as `link-admit` or `link-withdraw`. A generation whose causes are only mandatory is `mandatory-only` and is outside the mean. Stable omissions are outside the denominator. Window: one published generation. Session figure: the mean of counted per-generation rates. A generation is a phase-boundary flush only when its snapshot records `phaseBoundary: true` and a `phaseId`. Evaluators MUST exclude that generation and MUST NOT exclude any other generation by judgment. Provisional bar: **≤ 0.10** when the denominator is at least 1. Operator-adjustable, and the number MUST be fixed before Phase 4 can pass or fail (IMPL §8). Two evaluators of one trace use these fields and no others.
3. **Active-context token replacement.** Separate from the flip rate. A pass can replace the entire variable tail while flipping few states, or flip many tiny turns while leaving the tokens in place. Window: one published generation. Denominator: tokens in the previous generation's variable tail (expanded payloads, stubs, and link-admitted segments). If that token count is 0, do not compute a rate. Record `empty-tail`. The gate passes for this metric. The stable prefix and standing memories are outside both sides, so a large cached prefix cannot dilute the ratio. Numerator: tokens of that previous tail that are absent from the new tail and whose rendered-change span `originCause` is `score`, `edge-score`, or `summary-rewrite` (§6.1). This includes tokens inside a turn that stays in the tail with the same `projectionState`. The denominator is unchanged: previous variable-tail tokens. Tokens whose `originCause` is a mandatory safety withdrawal, a pin change, or another non-discretionary cause stay outside the numerator and are reported in `mandatory-token-count`. When one packing step's `pressureSource` list has both mandatory and discretionary entries, the numerator is only the discretionary share from §6.1, computed once for that packing step as `R - floor(R * M / (M + D))`, where `R` is the sum of previous-tail tokens removed in that step. The mandatory share is `mandatory-token-count` only. Those two shares sum to `R`. Flooring each demoted turn and summing those floors is non-conforming. Assigning every displaced token to one of the two sources is non-conforming. A generation is `mandatory-only` for this metric only when no absent previous-tail token has `originCause` `score`, `edge-score`, or `summary-rewrite`. Treating the generation as `mandatory-only` because `turnCause` is `link-withdraw` while `originCause` is `edge-score` is non-conforming. Exclude a generation from the mean and from the maximum when it is `mandatory-only` or when `phaseBoundary` is true with a `phaseId`. A mandatory pin or marker insertion that is the only cause does not fail the bar. Session figures: the per-generation mean and the per-generation maximum of the counted generations. Provisional bar: **≤ 0.25** on each counted generation. Operator-adjustable, and the number MUST be fixed before Phase 4 can pass or fail. Both bars are required. Passing the flip rate does not pass this metric. Edge-flip counting is §22 and uses the same empty-denominator, mandatory-cause, and phase-boundary rules. The projector sets `phaseBoundary` true if and only if the plan phase id on this snapshot differs from the plan phase id on the previous published snapshot, and the trace stores both ids. Evaluators exclude that generation if and only if the flag is true. If every generation in the session is excluded, do not compute a session mean. Record `empty-aggregate`. The stability gate passes for that metric. A missing mean is not a fail and is not a silent skip. The same `empty-aggregate` rule applies to metric 2 and to the edge-flip rate. Mixed-cause expected results are stated in §22 and are normative for these metrics.
4. **Projection token budget adherence:** fraction of issued model invocations, including tool-loop continuations (§6.3), whose measured assembly is ≤ `budgetTokens` (local estimator OK for this engineering metric only). An invocation that was refused by fail-closed is recorded as a refusal, not as adherence. An invocation that sent a §6.3 omission marker instead of an oversized live tool payload is adherence when the sent assembly is ≤ `budgetTokens`. It is not a fail-closed refusal. Refused payload bytes are outside the measured assembly.
5. **Re-admit usefulness:** when a turn is re-admitted, did the subsequent action correctly use it (human or rubric check)? Report score-admitted and link-admitted slices separately (§22).
6. **Pin integrity:** zero silent pin drops, including under invalidation, introduced-harm, budget pressure, and tool-loop spill (§6.2, §6.3).

### 9.2 Explicit non-metrics (for now)

- Estimator-only “token savings %” as a published claim.
- Provider bill deltas inferred from whitespace benches.
- Vanity context-window fill charts without task outcomes.

### 9.3 Protocol sketch

- Record real operator sessions into SessionLog (offline corpus).
- Phase 1 simulator: replay scorer + projector; operators score blind continuations (full context vs projection vs host-compact summary).
- Phase 2 online spike: one CLI oneshot path; log continuation failures and re-paste events.

## 10. Risks and open questions

1. **Thrashing:** scores oscillate; projection churns; prompt cache dies. Mitigation: discretionary hysteresis and re-admit cooldown (§6.1, enforced against `lastReAdmitGeneration`), which do not block mandatory overrides. Stability is the pair of metrics in §9.1 (state-flip rate and active-context token replacement), not the flip rate alone.
2. **Bad scorer drops quiet constraints:** low-verbosity “never X” turns get omitted. Mitigation: constraint detector → pin or MemoryBridge; fail tests in eval protocol.
3. **CLI Terms of Service / fair use:** sessionless high-frequency oneshots may trip rate or ToS limits. Mitigation: backoff, batching, respect vendor rules; do not pretend subscriptions are uncapped APIs.
4. **Tool-loop ownership:** split between orchestrator and CLI causes missing traces in SessionLog, and a CLI-owned inner loop can issue model calls the orchestrator cannot budget. Mitigation: one declared owner per spike; log everything observable; claim the §6.3 invariant only for calls the owner can measure and refuse.
5. **Host UI compact still happens:** operators may think context is gone when only the IDE view compacted. Mitigation: UX clarity that SessionLog + projection are authoritative under the outer-orchestrator deployment (IMPL §6, Option C).
6. **Re-score cost every turn:** LLM judge v2 can be expensive. Mitigation: v1 rules by default; judge on schedule or on budget pressure.
7. **Evaluation honesty:** easy to overfit summaries that *look* complete. Mitigation: adversarial hidden constraints in replay tests.
8. **Prompt-blob vs messages[] fidelity:** some tool schemas and multimodal parts may not round-trip cleanly through CLI stdin prompts.

Linking design, goal metrics, outcome records, storage constraints, evaluation hooks, open questions, and linking non-claims continue in §13 through §24.

## 14. Why this exists: weight-triggered re-admit does not guarantee recovery of joint value

WP Principle 4 makes re-admit first-class: "if a quiet constraint suddenly matters, the scorer must be allowed to pull the full turn back from SessionLog." WP §6 step 7 gives it exactly one trigger — an omitted turn's `weight` rising enough on a later reweight pass.

That trigger is not blocked by the turn's absence from the assembled projection. WP §6 step 1 loads every SessionLog turn for the session before weights are refreshed, and WP §5.2's v2 judge is given the goal, the recent projection, and candidate-turn stubs. An omitted turn is absent from the model-facing assembly and present, as a stub, in the reweighting input. The scorer can compare that stub with the current failure and raise the turn's weight. An earlier draft of this section claimed re-admit cannot fire because omission hides the turn from the scorer. That claim contradicts the design this paper extends, and it is retracted.

What remains is a representation limit, not an invisibility limit.

The scorer sees `summaryText`, not the sealed payload (WP §4.2, WP §6 step 5). A stub that dropped the quiet fact (an operator constraint, the exact error text, an environment condition (WP §5.1)) cannot suggest the relevance of that fact, and the v2 judge has no other view of an omitted turn. Locally obvious relevance that survives in the stub (a repeated identifier, the same file) can still raise weight. Four different holes are easy to collapse into one, and they are not the same hole (§15):

- **Missing input.** A fact that is absent from the stub is not available to infer. The judge cannot use a payload it was not given.
- **Contextual inference.** WP §5.2 gives the v2 judge the goal, the recent projection, and several candidate stubs on one call. Independent numeric outputs do not forbid that judge from noticing a relation among those inputs.
- **Persistent relation storage.** A scalar written back to one turn does not keep that noticed relation for a later call. The link index is the stored relation.
- **Dependency-aware packing.** A stored relation still does not put both endpoints in the assembly. That is joint admission (§16.1).

Re-admit can fire when the stub still carries the signal. It can also fire when the v2 judge sees several stubs and raises a weight because it noticed a relation (§15). What re-admit does not guarantee is recovery of joint value: a scalar does not persist the relation, and a higher weight does not pack the other turn. A stub that dropped the fact is a missing input, so that path has nothing to infer from. WP §10 risk 2 ("bad scorer drops quiet constraints") names the symptom; its stated mitigation is a constraint detector at write time, which helps only for constraints recognizable as constraints when written, and only if that detector's output is retained in the stub (§20.3).

The link index below is the proposal for the part a scalar does not guarantee. It does not replace the scorer's existing path from stub to weight. The per-turn scalar does not by itself persist a pair or co-admit both turns (§15). The quiet-constraint case, a fact recorded in passing with no shared criterion id, is still a candidate. Exact referent match is not enough when the failure does not quote the constraint. §18.4 requires both a referent match, when a checkable string is shared, and a `constraint-fact` scan that proposes marked constraint turns even when the failure never quotes them. A walk of the requirement graph alone does not recover that case.

For provenance: the reinforcement idea this whole design rests on is stated in BDPv4's monitoring list, where a steering message that re-surfaces workspace instructions after compaction "reinforces the weight applied to those requirements, which over time help the compaction algorithm to retain such instructions" (`docs/Development-Process-draft-v4.md`, Implementation). Weighted projection is a mechanization of that observation, and §19 is the part that supplies the progress measurement the observation assumes.

## 15. What a stored scalar does not guarantee

The deeper issue is what `weight` can represent.

Consider a session where turn 4 records an environment constraint in passing and turn 60 hits a failure the constraint explains. Scored individually against current work, turn 4 is unremarkable — it mentions no current identifier, it is old, it reads as background. Turn 60 is obviously relevant. The information that resolves the situation is not in either turn; it is in the *pair*.

WP §4.2 stores one scalar `weight` per turn. WP §5.2's v2 judge is not an isolated reading of one turn: its prompt contains the goal, the recent projection, and multiple candidate stubs. The number it writes is still one scalar per turn, and those scalars are not a normalized distribution (WP §4.2). Independent outputs mean one turn's score is not forced to fall because another turn's score rose. They do not mean the judge is unable to notice that two stubs in that same prompt bear on each other.

What the scalar does not do is the rest of the job:

- It does not fill in a fact the stub dropped. That is a missing input, not a property of the output type.
- It does not persist the noticed pair. The next call does not inherit an unnamed relation from the previous scalar.
- It does not pack both turns together. Co-presence is §16.1, not a side effect of either score.

The link index is the persistent relation. The context-conditioned scalar, run on the same stubs without that relation, is the baseline §22's without-admission replay measures. Beating that baseline is an empirical question. It is not entailed by the output being a scalar.

This is a generalization of the pattern already accepted elsewhere in the design: supersession and `tokenEstimate` both turned out to be *relations* or *derived functions* rather than intrinsic properties of a turn (IMPL §3.4, IMPL §5.4). Links are the same move applied to relevance.

## 16. Retrospective link index

**Proposal.** A service that periodically examines sealed turns and records typed, directed, weighted edges between turns whose connection is discoverable only in hindsight. The projector may then admit one endpoint because the other is load-bearing, rather than only because its own score rose, and only in the direction that edge type allows (§16.1). A link is not a license to pull either end into the assembly.

**Why sealing makes this tractable.** IMPL §5 seals a turn's payload at terminal status. An index over immutable content is stable, cacheable, and safely recomputable: re-running the indexer over the same sealed turns cannot produce different inputs. Without the seal, every index entry would be suspect the moment a turn was edited.

**Where links live.** Edges are derived data and belong in the mutable projection layer alongside `weight` and `projectionState`, never in the seal. This follows the resolution already reached twice: IMPL §5.4 derives supersession rather than writing it into the immutable row, and IMPL §3.4 derives `tokenEstimate` per renderer rather than freezing one value. A link is a hypothesis about content, not part of the content.

**Link types must be task-progress relations, not similarity.** WP Principle 2 rejects raw self-information, recency alone, and "interestingness" as weighting bases. A `similar_to` edge reintroduces all three under a new name, and topical similarity is both the cheapest thing to compute and the wrong thing to act on — it will happily link every turn that mentions the same file. Admissible edge types are ones that assert something about work:

| Type | Asserts |
|---|---|
| `constrains` | A commitment recorded in the source turn limits what the target turn may do |
| `invalidates` | The source turn makes a decision or result in the target turn no longer valid |
| `explains` | The source turn supplies the cause of an outcome observed in the target turn |
| `shares_root_cause` | Two symptoms trace to one underlying condition |
| `depends_on` | The target's result is contingent on the source's result holding |

The list is not closed. A new type is admissible only when traversing it changes what work should happen next, and only after §16.1 has a row for which endpoint may be admitted. "These are about the same topic" fails that test. There is no default admission direction for a type that lacks a row.

**Every edge carries its evidence.** An edge records the turns it connects, its type, a confidence value, and a reference to what justifies it — which acceptance criterion, which identifier, which recorded outcome, which sealed facts. An edge whose justification cannot be inspected cannot be audited when it turns out to be wrong, and §17 argues wrong edges are the primary hazard. Shared membership in a criterion is a candidate (§18.4), not this justification, and not a type.

### 16.1 Direction-specific admission

Directed storage records which turn is the source and which is the target. It does not say which endpoint may re-admit the other. A blanket rule — if either end is load-bearing, admit the other — injects false context even when the edge is correct. When a load-bearing source `invalidates` an older target, admitting an unpinned target's full payload injects the obsolete result the edge identifies. When a source `constrains` a target, the direction that matters is the opposite: the constraint is what the projection was missing.

Admission is defined per type. An edge whose type is not in this table is not traversable for admission until its row exists. There is no default direction.

| Type | Consult the edge when | Admit | Do not admit by this edge |
|---|---|---|---|
| `invalidates` | The target is in the assembly or is a plausible retry, or the source is load-bearing and names a result the actor might follow | The source, as the invalidating decision, expanded or stubbed. If an unpinned target is already present, force it to a marked stub: the obsolete result, and that this edge invalidates it. If the target carries an operator, system, or acceptance pin, leave that target expanded and attach the same invalidation marker separately | An unpinned target's full payload. That payload is the obsolete result |
| `constrains` | The target is load-bearing | The source, the commitment that limits what the target may do | The target. The constraint does not make the constrained work current |
| `explains` | The target, the observed outcome, is load-bearing | The source, the recorded cause | The target. It is already why the edge was consulted |
| `depends_on` | The target is load-bearing | The source, the precondition the target's result is contingent on | The target. Later contingent work is not pulled in because its precondition is in view |
| `shares_root_cause` | Either endpoint is load-bearing | The other endpoint. Storage direction is arbitrary; admission is symmetric, and neither end is obsolete by this type alone | Nothing is retired by this type. A separate `invalidates` edge is required before an unpinned payload is forced to a stub |

**Pins stay expanded.** The precedence is WP §6.2, which this section restates and does not replace. An operator, system, or acceptance pin stays `expanded` until unpinned, including when this edge is `invalidates` and including when the turn later draws an introduced-harm verdict (WP §6.2, §20.4). The invalidation marker (the result is obsolete, and which edge says so) is attached beside the expanded pin and charged against `B`. If the pin plus the marker exceeds `B_turns`, WP §6 fails closed. An unpinned obsolete target that is already present is forced to the marked stub in the table. The same pin rule covers every instruction in this section that forces a payload to a stub, including `shares_root_cause`. These forces are mandatory overrides in WP §6.1: they do not wait on weight hysteresis or re-admit cooldown.

**Final-assembly dependency invariant.** Co-presence is a property of the assembly that will be sent, not only of the edge's admit bit. An endpoint that is in that assembly for any independent reason (an active pin, a discretionary score that already cleared WP §6.1, the live result, or another edge already in the closure) still requires the counterpart this table names. "The edge admits neither" applies only when the target is in the assembly solely because of this edge. It does not remove a pin, and it does not leave a pinned or otherwise retained target in place while its required context is silently absent.

Traversal uses one closure per generation:

- **Depth.** Provisional **`Dep = 2`**. A newly required source may itself require a source, and that walk stops at depth 2 from the originally retained endpoint. A deeper edge is not admitted as a payload. Depth truncation is not an audit-only note. The retained endpoint that required the truncated source is rendered by the same rule as no-fit: `invalidates` fails closed, and every other type attaches a dependency-gap marker on that retained endpoint naming the missing source, the edge id, the type, and that the absence is `depth-capped`. An endpoint that entered the closure only as someone else's source is independently retained for its own further dependency. Sending it with the further source silently absent is non-conforming.
- **Cycles.** If the next endpoint is already in the closure, record `cycle` and stop that branch. Do not re-expand it.
- **Dedup and cap.** A turn named by several edges is charged once against the link sub-cap. A full source payload is one admission charge. A dependency-gap marker is a marker charge, not an admission charge.
- **No fit, target present only by this edge.** For `explains`, `constrains`, `depends_on`, and `shares_root_cause`, admit neither endpoint. For `invalidates`, fail closed under WP §6.2 and WP §6.3. Do not drop the pin, do not omit the marker, and do not admit the source while dropping the target's required form.
- **No fit, target independently retained.** Keep the target. For `invalidates`, fail closed: there is no degraded form that omits the source marker or the pin. For the other types, attach a **dependency-gap marker** on the target: edge id, source turn id, edge type, and the statement that required context is absent and the target must not be treated as unconstrained. The edge state is `degraded`, not admitted. The marker is mandatory and spill-protected (WP §6.3). Sending the target with neither the source nor that marker is non-conforming.

**Depth-three acceptance case.** Pinned T `depends_on` S1, S1 `depends_on` S2, S2 `depends_on` S3. The token budget can hold T, S1, S2, and S3. `Dep = 2`, so S3 is not admitted as a payload. S2 is in the assembly because the walk admitted it. The sent prompt carries a dependency-gap marker on S2 naming S3. Depth is the only reason S3's payload is absent. If the S2-to-S3 edge is `invalidates`, the call fails closed instead of sending S2 without that source.

Every link-admitted turn is marked as such (§17). The link sub-cap still applies. Tombstoned endpoints are ineligible on both sides (§21).

## 17. Why false links are worse than false weights

A weighting error has two forms. It can omit something useful. It can also admit something misleading: an erroneously high weight can expand an obsolete or harmful turn and displace current work. Both are weighting errors. The budget invariant still holds either way, and an omitted turn is still recoverable per WP §6. That recoverability is not a claim that a false weight leaves the projection honest, or that false weights are safe.

A link error injects content carrying an implied causal claim: this material bears on your current situation. That causal endorsement is a stronger risk than a bare weight, and it is a hypothesis to measure against the scalar baseline (§22's without-admission replay). It is not a measured result, and it is not a reason to treat false weights as categorically harmless.

Three consequences:

1. **False admission is the risk under test.** A wrong lead is an injected claim, so this design treats a false admission as more costly than a missing edge until measurement says otherwise. That cost ordering is a testable risk hypothesis, not a universal cutoff and not a measured result. The sentence "a link index at 60% precision is worse than no index" is withdrawn as a fact. Whether a measured precision is too low to admit edges is the predeclared gate in §22 (admission precision on the labeled shadow sample). Until that gate passes, edges MAY be recorded and revalidated, and MUST NOT admit turns into the model-facing projection. A shadow log of would-be admissions (§22) is a record for the gate. It is not admission. Prefer few, strong edges while the hypothesis is open.
2. **Link-admitted turns need a sub-cap inside `budgetTokens`.** Otherwise a burst of spurious edges can crowd out current unpinned work and force a fail-closed budget error. The sub-cap MUST NOT demote an active pin. Pins stay expanded under WP §6.2. If pins plus their markers plus the link sub-cap exceed `B`, the invocation fails closed (WP §6.3). The hard budget remains the outer bound; link admissions get a fraction of what remains after pins.
3. **Marking matters.** A turn admitted by link should be identifiable as such in the assembly, so a reader — human or model — can discount it. Silent injection removes the ability to tell a retrieved lead from established context.

### 17.1 Prior art: the adversarial link graph

Web search solved a structurally identical problem — a link graph whose edges are cheap to fabricate and profitable to fabricate — and the public record is worth reading before designing an indexer, because it does not vindicate the §17 position as stated.

**Links are weighted, not counted.** Google's "reasonable surfer" work models a user who follows some links more often than others, weighting each link by the probability it is actually clicked given position, prominence and context, rather than treating every link on a page as an equal vote ([US 8,117,209 B1](https://patents.google.com/patent/US8117209B1/en)). This is the nearest public analogue to typed, weighted edges over uniform ones. It is not a relation taxonomy.

**Bad edges are neutralized, not punished, and the credit is not recoverable.** Google describes using its spam system "to neutralize the impact of unnatural links on search results," with ranking changing "as spammy links are neutralized and any credit passed by these unnatural links are lost" ([Google Search Central, December 2022](https://developers.google.com/search/blog/2022/12/december-22-link-spam-update)), and states that once "our systems remove the effects spammy links may have... Any potential ranking benefits generated by those links cannot be regained" ([Google Search Central documentation](https://developers.google.com/search/docs/appearance/spam-updates)). That is §18.5's retraction lifecycle: withdraw the edge's contribution, keep the record.

**Edge annotations are hints, not directives — explicitly so information is not lost.** Google treats `sponsored`, `ugc` and `nofollow` "as hints about which links to consider or exclude within Search," reasoning that "by shifting to a hint model, we no longer lose this important information, while still allowing site owners to indicate that some links shouldn't be given the weight of a first-party endorsement" ([Google Search Central, 2019](https://developers.google.com/search/blog/2019/09/evolving-nofollow-new-ways-to-identify)). An edge marked untrustworthy is retained and downweighted rather than deleted — the same choice §18.5 makes.

**Trust is propagated from a human-evaluated seed set, as a counter-bias rather than a score.** TrustRank selects "a small set of seed pages to be evaluated by an expert," propagates trust along links, and is offered as "a counter-bias to be applied when results are ranked, in order to discount possible boosts achieved by spam," noting that plain PageRank "does not incorporate any knowledge about the quality of a site, nor does it explicitly penalize badness" ([Gyöngyi, Garcia-Molina and Pedersen, VLDB 2004](https://www.vldb.org/conf/2004/RS15P3.PDF)). This is the one result here that transfers cleanly: §19.4's passing tests and §19.3's HV verdicts are an expert-evaluated seed set, and edge confidence should decay with distance from a verified referent rather than being asserted per edge.

**The uncomfortable part.** The load-bearing signal in web search turned out not to be the link graph at all. A Google engineer's internal presentation, entered as a trial exhibit, states: "We do not understand documents. We fake it... Beyond some basic stuff, we hardly look at documents. We look at people. If a document gets a positive reaction, we figure it is good" ([UPX0203, U.S. v. Google](https://www.justice.gov/d9/2023-11/417516.pdf)). Google staff have since said links are not among the top three ranking signals and that "we need very few links to rank pages" ([Search Engine Land](https://searchengineland.com/links-google-search-ranking-factor-gary-illyes-432422)).

So the honest reading of the prior art is that the declared graph was never made trustworthy — it was **demoted in favour of an independent signal the ranking system did not author**: recorded reactions from millions of parties with no stake in any particular document's rank. A single agent session has no such population. §19's insistence that progress be read from acceptance-criteria state, and §19.3's insistence that the verdict come from a party that did not do the work, are the only available substitutes, and they are far weaker than a billion independent observations.

Two further disanalogies constrain how much of this transfers:

- **Opacity is not available.** Web search can partly defend a signal by not publishing it, and even that eroded — the 2024 Content Warehouse documents contradicted public statements about whether site-level authority and click signals existed. Here the actor is the same class of model, reading the same repository, including this document. Any anti-gaming property that depends on the actor not knowing the rule is void by construction.
- **The adversary is inside the system.** Web spam is third parties with a profit motive, and the remedy is demotion of the document. Here the misaligned party is the actor itself, and the closest available remedy is the one BDPv4 already prescribes for a session whose trust has broken: end it and start over (§19.4).

## 18. Continuous revalidation

**Proposal.** Model reconsideration is the capped schedule in §18.2 and §18.4. It is not a walk of every live edge after every turn. Tombstone and seal checks for edges in the assembly that will be sent are mandatory at the send fence (WP §6.1, §21). An edge that fails either is ineligible. Changed evidence forces the same ineligibility even when seal sequences, weights, projection states, and goal attribution are unchanged (§18.2). Stale edges and never-judged proposals stay on resumable cursors; the skip rule MUST NOT drop those cursors. A model is asked for the ordered subset in §18.2, subject to the per-generation cap, and each generation serves at least one oldest unjudged candidate when any exist (§18.4). A discretionary admission flip has to clear the §18.3 hysteresis band and the WP §6.1 cooldown. A mandatory invalidation (reseal, tombstone, or changed evidence) removes eligibility immediately and does not wait on that band. Links are per-generation hypotheses. Whether they are precise enough to admit turns is measured with independent labels (§22), not by how often edges are retracted.

Three constraints make the difference between this working and this entrenching errors.

### 18.1 Evaluation must be blind to the projection it influenced

If a false edge admits turn 4, and the next evaluation judges that edge while turn 4 is present in the assembled context, the evaluator sees a coherent narrative and confirms the edge. The edge has become its own evidence. Each generation then raises confidence in a false link, and revalidation — the mechanism introduced to remove false links — entrenches them instead.

**Requirement:** edges are judged against sealed payloads and recorded outcomes directly, out of band, never against the projection they contributed to. The convenient implementation is to ask the model about the context it already has; that implementation has the failure built in.

### 18.2 Evaluate the decision boundary, not the graph

Re-judging every edge after every turn is `O(E)` model judgments per turn. With candidate generation producing even a sparse `k` edges per turn, `E` grows with session length, so cost per turn grows and total session cost is superlinear — while competing with the live turn the index exists to help. WP §10 risk 6 already flags per-turn re-score cost as a live concern; this multiplies it.

Model calls are spent on edges that could change a decision this generation, plus edges the skip rule still requires: changed evidence and stale edges (§18.2 items 3 and 6). An edge between two turns that are both currently omitted, with confidence well away from the admission threshold, with unchanged evidence, and not yet stale, cannot alter the projection no matter how it is judged. That edge is the one the skip rule may pass over.

The requirement graph also bounds which pairs are eligible in the first place — see §18.4, which is the cheaper half of this problem. It generates candidates. It does not supply the causal type.

**Judgments are bound to seal sequences.** Each confirmed or retracted judgment records the seal sequence of both endpoints it was judged against. IMPL §5.4 derives the current seal as the row with the highest sequence. A later judgment against a different pair of sequences is a new transition (§18.5), not an edit of the old one. An edge is eligible for admission only while both endpoints' current sequences match the sequences on its latest confirming judgment.

**Reseal invalidates.** IMPL §5.1 permits a post-terminal mutation - `ReplaceTurnAsync`, section replace, item delete, title set, or a dialog append on an already terminal turn - to produce a new seal without changing `weight`, `projectionState`, or goal attribution. Those three are not a sufficient change detector. If either endpoint's current seal sequence differs from the sequence the edge was last judged against, the prior judgment is void and the edge is ineligible for admission until it is re-judged against the new payloads. The superseded payload is not evidence for the current edge. A reseal is an invalidation trigger ahead of any model call. It is ordering item 2. Changed evidence is ordering item 3 and is the same class of invalidation: the prior judgment is void even when weight, projection state, goal attribution, and seal sequence are unchanged.

Ordering, highest priority first. The per-generation judgment cap spends this list in order. Items that do not fit are deferred and recorded. A deferred edge whose prior judgment was voided (items 2 and 3) stays ineligible for admission until a later generation judges it.

1. Edges currently admitting a turn.
2. Edges whose endpoint seal sequence changed since the last judgment, including reseal after post-terminal mutation (IMPL §5.1, IMPL §5.4).
3. Edges whose cited evidence changed since the last judgment, even if seals, weights, projection states, and goal attribution did not. Cited evidence is any checkable referent the edge records (§16): acceptance-criterion state, bound-test pass or fail, an appended or superseded outcome record, an appended or superseded explanation, or a change in turn-to-criterion attribution. A superseded payload or a superseded explanation is not evidence for the current edge.
4. Edges with an endpoint whose `weight`, `projectionState`, or goal attribution moved this generation.
5. Edges near the admission threshold in either direction.
6. Stale edges: generations since last evaluation are at least `S`. Provisional **`S = 10`**. Operator-adjustable, and MUST be fixed before a revalidation run can pass or fail.

**Skip rule.** No model call is made for an edge only when all of the following hold: both endpoints are non-deleted; both seal sequences still match the latest judgment; no cited evidence changed; neither endpoint's weight, projection state, or goal attribution moved; the edge is not near the admission threshold; and the edge is not stale under `S`. Changed evidence forces a judgment. Staleness forces a judgment. Neither is skipped because weight and seal happened to be stable. When the cap is full they are deferred, recorded, and, if the prior judgment was voided, ineligible for admission.

**Judgment slots are reserved, so stale edges cannot be starved.** `J` (provisional **8**) is the model-call cap. It is split, and a configuration with `J_stale < 1` or `J < J_void + J_stale` is non-conforming:

- `J_void` (provisional **4**) is spent on ordering items 2 and 3 (voided judgments). Unused `J_void` slots MAY be used by stale edges, then by first judgments, then by items 1, 4, and 5.
- `J_stale` (provisional **2**) is reserved for ordering item 6. Whenever any stale edge exists, these slots MUST be spent on the oldest stale edges. Items 1, 4, and 5 MUST NOT consume `J_stale`.
- `J_first` (provisional **1**) is reserved for edges and proposals that have never been judged. Items 1, 4, and 5 MUST NOT consume `J_first` while any never-judged candidate remains. A configuration with `J < J_void + J_stale + J_first` is non-conforming.
- The remainder (`J - J_void - J_stale - J_first`, provisional **1**) is for items 1, 4, and 5.

A generation that spends a `J_stale` slot on a non-stale edge while a stale edge remains is non-conforming. Deferral of a voided edge still leaves that edge ineligible for admission.

**Starvation promotion.** If generations since an edge's last judgment reach `S + S_starve` (provisional **`S_starve = 10`**), that edge is judged before items 4 and 5, from `J_stale` and then from unused `J_void`. Promotion does not void the edge. It stops a standing diet of load-bearing and near-threshold edges from postponing item 6 forever.

**Contradictory evidence outside the citation set.** Reserved stale slots schedule review. They do not define what a review must consider. A confirming judgment records the citation set it used and a `claimFamily`: the approach name or result name the explanation asserts. A later turn can dispute that family without resealing either endpoint, without superseding their outcome records, and without changing a criterion id already in the citation set.

On append, a turn that records a disproof, a failed reproduction, or an HV label that a named approach or result does not hold MUST be marked `contradicts` and MUST name the `claimFamily` it disputes. That name need not be a string already stored in any edge's citation set. The append bumps `evidenceWatermark(claimFamily)` by one. The handler does not walk every dependent (§18.4). Every effective edge with that `claimFamily` is **suspended** when its stored `evidenceVersion` is below the watermark, including edges whose citation set does not contain the new turn's referents.

**Eligibility while adjudication is pending.** A suspended edge's admission bit is clear. It MUST NOT admit, MUST NOT satisfy joint admission (§16.1), and MUST NOT influence packing or a sent prompt. The prior confirming record stays in the audit log. Suspension is not a claim that the old judgment was edited. If the judgment cap defers the re-judgment, the edge stays suspended. Re-judgment reads both sealed endpoints and the contradicting turn. A confirming re-judgment may set the admission bit again under §18.3. Until that record exists, the edge is withdrawn from influence.

**Acceptance trace (third turn, no endpoint edit).** Turns A and B are sealed. Edge E is a confirmed `explains` from A to B. Its citation set is facts inside A and B, and its `claimFamily` is the approach those facts assert. E is admitting A beside B. Turn C is appended. C disproves that approach, does not modify A or B, and does not cite a criterion already in E's citation set. C names E's `claimFamily`. The next generation whose snapshot includes C suspends E before packing. The next send after C is durable MUST NOT carry E's admission. If the cap defers the model judgment, E is still absent from that send. A later judgment that retracts E appends a retraction. A later judgment that confirms E against C may admit again. Neither judgment is required for the withdrawal that precedes the send.

Model-call tokens are bounded by `J * T_j`. The cheap eligibility walk is not bounded by `J`. Its bound is §18.4. Deferred candidates share the backlog cap and the overflow cursor in §18.4.

### 18.3 Edge churn, and why the plan bounds it

Thrashing (oscillating scores, churning projection, dead prompt cache) reappears here because a single edge flipping can swing several turns at once. Discretionary admission flips use the band and the clock in this section. Mandatory invalidation (reseal, tombstone, changed evidence, contradictory evidence under §18.2, introduced-harm on an endpoint) MUST be applied during cooldown. Cooldown blocks only discretionary flips. Edge flip rate is a metric in its own right (§22). Active-context token replacement (WP §9.1) is the metric that shows whether those flips replaced the live tail. A linking run whose thresholds or clock are still the word "provisional" and have not been fixed for that run cannot pass or fail; the numbers below are the contract until an operator replaces them in the run record.

**Edge confidence band.** Provisional, and fixed for a run before that run executes:

- Discretionary admit requires confidence `≥ T_admit`. **`T_admit = 0.80`**.
- Discretionary withdraw of a confirmation requires confidence `≤ T_withdraw`. **`T_withdraw = 0.60`**.
- Confidence strictly between those values causes no discretionary flip.
- Scheduling item 5 ("near the admission threshold") means within 0.05 of either threshold.

**Edge cooldown clock.** `C = 2` is the same constant as WP §6.1, counted in `projectionGeneration`, not wall time. The clock starts when a discretionary admit or a discretionary withdraw changes the admission bit, at that generation. It does not start on forced invalidation. It does not reset because weight moved. Forced invalidation clears the admission bit immediately (§18.2). A later judgment that confirms the same edge again is a mandatory reconfirmation: it MAY set the admission bit without waiting out `C`, and that reconfirmation generation starts a new `C` so the next discretionary withdraw cannot oscillate on the following generation.

**Turn `Δweight` baseline.** WP §6.1 compares `weight` with `weightAtLastStateTransition`, the weight stored when `projectionState` last changed, not with the previous generation's weight. The field updates on every discretionary flip and on every mandatory state change. Repeated steps of 0.04 do not flip while the sum from that baseline stays below 0.05.

**Acceptance traces.** Gradual drift: state last changed at weight 0.50. The next generation is 0.54. Absolute delta from the baseline is 0.04, so no discretionary flip. The generation after that is 0.58. Delta from the baseline is 0.08, so a discretionary flip is allowed if cooldown allows it. Comparing only with the previous generation would have seen 0.04 and would be non-conforming. Forced invalidation: an edge inside cooldown is suspended by §18.2 on the generation the contradicting turn becomes visible, before the next send. A later confirming judgment re-admits without waiting for the old `C` to expire, and starts a new `C`. Capacity that appears because some other turn shrank still does not expand an omitted or summarized turn (WP §6 step 5).

**Hysteresis and cooldown stay primary until turn density is actually bounded.** A BDPv4 phase has a declared, finite acceptance-criteria set (§19.4), and those criteria are pinned by construction under WP §4.2's **acceptance** pin class. That bounds which criteria are in scope. It does not bound the volatile turn set or the edge set. One criterion can accumulate arbitrarily many retry turns, and the edges among them can swap those turns through the residual budget while the criterion itself stays pinned. Pinning the criterion does not pin the turns. v0.1.4 treated the finite set as the first line of defence and hysteresis as a refinement over a bounded residual. That overstated what the anchor bounds. Until a per-criterion density cap is defined - what it counts, the numeric limit, and what the projector does at the cap - hysteresis and cooldown are the primary defence against projection and cache instability. The criteria set remains a scope constraint on which pairs §18.4 may propose. Hysteresis and cooldown are the dampers for discretionary flips. Mandatory overrides in WP §6.1 still apply during cooldown.

Criteria themselves still move slowly, which is a useful property and not a churn bound on turns. BDPv4 expects requirement refinement every iteration, through approved diffs to plan artifacts at human cadence, not per turn. That rate applies to the criterion list. It does not apply to the turns attributed to one criterion.

Three things this does not cover, each of which the dampers still have to hold:

- **Phase boundaries are not thrash.** When a phase or slice completes, the relevant criteria set turns over wholesale and the projection legitimately changes with it. That is a scheduled flush — one predictable cache loss at a known point, which is cheaper than continuous churn — and the §22 flip-rate metric must be conditioned on phase boundaries or it will alarm loudest exactly when the system is behaving correctly.
- **Unattributed turns stay unbounded.** Turns that bear on no acceptance criterion — exploration, environment fights, debugging that led nowhere — fall outside the criteria set, and churn among them is bounded only by hysteresis and cooldown.
- **Bounded criteria do not bound turns per criterion.** A loop that retries the same criterion twenty times produces twenty turns all legitimately attributed to it, and the edges among them are dense, mutually confirming, and nearly worthless. This is why the density cap has to exist before the plan can be described as a churn bound. A criterion accumulating turns without a progress change is the §23 open question 11 deadlock signal rather than a linking opportunity. Until the cap is specified, open question 13 records it as unset, and §18.3 does not assume it.

### 18.4 Candidate generation is a traversal of the requirement graph

The hardest engineering problem in §15–§17 is which pairs to consider at all, and a plan-anchored design answers it without a vector index. Acceptance criteria carry stable identifiers that bind to requirements, test ids, named test methods, and slices (§19.1), and requirement families already have a human-authored relation structure recorded in the traceability mapping and matrix (§19.4). Turns inherit those identifiers by attribution. So candidates are turns reachable through shared or related criteria, not turns that resemble each other.

Three consequences, in descending order of how much they matter:

- **No embedding dependency. Quadratic all-pairs is withdrawn.** §21 records that the only embedding column at the code baseline is on `Chunks`, so an index over turns would have to be built. Traversing identifiers avoids that index for the first cut. It does not make pairing sub-quadratic: the turns on one criterion can still be paired with each other. The bound is the per-generation cap below, not the shape of the graph.
- **Shared criteria generate candidates, not edge types.** "Both turns bear on `AC-FR-MCP-MEMORY-010-02`" is common membership. It does not establish `constrains`, `invalidates`, `explains`, `depends_on`, or `shares_root_cause`, and it does not establish direction. Treating membership as one of those types would be the `similar_to` relation §16 rejects, under a checkable name. The requirement artifact may propose the pair. The causal type and the direction still require evidence in the sealed payloads or the outcome records, or an explicit judgment against that evidence (§16, §16.1, §18.1). The checkable referent §20.1 demands is the evidence for the typed edge, not the shared identifier by itself. The cheap identifier removes the temptation to use similarity as the only signal; it does not remove the judgment.
- **Candidate pairing is narrower than topical similarity; edge precision is not free.** §17 states a hypothesis that false admissions are costly, and §22 turns that hypothesis into a pass/fail gate. Criteria-derived pairs are wrong mainly when attribution is wrong, which is a narrower and more auditable failure than topical drift. A correct pair with an invented type or the wrong direction is still a false lead (§16.1). Proposal precision and admission precision are measured separately with independent labels (§22). Neither is assumed from the candidate generator, and neither is the retraction rate.

**Bounding by phase would reintroduce the hole this paper exists to open.** The valuable links are frequently long-range — §14's omitted constraint and §15's joint-value pair typically sit in different phases. Time is not the bound. The bound is the plan structure that is actually recorded, which at the baseline supports three traversals:

- The same acceptance criterion across any phase, where a catalog binds that criterion id.
- Sibling criteria under one requirement, where the catalog or the requirement document groups them.
- Co-membership of an FR with its primary TRs and `TEST-*` ids, from `docs/Project/TR-per-FR-Mapping.md`.

**Exact referent match is not enough for the quiet constraint.** The three traversals above do not recover §14 and §15, and neither does a match that fires only when the failure already quotes the constraint. Two candidate paths are both required:

- **Referent match.** Propose a pair when a load-bearing turn's outcome record, residual payload, or live error text names a checkable referent (an exact identifier, path, quoted constraint, or error token) and a sealed turn contains that same referent. This is not an embedding neighbor and it is not `similar_to`. Turns with no criterion id are eligible.
- **Constraint scan.** On append, a turn that records an operator constraint, an environment condition, or a standing "never" commitment (WP §5.1) MUST be marked `constraint-fact`, including when it has no criterion id, and its turn id MUST be appended to the plan's `constraintLedger`. The ledger is the retention horizon: every marked turn in the active plan stays addressable. The hot posting list below is an accelerator. Falling off that list does not delete the ledger id. The failure text does not have to contain the constraint string. Paraphrase and a stub that dropped the fact do not remove the ledger id.
- **Rotation, not newest-only.** Each scan proposes `K_constraint` ledger entries that have not yet been judged against the current `failureEvidenceRevision` (provisional **`K_constraint = 4`**), oldest unjudged first, from a durable `constraintCursor`. `K_constraint` counts against the generation-wide `K_ref` budget below. Newest-four selection is non-conforming. Turn 4 is proposed when the cursor reaches it, including when newer marks exist and including when turn 4 is outside the hot list. A rejection suppresses a later proposal only when the stored revision equals the current `failureEvidenceRevision`. One full cursor cycle on that revision with no confirming edge records `constraint-scan-exhausted` for that revision. That record is not success, and it does not apply to a later revision.
- **Failure identity and claim set.** A live failure has `failureId` (the same turn id plus its evidence watermark) and a claim set with `claimSetVersion`. Each claim has a `claimId`. `claimSetStatus` is `empty`, `unclassified`, `partial`, or `complete`. An ordinary raw error starts as `empty` until a writer assigns claim ids, or as `unclassified` when text exists but no id has been assigned. Status and version are append-only. `failureEvidenceRevision` is the tuple (`evidenceWatermark`, `claimSetVersion`, `rawErrorHash`). A constraint judgment and a scan-coverage record bind to that tuple, not to the turn id alone and not to the watermark alone.
- **Revision invalidates rejections.** A new raw-error hash MUST bump `claimSetVersion` and MUST increment `evidenceWatermark`. Either change produces a new `failureEvidenceRevision` on the same turn. That new revision invalidates prior rejection records and prior coverage-stop records, including `constraint-scan-exhausted` and an HV `explained` or `adjudicated-empty` that names the previous tuple. A writer that bumps `claimSetVersion` and leaves the watermark number unchanged still invalidates those records, because the tuple differs. Confirming edges are not deleted by the bump. The `constraintCursor` for the new revision restarts at the oldest ledger entry. Resuming a cursor that was exhausted under the previous revision is non-conforming. Reopening the scan without invalidating rejections is non-conforming.
- **Partial explanation does not stop the scan.** One effective `explains` or `constrains` edge does not suppress the scan. The scan stops only when `claimSetStatus` is `complete` for the current `failureEvidenceRevision` and every claim id in that version is cited by an effective non-suspended edge, or when HV records `explained` naming that same revision. A stop record for an earlier revision does not stop the new one. An empty or unclassified set is not complete. "Every claim id is covered" is false when the set has no ids. HV may stop an empty set only with `adjudicated-empty` naming the current `failureEvidenceRevision`. Any other stop on an empty or unclassified set is non-conforming, and the cursor keeps walking.
- **Empty is not success.** If the ledger has no entries and referent match also proposes nothing, record `constraint-scan-empty`. That record is not a successful recovery. Neither is `constraint-scan-exhausted`.
- **Recall.** The denominator is the set of constraints an independent labeler marks as bearing on the failure, including constraints the generator never proposed. The numerator is how many of that set were proposed before the cursor completed a cycle that should have reached them. Candidate-source share is not this ratio. A recovery test fails if a labeled constraint is missing from the ledger, or if newest-only selection skips it while the cursor contract would have reached it.
- **Recovery acceptance cases.** Each of the following MUST propose the labeled constraint from the ledger before the cursor laps, and the recall denominator MUST include it even if a candidate list omitted it: an old constraint (turn 4, failure at turn 60, more than four newer `constraint-fact` turns); a paraphrased constraint with no shared string; a constraint whose fact is absent from `summaryText`; an unattributed constraint with no criterion id; a crowded-out constraint that is not among the `L` hot-list ids; a raw error with no claim id, whose claim set is `empty`, so the scan is not allowed to stop before the cursor reaches the labeled constraint. Revised-failure reconsideration: constraint C is rejected against the same failure turn at `evidenceWatermark` 7 and `claimSetVersion` 1. The raw error then changes and C now bears on that failure. `claimSetVersion` becomes 2 and `evidenceWatermark` becomes 8. No new failure turn is created. The rejection of C is invalid. The cursor restarts at the oldest ledger entry. C is proposed again before that new cursor laps. Leaving the watermark at 7 while bumping only `claimSetVersion` still proposes C again. Skipping C because it was judged at watermark 7 is non-conforming.

Both paths produce candidates only. Type and direction still require out-of-band judgment (§16, §16.1, §18.1).

**What the caps actually bound.** Eligibility and emission are different limits. The plan structure, including cross-phase criteria, decides which pairs may be considered. The caps decide how many are emitted and how the cheap walk is done. Pairing every turn on one criterion is quadratic. The generator MUST NOT emit all pairs. v0.1.7 said work per generation is O(K) and that revalidation cost is bounded by `J` rather than by graph size. v0.1.8 said session cheap work is O(turns times (D + K_crit + K_ref)) and that a shared evidence event enqueues in O(D). v0.1.9 said session cheap work is O(G_session times (T_new + K_gen + J + F_max) + E_events). v0.1.10 said session cheap work is O(G_session times (T_new times L + K_gen + J + F_max)). Those sentences are withdrawn. The v0.1.9 formula did not include posting-list reads, did not forbid a walk of E_live, and did not schedule first judgments. The v0.1.10 formula capped each list's length and did not cap how many lists a turn opens, and it left `E_events` out of the displayed expression.

The bounds that this algorithm actually has, counted in sealed turns, generations, evidence events, and dependents pulled from a cursor:

- **Generation-wide inspection.** A generation considers at most `T_new` newly arrived or newly imported turns (provisional **`T_new = 4`**). Further turns wait on the overflow cursor. Per-turn emission caps are not a license to process an unbounded catch-up inside one generation.
- **Generation-wide emission and attempts.** At most `K_gen` candidate pairs are emitted per generation (provisional **`K_gen = 16`**, of which at most `K_crit = 8` are criterion-graph hits and at most `K_ref = 8` are referent or constraint-scan hits). At most `K_attempt` pair inspections are attempted per generation (provisional **`K_attempt = 32`**), counting duplicates, deleted endpoints, ineligible edges, already-judged pairs, and emitted pairs. `K_gen` is not larger than `K_attempt`. Emission of zero pairs does not permit further attempts. Both caps are per generation, not per turn.
- **List openings.** A generation opens at most `P_open` posting lists (provisional **`P_open = 8`**): criterion-id lists, referent-token lists, and the load-bearing list count toward the same cap. A turn may name more keys than `P_open`. Unopened keys are not dropped. The durable `inspectionCursor` stores the turn id and the next unopened key ordinal and resumes there on a later generation. Opening every referent on a turn in one generation is non-conforming.
- **Posting lists and the ledger.** A criterion id, a referent token, and the load-bearing set each retain at most `L` turn ids (provisional **`L = 16`**). The load-bearing list is not an uncapped exemption. Ids past `L` wait on that list's cursor. The `constraint-fact` hot list has the same cap. The `constraintLedger` is not capped by `L`. Selection reads at most `L` ids from each list it opens, and it opens at most `P_open` lists. It does not scan every sealed turn and it does not scan `E_live`.
- **Degree.** A turn holds at most `D` effective edges (provisional **`D = 32`**). A new edge past `D` is not admitted. Its id is the next overflow cursor key.
- **Shared-evidence fan-out.** An evidence event bumps one watermark and returns. It does not enumerate dependents. An edge whose `evidenceVersion` is below that watermark is suspended (§18.2). A generation pulls at most `F_max` such edges from a durable cursor (provisional **`F_max = 32`**) for judgment. The rest stay suspended and ineligible. Their bodies are not copied into a second queue.
- **Model judgments.** At most `J` per generation and at most `J * T_j` estimated tokens (provisional **`T_j = 4096`**), with the slot split in §18.2.
- **Backlog and overflow.** Unjudged candidate bodies wait in a backlog capped at `M` (provisional **64**). When another body would exceed `M`, do not store it and do not drop it silently. Append one `overflow-cursor` audit record (event id, turn id, edge or ledger id) and resume from that cursor on a later generation. The cursor is FIFO by append order. A second unbounded queue is non-conforming. A drop without the cursor is non-conforming.
- **Inspection is the capped reads above.** A generation reads at most `T_new` new turns, opens at most `P_open` lists, reads at most `L` ids from each opened list, attempts at most `K_attempt` pairs, emits at most `K_gen` pairs, pulls at most `F_max` watermark hits, and performs at most `J` judgments. It does not walk `E_live`. Seal and tombstone checks for the sent assembly happen under the send fence (WP §6.1) for turns in that assembly only. `J_first` and the FIFO overflow rule below are unchanged.
- **Oldest-first service.** Whenever any never-judged candidate or overflow-cursor entry exists, the generation MUST spend `J_first` on the oldest such candidate before it spends remainder slots on newer ones. Under sustained arrivals that keep filling the tail, an older candidate at FIFO position `n` is judged within `n` generations. A scheduler that always serves new arrivals first is non-conforming.

`E_live` is at most `turns * D` under the degree cap. That cap limits stored edges. It is not a license to scan them each generation. `G_session` counts every tool-loop model call (WP §6.1). Session model-token cost is O(`G_session` * J * `T_j`). Session cheap work for this procedure is O(`G_session` * (`T_new` + `P_open` * `L` + `K_attempt` + J + `F_max`) + `E_events`). `E_events` counts watermark-bump events. Each bump is O(1) and is inside that term. Omitting `E_events` from the displayed bound is non-conforming. The term does not add an `E_live` walk. An implementation that scans `E_live` each generation is non-conforming, and this bound does not apply to it. The caps MUST be fixed before a linking run can pass or fail.

**Acceptance traces for the bound.** Multi-call turn: five tool-loop calls inside one unsealed turn are five generations, and the cheap-work total counts five, not one. High fan-out: one criterion-state change bumps one watermark; the handler does not list the dependent edges; at most `F_max` are judged in that generation; every other dependent edge is suspended and absent from the send. Sustained overload: arrivals that would emit more than `K_gen` candidates, with only `J` judgments, fill `M` and then advance `overflow-cursor`. No candidate influences a call from beyond the cursor, and none disappears without that audit record. First-judgment service: 30 never-judged candidates sit on the FIFO cursor while new candidates keep arriving. Each generation spends `J_first` on the oldest. Candidate 30 is judged by generation 30. A schedule that never reaches it while new work arrives is non-conforming. Many-referent inspection: one new turn names 1000 distinct referents. Almost every posting-list hit is a duplicate, a deleted endpoint, or an already-judged pair, and the generation emits zero candidates. That generation opens at most `P_open` lists and attempts at most `K_attempt` pairs. `inspectionCursor` stores the next unopened referent. Later generations resume there. Probing all 1000 lists in one generation is non-conforming even though emission is zero.

**A requirement-to-requirement dependency graph is not in those artifacts.** `docs/Project/TR-per-FR-Mapping.md` maps each FR to primary TRs and tests. `docs/Project/Requirements-Matrix.md` maps each requirement to a status and source files. Neither records an edge between requirements, a direction, or what following that edge would mean. An earlier draft named "requirement-to-requirement dependencies from the matrix" as a traversal this design could execute. It cannot, and the long-range candidates that exist only as cross-requirement dependencies are absent until an artifact declares them. That artifact would still be candidate generation under the rule above: a dependency between requirements proposes pairs, and the turn-level edge type and direction still need payload or outcome evidence. Semantics required before any such traversal runs: what the requirement edge asserts, which direction it has, and that it is a hint rather than an admission. Open question 12 records the gap. Inventing the graph inside the indexer would recreate the unsupported causal edge this section exists to avoid.

Turns bearing on no criterion are eligible for referent match and for the `constraint-fact` scan. A similarity fallback remains out of scope until it meets the §22 admission gate and answers the `similar_to` objection.

### 18.5 Lifecycle is append-only

An edge's history is a sequence of recorded transitions — proposed, confirmed, retracted, re-proposed — each with its reason and generation, not a mutated confidence column. Two reasons:

- **Auditability.** When a projection changes between generations, the operator can ask why, and the answer is a readable record rather than a diff of vanished state. Each transition also records the endpoint seal sequences it was judged against (§18.2), so a reseal is visible as an invalidation rather than as a silent reuse of the old judgment.
- **Free churn measurement, not free precision.** The lifecycle yields a retraction rate and a flip rate per generation with no extra harness. Those are churn metrics. They are not precision. A false edge may stay confirmed indefinitely, and a correct edge may be retracted because a reseal or a later turn changed its applicability. Proposal precision and admission precision are defined in §22. Both need labels from a party that did not propose the edge: operator review, or another adjudicator judging the sealed payloads. Using retraction rate as either ratio would make the §22 report invalid. See §22.

**Persistence is mandatory.** IMPL §3.2.1: set-based updates bypass the audit ledger. Edge transitions, scope and progress revisions, and outcome records (including explanation supersessions) MUST be written through the tracked save path, or through an equivalent append-only ledger that set-based updates cannot bypass. If that path is unavailable, the write MUST fail closed. A mutable confidence column, progress cell, or explanation body updated in place is non-conforming.

**Effective state.** Readers compute current state from the append-only sequence. The effective edge is the latest transition that has not been invalidated by a later seal mismatch or a later evidence change. A new transition MUST name the transition it supersedes. Earlier transitions stay readable. Admission, weight revision, and projection MUST use the effective transition, not a side column. The same rule applies to the progress series (§19.2) and to explanations (§20.2): a correction is a new record that names the record it supersedes.

## 19. Goal metrics: scope and progress

### 19.1 The measurement that weight has been missing

WP §5 scores weight as relevance to unfinished work. This section defines the only progress quantity that may revise that weight.

**The goal is the plan, not the turn.** This is the unit correction that makes the rest of §19 tractable, and an earlier draft got it wrong by treating each turn as a thing to be scored. A turn has no goal of its own; it either moves the plan or it does not. Byrd Development Process v4 already fixes the unit: "Completion is not a definitive end state, simply a declaration of a set of requirements and acceptance criteria and proof of achievement of both" (`docs/Development-Process-draft-v4.md`, Planning). A plan declares the criteria; a turn contributes proof.

**Authoritative definitions (binding for weight and packing).**

The stored object is a **per-criterion state vector** for the active plan. Each in-scope acceptance criterion has one state: `passing`, `failing`, `skipped`, `untested`, or `blocked-no-test` (declared, but no bound test). A criterion id appears once. A slice view is a filter of this vector. It is not a second progress number for weight.

- **Scope** is the count of criteria in the vector, including `failing`, `skipped`, `untested`, and `blocked-no-test`.
- **Progress** is the count of criteria whose effective state is `passing`. `skipped` is not passing. `failing`, `untested`, and `blocked-no-test` are not passing.
- A **tier-2 checkpoint** may update every criterion the suite actually executed. Criteria the suite does not name keep their previous state. The revision records which ids ran.
- A **tier-3 targeted run** updates only the criteria it executed. It MUST NOT mark an unrun criterion `passing` or `failing`, and it MUST NOT replace the vector with the partial count.
- The **effective state** of a criterion is the latest append-only revision for that id (§18.5). A mutated cell is non-conforming. "Progress is an estimate" in §19.2 means a revision of this same vector can be wrong. Introduced versus revealed classifies a downward revision. It is not another progress series.
- A turn's **reading** is the set of per-criterion attributions after a tier-2 or tier-3 revision, plus the scope and passing counts. Each criterion the turn affected stores `{criterionId, before, after, class}` where class is `gain`, `loss-introduced`, `loss-revealed`, or `none`. The net counts do not replace that set. §19.5 reduces the set into weight and warnings. A `gain` MUST NOT delete a `loss-introduced` row.

**Evidence state is not the test observation.** Each criterion stores two records. The **test observation** is `pass`, `fail`, `skipped`, or `not-run`. The **satisfaction** state is what progress counts, and only HV writes it: `passing`, `failing`, `skipped`, `untested`, `blocked-no-test`, or `disputed`. Progress counts `passing` only. A `pass` observation is not `passing`. `disputed` is not `passing`.

Every observation and every satisfaction revision binds five artifact versions plus the observation revision: `codeHash` of the exercised files and their declared dependency closure, `testHash` of the bound test, `criterionHash` of the criterion statement, `catalogHash` of the catalog row, `environmentId` of the named toolchain and fixtures, and `observationSeq` of the observation HV adjudicated. A revision that omits any of these is non-conforming and MUST NOT be treated as current. A newer observation on the same five artifact versions gets a higher `observationSeq`. The historical satisfaction row stays readable and is labeled with the `observationSeq` it adjudicated. It is not current satisfaction once a newer contrary observation exists.

**Precedence.** HV satisfaction outranks an observation only for the `observationSeq` it names. A later run that observes `pass` on the same binding MUST NOT overwrite an HV `failing` or `disputed` satisfaction. Overwrite of an adverse judgment requires a new binding together with a new HV adjudication, or an HV record `addressed` that names the prior adverse revision. A newer observation of `fail` or `skipped` on the same five artifact versions, with a higher `observationSeq` than the one current satisfaction names, suspends that satisfaction immediately: current satisfaction becomes `disputed` before the next HV record. Progress MUST NOT keep counting the older `passing` row.

**Stale and disputed.** If any of the five bindings changes and the criterion is not re-executed and re-adjudicated on the new tuple, the old observation becomes `stale` and satisfaction becomes `disputed`. A partial run updates observations only for criteria it executed. It still applies the binding check to criteria it did not execute. An unexecuted criterion whose bindings did not change keeps its satisfaction. An unexecuted criterion whose shared dependency changed becomes `disputed` and drops out of the passing count.

**Acceptance cases.** Passing-but-inadequate: the bound test observes `pass`, and HV writes satisfaction `failing` with reason `inadequate`. The criterion is not in the passing count. A later run of the same test hash that again observes `pass`, with no new HV adjudication and no `addressed` record, leaves satisfaction `failing`. Targeted run after a shared dependency change: criterion X is `passing` on binding B1. A tier-3 run executes only criterion Y and changes a file in X's declared dependency closure, so X's `codeHash` moves to B2. X was not executed. X's satisfaction becomes `disputed`. The passing count falls by one until X is re-executed and HV adjudicates B2. Same-binding pass-then-fail: observationSeq 1 is `pass` on binding B and HV writes `passing` for that seq. observationSeq 2 is `fail` on the same five artifact versions. Current satisfaction becomes `disputed` before any new HV record. The passing count drops. The observationSeq 1 row remains readable and is not current.

The following are not authoritative progress and MUST NOT revise `weight` or change packing on their own: WP §5.1 relevance (the quantity `weight` already is); a raw test observation with no HV satisfaction on the current binding; a tier-1 pending verdict; an actor intent claim; a completion ratio; the prose label "progress narrative."

**Proposal.** Track those two series per plan. Scope rises when the plan grows or proves more complex than believed. Progress rises when another in-scope criterion's bound test is passing on the latest authoritative reading.

BDPv4 plans in this repository carry Functional, Technical and Testing requirements with stable identifiers, and `docs/plans/mcp-memory-002-ac-catalog.json` enumerates 283 acceptance criteria that each bind a statement to a requirement, a `TEST-*` id, a named test method, and a slice. The counts above are commensurate by construction (the §19.3 commensurability requirement is satisfied by the artifact), and BDPv4's phase-exit gate ("the full test suite for the current increment plus all prior work must be green") is one way to produce a tier-2 reading. That reading is plan-level. It is not by itself a per-turn verdict, and `Validate-RequirementsTraceability.ps1` does not compute it (§19.4).

Two independently moving lines, rather than a single percent-complete, which is the property that makes the pair robust to a goal changing underneath the measurement. A completion ratio alone cannot distinguish "advanced" from "target moved." This is the burn-up / earned-value shape, and that lineage should be cited if this enters the whitepaper — WP §12 is frozen for v0.1.x, so it is named here as a concept and needs a reference in v0.2 rather than a citation added now.

Both values belong to the plan. A turn's reading is the pair of plan-level deltas attributed to it:

| Scope | Progress | Reading |
|---|---|---|
| flat | up | Genuinely useful turn |
| flat | flat | No net movement. Harm still applies if any criterion is `loss-introduced` (§19.5) |
| up | flat | Discovery or decomposition — the goal was larger than believed. Not harmful |
| up | up | Work plus discovery |
| flat | **down** | Regression — but see §19.2 before calling it harm |
| **down** | up (ratio) | Descoping. Must be justified, never rewarded — see §19.3 |

### 19.2 Progress regression does not imply a harmful turn

A regression is a downward revision of authoritative progress as §19.1 defines it. The rule "progress regresses with scope constant, therefore the turn was harmful" is not sound as stated, and the correction matters because the exception is high-value.

A turn that discovers earlier work was wrong reduces progress without changing scope. It is also frequently the most valuable turn in a session. Under the unqualified rule it is scored as harm, which optimizes directly against error detection.

BDPv4 states this outcome as an expectation rather than a hazard, under "Resolving Defective Requirements": writing tests against acceptance criteria surfaces "paradoxes created by mismatched priorities, ambiguity and incorrect rules," and "Expect to refine requirements in each iteration... Expect to touch previously written code... This is not a failure of the process, but validation that the core philosophy of iterative improvement is alive and working." The argument below is therefore a restatement of existing process doctrine in metric terms, not a new finding, and it is cited here as precedent rather than presented as a discovery.

The distinction is **introduced** versus **revealed**:

- *Introduced* — the turn made things worse. Progress genuinely fell. This is harm.
- *Revealed* — the turn discovered that a previous progress reading was overstated. Nothing got worse; the measurement was corrected.

This forces a useful admission: **progress is an estimate carrying error, not ground truth.** So the progress series must be append-only revisions with attribution, never a mutated current value. Overwriting destroys the only evidence that distinguishes the two cases after the fact.

Worked example from this document's own history: the whitepaper and implementation proposal absorbed five corrections in one session, each one reducing apparent progress — sections reopened, recommendations reversed, claims retracted — while raising actual correctness. A metric that scored those as harm would have taught the agent not to look.

### 19.3 Who measures progress: Hostile Validation, not the actor

The acting agent must never score its own progress. It is an unreliable narrator with a standing incentive to report advancement, and that is structurally the same defect WP Principle 8 exists to block — a self-produced number presented as an outcome.

**Progress and regression readings are outputs of Hostile Validation.** WP §11 defines HV as an accuracy and completeness gate. Today it is applied as a document-level review ritual; here it becomes a runtime component that adjudicates turns. The actor does the work; an adversarial validator, which did not do the work and is not rewarded for it having gone well, determines what was accomplished.

This is the same structural move as §18.1, and the two should be stated as one rule:

> **No component may validate using the artifact it produced.** Link revalidation is blind to the projection it influenced (§18.1); progress adjudication is blind to the actor's own account of its work (§19.3).

**Claim versus verdict.** The actor is still the best source of *intent* — what it was trying to do and why it believed the approach would work — and that knowledge is not recoverable from a transcript afterwards. So the two roles split:

- The actor records an **intent claim**: the goal targeted, the criterion it expected to satisfy.
- HV records the **verdict**: what actually resulted, and the progress or regression delta.

One direction of divergence is the harm case in §19.2: the actor claims a criterion was met and HV finds it was not, detected without anyone having to trust the actor. Agreement is not a failure mode. When the claim is accurate and the work is straightforward, a competent independent validator should agree. Near-zero divergence is compatible with a healthy batch and with rubber-stamping; the rate alone cannot tell them apart, and treating agreement as capture would reward false adverse verdicts (§22).

**HV is not ground truth either.** It is an adversary with its own error modes, false accusation among them, and it may be wrong in the other direction. So verdicts are evidence rather than fact: append-only (§19.2), and anchored to checkable referents rather than to HV's unsupported opinion. WP §4.2's `pin` classes already include **acceptance**, which supplies the anchor — HV's job is to check acceptance criteria, tests, builds and artifacts, and to label any interpolation between them as interpolation rather than as measurement.

**Where the gaming surface moves.** HV closes self-reporting; it does not by itself stop an actor from arranging favorable criteria. §19.4 closes the part planning can close: criteria precede the turn. The traceability script fails when a present `## FR-` heading is absent from the mapping or the matrix. It does not fail when that heading is deleted and the row is left behind. With `-StrictTrAndTestCoverage`, a present `## TR-` heading or a present `TEST-` token that is absent from the matrix also fails the script. Without that switch those gaps warn and the script exits 0. It leaves the catalog-to-test surface open, and it leaves orphan rows open. Deleting an acceptance criterion, or weakening the test bound to it while the matrix row remains, is not a script failure. Deleting the definition while the row remains is not a script failure either.

**Cost and cadence.** Plan-level progress in §19.1 is criteria with passing tests. BDPv4 requires the full suite for the current increment plus all prior work to be green before an implementation phase exits (`docs/Development-Process-draft-v4.md`, Implementation). It does not require that suite after an ordinary turn inside the phase. A phase-exit run is one reading for the phase. It cannot attribute a pass or a failure to an individual turn: every turn since the previous green reading is a candidate cause. Reusing that eventual run as a per-turn verdict would invent attribution the runner does not have. Running the full suite after every turn would be a new cost, and it would contradict any claim that per-turn readings are free.

Per-turn HV verdicts use three tiers. The cost sits with the tier that actually ran:

1. **Intent only, between runs.** After an ordinary turn the actor's intent claim is recorded and the HV verdict is `pending`. No suite is launched. This tier does not fill §19's scope/progress table and it is not a progress delta. It also does not write satisfaction. A test observation, if one was already stored, stays an observation (§19.1).
2. **Batched attribution, at a checkpoint.** The next scheduled run - a slice checkpoint the plan already names, or the phase-exit suite - produces one scope/progress reading for the batch. HV attributes the delta to turns inside the batch. The candidate set for a criterion is the union of three sets, since the previous authoritative reading. (1) Turns that modified that criterion's bound test or the code the test exercises. (2) Discovery turns: turns that did not modify that code, whose sealed residual facts or outcome record cite the criterion, a requirement it decomposes, or the defect being revealed, and that HV labels `discovery` or `revealed` for that criterion. Scope-up with flat progress in the §19.1 table is this class. (3) Investigation turns whose intent claim names that criterion, when HV accepts the claim as discovery. The actor's claim alone does not attribute. Turns in none of these sets stay unattributed for that criterion. Discovery and revealed-regression turns are inside the set; they are not dropped because they never touched the test. Attribution is a judgment over that candidate set (§19.2, introduced versus revealed), not a property of the test runner. The suite is charged once per batch on the §22 HV adjudication cost, not once per turn, and not described as free.
3. **Targeted tests, when a turn-level verdict cannot wait.** A harm flag, link evidence that cites a criterion, or the §23 deadlock threshold may request the tests named by the affected criteria, not the full suite. That request is a cost BDPv4's phase-exit gate does not already pay. It is reported per request in the §22 HV adjudication cost. It is not the default tier.

Model adjudication remains what tests cannot decide: whether a passing test demonstrates its criterion, and the introduced-versus-revealed split inside a batch. That ordering follows WP §10 risk 6 ("v1 rules by default; judge on schedule or on budget pressure"). An earlier draft of this section called the phase-exit suite the per-turn base tier and said most readings are free. That collapsed a phase aggregate into a per-turn verdict. The phase-exit suite remains the BDPv4 gate and the plan-level reading in §19.1. It does not yield per-turn verdicts. If targeted runs or full-suite runs grow with turn count, adjudication has become the default tier. Nothing here claims runtime HV is cheap or currently available. The operational Perplexity HV gate remains blocked on an API key after box reseed and must not be described as done. The secondary document pass named in Appendix A is a separate finding list. It is not that gate, and it does not qualify the design.

**Commensurability.** Scope and progress must share units, or independent movement means nothing. If scope counts known acceptance criteria, progress counts criteria met. If scope is in estimated units of work, progress must be in the same units. Mixing "complexity" with "criteria completed" produces two series whose deltas cannot be compared.

**Descoping.** Removing scope inflates any completion ratio without work being done. Every scope change records direction, reason, and justification, and the ratio must never be a reward signal on its own. A scope reduction is a claim that work is unnecessary, and that claim is exactly as checkable as a progress claim. BDPv4 places that decision outside the actor entirely: "stakeholders need the flexibility to iteratively approve or deny continued resource expenditure towards completion." Descoping is a stakeholder act, and an actor-initiated one is a request, not a scope change.

### 19.4 Planning closes the criteria surface

> **Traceability script limits.** `scripts/Validate-RequirementsTraceability.ps1` covers present identifiers only. `FR-` and `TR-` present identifiers are `##` headings. `TEST-` present identifiers are tokens in `Testing-Requirements.md`, not headings. Default mode fails when a present `## FR-` heading is absent from the mapping or the matrix. Default mode warns, and can still pass, when a present `## TR-` heading or a present `TEST-` token is absent from the matrix. `-StrictTrAndTestCoverage` makes those TR and TEST gaps fail. Deleting a definition while retaining the mapping or matrix rows can pass. The script does not check orphan rows, acceptance catalogs, named test methods, or test adequacy. The same box is in the whitepaper after Scope and in IMPL §1.
>
> **Qualification prerequisites.** Implemented WCP behavior, measured efficacy, operator approval, and independent operational HV / MCP audit closure remain qualification prerequisites. A documentation review does not establish those.

Criteria authorship is not left to the turn that will be judged by it. BDPv4 requires the criteria to exist before implementation: "Planning results in a set of artifacts that capture Functional Requirements... Technical Requirements... Testing Requirements... and Iterative Phases," and "System components need to be discovered, designed and all public interfaces documented before writing implementation code." Plans in `docs/plans/` name their requirement families in the header and withhold `Done` until independent gates pass — `PLAN-LLMSTRATEGY-001-bdpv4.md` records "leave `Done: false` until Codex READY, tests Failed 0/Skipped 0, and hostile AGREE." Three gates, none of which the acting agent controls.

Two mechanical properties do the work that §19.3's adjudication cannot:

- **Criteria precede the turn.** An actor cannot mint a favorable criterion mid-turn, because the criterion set is a plan artifact authored before implementation and versioned with it. Scope changes are visible as diffs to that artifact.
- **Identifier coverage is one direction. Catalog-to-test coverage is not checked, and orphan rows are not checked.** `scripts/Validate-RequirementsTraceability.ps1` reads `## FR-` headings from `Functional-Requirements.md`, `## TR-` headings from `Technical-Requirements.md`, and `TEST-` tokens from `Testing-Requirements.md`. It checks those present identifiers against `docs/Project/TR-per-FR-Mapping.md` and `docs/Project/Requirements-Matrix.md`. It does not read mapping or matrix rows as the list of required definitions, so a row with no remaining definition is not a failure. It exits non-zero when a present `## FR-` heading is absent from the mapping or from the matrix. With `-StrictTrAndTestCoverage` it also exits non-zero when a present `## TR-` heading or a present `TEST-` token is absent from the matrix. Without that switch, those TR and TEST gaps warn and the script exits 0. It does not read `docs/plans/*-ac-catalog.json`, it does not resolve named test methods, and it does not compare an acceptance-criterion statement with the test that is supposed to demonstrate it. Deleting an `## FR-` heading while its mapping row and matrix row remain passes, in default mode and with `-StrictTrAndTestCoverage`. The same holds for deleting an `## TR-` heading or a `TEST-` token while the matrix row remains. Fixture shape: `FR-DEMO-003` is present in the mapping and the matrix, the `## FR-DEMO-003` heading is removed, and other headings stay. A runspace fixture of that shape passes. Restoring that heading without a mapping row, or without a matrix row, fails in that same fixture style. Appendix A records that these checks were not separately measured native process exit codes, and that no build or full unit-test suite was run. Deleting an acceptance criterion from a catalog, or deleting or weakening its bound test while the corresponding `TEST-*` row remains in the matrix, still passes. That is the criteria-gaming surface this section is about, and the script leaves it open. Closing it would take a separate catalog-to-test check and a separate orphan-row check. This paper does not claim either check exists. Until they exist, a catalog edit, a bound-test edit, or a deleted definition with a leftover row is visible to a reader of the diff and invisible to this gate.

**The real gaming mode is narrower than criteria invention, and it is already documented.** BDPv4's monitoring list names it: an agent stuck in "unresolved loops of failing tests... can lead to the agent marking a test as invalid so it can keep moving forward while trying to be a useful assistant, losing its identity as a precise software engineer in the process." That is criteria gaming as actually observed — not authoring an easy criterion, but invalidating a criterion that is bound to a test and blocking. A reader of the diff can see a test method named in the acceptance catalog changing state to skipped, deleted, or rewritten. `Validate-RequirementsTraceability.ps1` will not. This is why BDPv4's phase-exit gates count skips (`Failed 0/Skipped 0`) rather than only failures, and why a test-state change touching a catalogued method should be treated as a scope change requiring stakeholder approval rather than as ordinary refactoring. The gate that would fail the build on that diff does not exist yet; the stakeholder rule is the control that does.

**The residual is human.** BDPv4 does not claim automation closes this — its mitigations for all three monitored behaviors are an experienced human steering in real time, and for a session whose trust is broken, abandonment: "its impossible to fix the trust and get the model to behave correctly. Simply end that session, close that agent, and start over." Any claim that this paper removes the operator from the loop would contradict the process it depends on.

### 19.5 How authoritative progress revises weight

Two layers. `scorerWeight` comes from WP §5.2 and does not include this section. `effectiveWeight` is `scorerWeight` after the rule for the **effective** verdict only: the latest superseding outcome record (§18.5, §20.2). Progress machinery MUST NOT write `weight` from a tier-1 pending verdict or from an actor claim alone. Floors and ceilings below are provisional, operator-adjustable, and MUST be fixed before a scoring run can pass or fail. They are absolute values on the independent scalar in WP §4.2.

A corrected verdict replaces the progress layer on the next generation snapshot (WP §6.1). It does not stack a new floor or ceiling on top of the old one. The previous ceiling or floor does not remain after the class changes.

- **Progress up** (scope flat or up, passing-count up), attributed to the turn: `effectiveWeight = max(scorerWeight, 0.60)`.
- **Discovery** (scope up, passing-count flat), attributed to the turn: do not lower `scorerWeight` because scope grew. If the discovery is the current blocker or the constraint the live failure cites, `effectiveWeight = max(scorerWeight, 0.60)`. Otherwise `effectiveWeight = scorerWeight`. The turn stays eligible for the constraint scan and the criterion graph (§18.4).
- **Introduced harm** (any per-criterion class `loss-introduced`, even when scope is flat and the passing count is flat or up): `effectiveWeight = min(scorerWeight, 0.20)`, and WP §6.2 applies (marked stub if unpinned; expanded pin plus harm marker if pinned). A `gain` on another criterion does not cancel this warning and does not replace the ceiling with the progress floor. The gain row stays in the audit. Floors and ceilings do not stack: when both a gain and an introduced loss are present, the ceiling is the progress layer and the warning stays.
- **Revealed regression**, on the revealing turn: do not apply the introduced-harm ceiling to that turn. If it is the current blocker, `effectiveWeight = max(scorerWeight, 0.60)`. Turns that held the overstated progress take the introduced-harm rule only when the effective verdict attributes `introduced` to those turns.
- **No attributed delta,** or a superseding verdict whose effective class is none of the above: `effectiveWeight = scorerWeight`. Remove the harm annotation only when this bullet is a superseding verdict, not when a floor merely expires. A pin stays expanded. An unpinned turn is no longer forced to the harm stub when the effective class is not `introduced` or when §20.4 has retired the warning.

**Floors and ceilings expire without a false verdict.** A floor or ceiling applies only while the contribution is still active. Active means the credited criterion's satisfaction is not `passing` on the current binding, or the turn is the current blocker, or the live failure cites the turn. When the credited criterion is `passing` on the current binding and the turn is neither the blocker nor cited by the live failure, the next snapshot sets `effectiveWeight = scorerWeight`. The progress-up or discovery record stays in the audit log. Expiration is recomputation. It MUST NOT be written as a superseding verdict that calls the old credit false. The same recomputation drops an introduced-harm ceiling when §20.4 retires the warning. The `introduced` verdict stays in the audit log.

Floors and ceilings still do not stack. A superseding verdict replaces the progress layer. An expiration removes the layer. Neither adds a second floor onto a leftover one.

**Acceptance traces.** Verdict correction: HV supersedes `introduced` with `revealed`. The next snapshot drops the 0.20 ceiling and does not keep a 0.60 floor from an earlier credit unless the revealed bullet above applies. Completion-driven relevance loss: a turn's credit is real, `scorerWeight` moves from 0.50 to 0.00 after the credited criterion becomes `passing`, and the turn is not the live blocker. The floor expires. `effectiveWeight` is 0.00. Discretionary demotion compares that value with `weightAtLastStateTransition` (WP §6.1) and MAY demote. The audit row for the original progress-up credit remains. Mixed outcome, one plan, one turn: criterion A moves from `failing` to `passing` (`gain`) and criterion B moves from `passing` to `failing` with class `loss-introduced`. Scope is flat and the passing count is flat. The turn still takes the introduced-harm ceiling and an active harm marker. The A gain remains in the audit and does not clear the marker.

If HV supersedes `introduced` with `revealed` or with no delta, the next snapshot uses the new `effectiveWeight` and the new annotation. The old 0.20 ceiling is not left in place.

A weight write from this section is allowed during re-admit cooldown. `projectionState` still follows WP §6.1: the effective harm class is a mandatory override; discretionary state changes wait on hysteresis and cooldown.

## 20. Turn outcome records: result plus explanation

**Proposal.** Each turn carries a record of its result together with an explanation of why that result occurred. The explanation, not a bare number, is the signal that determines whether the turn advanced or regressed the goal.

This is what makes §19 operable. A progress delta on its own cannot distinguish introduced from revealed regression (§19.2), nor justify a scope change (§19.3). The explanation supplies the attribution that both need.

Per §19.3, the explanation is an **HV output, not an actor output**. The actor contributes its intent claim; the adversarial validator accounts for what actually happened. An earlier draft of this section had the actor explaining its own result, which reintroduced the exact gaming surface §19.3 exists to close — and free-text self-justification is *worse* than a self-reported number, because prose can persuade in ways a number cannot.

### 20.1 Explanations must be structured claims, not prose

Moving authorship to HV removes the incentive to flatter; it does not by itself make an explanation checkable. An adversary can also be confidently wrong, and a fluent accusation is as unfalsifiable as a fluent excuse.

So explanations — from either side — are constrained to verifiable referents: which acceptance criterion changed state, which test moved, which prior turn is contradicted, which file or identifier is implicated, which goal is affected and in which direction. Then the account is checkable rather than merely persuasive, and one citing nothing checkable is visibly weak on its face. This applies symmetrically to the actor's intent claim and to HV's verdict; neither gets to assert an outcome it cannot point at.

#### 20.1.1 The explanation's destination is the plan, not just the metric

BDPv4 already uses explanations this way, and for a purpose stronger than scoring: "ask the model what caused it to go on a tangent, and how the requirements and workspace guidelines could have guided it towards the correct path to take. Then have **THAT** model update the documentation and guidelines." The explanation is an input to criteria refinement.

That closes a loop §19.4 would otherwise leave open. Criteria precede the turn, so an actor cannot revise them to suit its own result — but criteria are also frequently the thing at fault, which is BDPv4's "Resolving Defective Requirements" case. Routing explanations into requirement and guideline revision lets defective criteria be fixed without letting the actor fix them *for its own verdict*: the revision is a scope change to a plan artifact, visible as a diff and subject to the stakeholder approval in §19.3.

### 20.2 Explanations are append-only evidence

An explanation is written at the time, from what was then known, but the signal it feeds is retrospective. Later turns may show it was mistaken. It must therefore be preserved and reinterpreted, never rewritten in place: the record is evidence-at-the-time. A correction is a new record that names the record it supersedes (§18.5). The effective explanation is that latest record. This is the same append-only requirement that §18.5 places on edges and §19.2 places on the progress series, and for the same reason - retrospection needs an unedited past.

### 20.3 Consequence: `summaryText` keeps residual payload facts

WP §4.2 carries `summaryText` as the mid-tier stub, produced by summarizing the payload. The outcome record is an input to that stub. It is not a sufficient source for it.

An earlier draft said the pairing of intent claim and HV verdict should replace the payload summary: it is already compressed, it avoids a second summarization pass, it is stable across regenerations, and each half has an author the payload summary lacks. That replacement drops facts that are neither the attempted criterion nor the outcome. WP §5.1 treats those facts as high-weight inputs: an operator constraint that has not been externalized to memory, the exact error text of an unresolved blocker, an environment condition, the latest tool result the next action depends on. WP §5.2's v2 judge re-scores omitted turns from candidate stubs, not from full payloads (§14). A stub that kept only intent and verdict makes those facts invisible to scoring and to the live projection, which removes the quiet constraints this paper is trying to keep recoverable.

**Requirement.** `summaryText` is derived from the outcome record and from residual payload facts. The outcome record contributes what was attempted, what HV judged, and the checkable referent (§20.1). The payload contributes facts the outcome record does not state. A derivation that cannot point at those facts in the sealed payload is incomplete. Intent plus verdict is the outcome half of the stub, not the stub.

The cost and stability arguments still apply to the outcome half. They do not justify omitting the payload half. Inside the outcome half, both roles still matter: an HV verdict alone loses why the approach was chosen, which is what stops the same reasoning being retried; an actor claim alone is the self-assessment §19.3 rejects.

This is a design change to the summarized tier and should be evaluated as one, not adopted by assumption.

### 20.4 Consequence: introduced-harm is a marker, and pins stay expanded

WP §4.2 allows `expanded`, `summarized`, `omitted`. None of those names is "actively misleading." Introduced-harm (the `introduced` class in §19.2) is an annotation on one of those states, not a fourth `projectionState`. Open question 2 is closed by this rule. The rule is WP §6.2; this section restates it.

- An **unpinned** introduced-harm turn MUST be `summarized`, with a marked stub: the approach, that HV judged it introduced a regression, the checkable referent (§20.1), and a statement that the payload is not the recommended next action. It MUST NOT stay `expanded`. It MUST NOT be silently `omitted`, because omission leaves the failed approach available to retry with no marker.
- A **pinned** introduced-harm turn (operator, system, or acceptance pin) stays `expanded` until unpinned. The same harm marker is attached beside the expanded payload and charged against `B`. The pin is not stubbed, omitted, or suspended. If the pin plus the marker exceeds `B_turns`, WP §6 fails closed.
- A **revealed** regression is not introduced-harm and does not force either bullet.

The marker is what tells the model not to treat a pinned payload as the next action, while Principle 5 keeps the pinned text verbatim. Stubbing a pin would hide content the pin exists to keep. This is the same precedence §16.1 already uses for `invalidates`.

**Active warnings only.** A harm marker or an invalidation marker is part of the mandatory set only while its `warningState` is `active`. Active means the warning still prevents a current retry: the plan is not retired, and HV has not recorded `repaired` for that verdict on a criterion whose satisfaction is `passing` on the current binding. Audit history is the verdict row plus every later record. Retirement does not delete it and does not relabel a true `introduced` verdict as false.

**Retirement.** Append `warning-retired`. Any one of these is sufficient:

- HV records `repaired` and the affected criterion is `passing` on the current binding.
- The plan or slice that made the warning load-bearing is retired.
- **Consolidation.** Provisional **`W_max = 8`** active markers. When active markers exceed `W_max`, the oldest active markers whose criterion is already `passing` may collapse into one consolidated marker only after the replacement check below passes. Their verdict rows stay.
- **Standing memory.** A standing memory already in the prefix may replace the per-turn marker only after the replacement check below passes.

**Replacement meaning.** A consolidated marker or a standing memory is an adequate replacement only when the sent text itself contains all four of these, not merely an id: the prohibited approach or obsolete result; whether the meaning is harm or invalidation; a checkable referent; and an explicit statement that this is not the next action. Retirement by consolidation or memory transfer is refused when any of the four is missing. An id-only replacement is non-conforming, and the individual marker stays active and spill-protected. `repaired` and plan retirement do not need a replacement, because the retry obligation has ended.

**Presence in each send.** A warning retired only because of a replacement stays retired for a generation only when that generation's sent assembly still contains an adequate replacement for it. If the standing memory leaves the prefix, or the consolidated marker no longer carries the four fields, the individual warning is active again before send. Reactivation is mandatory and spill-protected. Pins stay expanded.

Retired markers MUST NOT be spill-protected and MUST NOT by themselves fail the budget closed. Active markers, including the consolidated marker, any dependency-gap marker (§16.1), and any reactivated marker, stay spill-protected (WP §6.3). Retiring a marker does not unpin. Pins stay expanded.

**Acceptance cases.** A long history contains more resolved regressions than fit in `B` as individual raw markers. Each of those regressions is `repaired` and its criterion is `passing`. After retirement, the generation sends a projection. It does not fail closed because of the retired set. One warning that is still active remains in the mandatory set, survives spill, and is visible on the sent prompt. Pins in that same assembly stay expanded. Id-only replacement: a consolidated marker or memory that cites only a warning id does not retire the individual marker. Later removal: a warning was retired because an adequate standing memory was in the prefix; the next snapshot whose prefix lacks that memory reactivates the per-turn marker before send.

### 20.5 Consequence: explanations are an indexing substrate, not a sufficient one

Explanations name causes, so they are a useful index for the admissible edge types, which are causal or dependency assertions. `shares_root_cause` in particular is close to a comparison of two explanations. They are not a sufficient index. Residual payload facts that never entered the outcome record (§20.3) are the constraints a link may need to cite, and discovery over explanations alone will miss them. Candidate evidence is the outcome record plus those residual facts, still judged out of band against the seals (§18.1), not against the projection. Cheaper than indexing every byte of every payload is not the same as indexing only the verdict.

## 21. Storage notes against the baseline

**Existing precedent for edge shape.** `GraphRelationshipEntity` (`src/McpServer.Storage/Entities/GraphRelationshipEntity.cs`) is a directed, typed, workspace-scoped edge with a `RelationshipType` string, a `Weight` double, an optional `Description`, and a `Metadata` JSON blob. That is close to the shape §16 needs.

**But it is not reusable as-is.** Its endpoints are `GraphEntityEntity` nodes via `SourceEntityId` / `TargetEntityId` foreign keys, not session turns. Turn-to-turn edges need their own table modeled on this precedent rather than rows in this one.

**No embeddings over turns.** The only embedding column found at the baseline is a nullable `Embedding` BLOB added to `Chunks` (migration `20260216171000_AddEmbeddingColumn`). Candidate generation cannot assume a vector index over turns exists. §18.4 takes the non-vector route deliberately rather than as a fallback: traversal over requirement and acceptance-criteria identifiers needs no embeddings, so a first cut requires no new index and no migration for one.

**Tombstone registration is mandatory, per IMPL §3.2.3.** Every table introduced here — edges, edge transitions, goals, scope/progress series, outcome records — is subject to the trap that section documents: `SoftDeleteTurnRowsAsync` and the revival path name their targets explicitly and discover nothing, so new tables keep `IsDeleted = false` when their turn is deleted.

This is more dangerous for links than for the sealed-turn table. An edge is *traversed automatically*. An unregistered edge table becomes a side channel that silently re-admits content from a deleted turn into a live projection — the operator deletes a session and the material keeps arriving through the index. IMPL §3.2.3's two remedies apply to every new table: register it on both the tombstone path and the revival path, and join reads so visibility follows the turn rather than a flag a future table might forget to set.

For an edge the join is stricter than the single-turn join IMPL §3.2.3 states for seal and projection-state rows. Traversal, link admission, and projection reads treat an edge as ineligible unless **both** the source turn and the target turn are non-deleted. Filtering one endpoint leaves the side channel open. A live source pointing at a tombstoned target can still inspect or re-admit that target; a live target reached from a tombstoned source is the same hole in the other direction. §16.1 admits a specific endpoint, so either end can be the turn the projector reads. An edge with either endpoint tombstoned is not a candidate and not an admission, regardless of type, confidence, or which end is live.

**Deletion is a snapshot input, and the send fence is the commit point.** WP §6.1 freezes the tombstone set with the other inputs. The final read and the transport handoff share one fence. A tombstone, reseal, evidence change, or superseding verdict cannot commit in the gap after the final read and before handoff. If that mutation wins the fence, the handoff is cancelled. If the handoff wins, the mutation has not committed and applies at the next generation. A published call that contains an endpoint whose tombstone committed before handoff is non-conforming. Using a pre-tombstone assembly after that commit is the side channel this section forbids. A generation interrupted before handoff is not published. The required traces are tombstone-before-send, reseal-before-send, concurrent supersession, interrupted generation, and the after-read-before-handoff race, as WP §6.1 states them.

**Audit path.** Per §18.5, edge transitions, scope and progress revisions, and outcome records MUST be written through the tracked save path (IMPL §3.2.1) or an equivalent append-only ledger. Set-based updates that bypass the ledger are non-conforming, and the write fails closed when the conforming path is unavailable. Effective state is the latest superseding record, as §18.5 defines it.

## 22. Evaluation hooks

This capability must not be adopted on the argument that it sounds right. Hooks into WP §9:

- **Re-admit usefulness (WP §9.1 metric 5)** is the natural home: when a turn is admitted by link, did the subsequent action correctly use it? Report link-admitted and score-admitted slices separately. The link-admitted slice has its own pass bar below.
- **Edge retraction rate** — retractions per generation, from §18.5's append-only lifecycle. This is a churn metric. It is not precision. A rising rate means edges are being withdrawn. It does not say whether the withdrawn edges were false, or whether the edges that remained confirmed were true. A false edge can sit confirmed forever; a correct edge can be retracted because its applicability changed.
- **Proposal precision** is the fraction of proposed edges that an independent labeler marks true. The population is every proposed edge in the sample, including edges that never admitted a turn. The labeler is not the component that proposed the edge. The label is against the sealed payloads current at judgment time, not against later retraction. This number is reported. It is not the adoption gate.
- **Admission precision** is the fraction of edges that admitted a turn into at least one assembly and that the same kind of labeler marks true. The population is admitted edges only. A high proposal precision does not pass this metric. It is not `1 - retraction rate`.
- **Adoption gate (predeclared).** Live link admission stays off until both bars below pass. There is no live trial in the production session: shadow assemblies are not copied into the model-facing projection, do not charge the link sub-cap, and are not shown to the actor. The frozen record for a gate run is the workload id, the generator version, the judge version, and the config hash (`K_*`, `J`, thresholds, `W_max`, `Dep`). A pass does not transfer to another tuple.
- **Predicted usefulness is not enablement.** The shadow log records whether an edge would have admitted a turn into a shadow assembly. **Predicted usefulness** is a labeler's judgment that the already recorded action was compatible with that turn. The action was generated without the admission, so the label is a prediction. It MUST be reported under that name. It MUST NOT be called WP §9.1 metric 5, and it MUST NOT by itself turn live admission on. Admission precision on the shadow-admitted population remains a required bar: at least 50 proposed edges, at least 30 shadow-admitted edges, admission precision ≥ 0.90. Thirty easy admissions do not pass the gate if recovery recall fails.
- **Observed-outcome gate, required before general enablement.** From the same frozen prefix, run two isolated replay continuations: one with link admission, one without. Production admission stays off; the replay is not the live session. An adjudicator that did not produce either continuation scores whether the with-admission continuation actually used the admitted turn. That score is observed usefulness. Provisional bar: ≥ 0.80. The without-admission continuation is the context-conditioned scalar baseline (§15). **Recovery coverage** uses the §18.4 label set (old, paraphrased, summary-lost, unattributed, crowded-out, and a raw error with no claim id). Recall on that denominator, which includes constraints the generator never proposed, MUST be ≥ 0.80. Below either observed bar, live admission stays off.
- **Requalification.** A material change to the generator, the judge, any `K_*`, `J`, a threshold, `W_max`, `Dep`, or the config hash voids the pass and turns live admission off until this gate is repeated on the new tuple. Shadow logging continues either way.
- **Edge flip rate** uses the published snapshot sequence only, so two evaluators of one trace get one result. The admission bit is 1 when the effective edge is admitting and 0 otherwise (`degraded` and suspended are 0). Denominator: edges whose bit existed on published snapshot G-1. If that count is 0, do not compute a rate; record `empty-edge-denominator`; the stability gate passes for this metric. Numerator: edges whose bit at G differs from the bit at G-1 for edge-layer cause `edge-score` (WP §6.1, §18.3). Intra-generation records do not add extra flips; only the bit on the published snapshot counts, once. `edge-invalidation`, `edge-suspend`, `edge-reconfirm`, `edge-degrade`, and `edge-budget` are mandatory. They are `mandatory-edge-flips` and are outside the numerator. `edge-score` maps to turn cause `link-admit` or `link-withdraw` and to `originCause` `edge-score`. Those turn causes stay outside the state-flip numerator. They stay inside the token-replacement numerator when `originCause` is `edge-score` (WP §9.1 metric 3). Dropping that token churn because the turn-layer label is mandatory is non-conforming. Mandatory origins (`edge-invalidation`, `edge-suspend`, pin changes, phase boundaries) stay outside the token numerator and are reported in `mandatory-token-count`. A generation whose trace causes are only mandatory is `mandatory-only` and is outside the mean. A generation with `phaseBoundary: true` and a `phaseId` (WP §9.1) is outside the mean. No other exclusion is allowed. Provisional bar: ≤ 0.10 when the denominator is at least 1. The rate is instability, not precision. Active-context token replacement (WP §9.1 metric 3) measures whether the live tail was replaced. If every generation in the session is excluded, do not compute a session mean. Record `empty-aggregate`. The stability gate passes. A missing mean is not a fail and is not a silent skip. The projector sets `phaseBoundary` true if and only if the plan phase id differs from the previous published snapshot (WP §9.1).
- **Mixed-cause expected results.** These numbers are the pass/fail oracle for WP §9.1 metrics 2 and 3 and for the edge-flip rate. State-flip: 1 discretionary `score` flip and 1 mandatory `link-admit` out of 10 previous active turns is 1/10 = 0.10, passes ≤ 0.10, and records `mandatory-transition-count` 1. The state-flip denominator stays the previous active set. Token replacement, mandatory-only: 40 of 100 previous-tail tokens change, all with `originCause` `edge-invalidation`. The generation is outside the mean. If it is the only generation, record `empty-aggregate` and the gate passes. Token replacement, mixed: 30 tokens with `originCause` `score` and 40 tokens with `originCause` `edge-invalidation` out of 100. The rate is 0.30 and fails ≤ 0.25. The 40 mandatory tokens are outside the numerator. Edge flip: 1 `edge-score` flip and 1 `edge-suspend` out of 10 prior edges is 1/10 = 0.10, passes ≤ 0.10, and records `mandatory-edge-flips` 1. A scorer that puts `link-admit` in the state-flip numerator, or that fails an `empty-aggregate` session, is non-conforming. Large-source discretionary withdrawal: 100 edge bits exist on the previous snapshot. One admitted source is 90 of the previous tail's 100 tokens. After cooldown, `originCause` `edge-score` withdraws that edge and `turnCause` is `link-withdraw`. The source has no independent retention and leaves the tail. Edge-flip rate is 1/100 = 0.01 and passes ≤ 0.10. Token-replacement rate is 90/100 = 0.90 and fails ≤ 0.25. The generation is not `mandatory-only`. A scorer that drops those 90 tokens from the token numerator, or that passes the token gate by excluding the generation, is non-conforming. The same withdrawal with `originCause` `edge-invalidation` reports the 90 tokens in `mandatory-token-count` and does not by itself fail the token bar. Pin changes and `phaseBoundary` generations stay outside the token numerator. Summary-growth displacement: budget `B` is 100. Turn S is summarized at 20 tokens and stays summarized. Metric 2 numerator is 0 because the state changes are not `score`. The generation is not `mandatory-only`. Excluding the 70 tokens because the immediate cause is `budget-demotion` is non-conforming. Contrast: the same 70-token displacement caused only by a new pin (`D` is 0) inherits `originCause` `pin`, stays in `mandatory-token-count`, and does not by itself fail metric 3. The pin stays expanded. Mixed pressure, same packing step: budget `B` is 100. Turn S is summarized at 20 tokens. Turns A, B, C, and D are expanded at 20 tokens each. In one packing step a new pin consumes 40 tokens and S grows from 20 to 50 (`summary-rewrite`, `tokenDelta` 30). `pressureSource` has both entries. `M` is 40, `D` is 30, and `R` is 70 (A, B, and C omitted, plus 10 tokens of D). The mandatory share is `floor(70 * 40 / 70)` = 40, taken once for that packing step, and is `mandatory-token-count` only. The discretionary share is 70 - 40 = 30 and is the metric 3 numerator. Span conservation: 40 + 30 = 70 = `R`. The rate is 30/100 = 0.30 and fails ≤ 0.25. Metric 2 numerator is 0 because those state changes are `budget-demotion`, not `score`. The pin stays expanded. Assigning all 70 tokens to the pin, or all 70 to `summary-rewrite`, is non-conforming. Flooring A, B, C, and the 10 tokens of D as four separate demotions is also non-conforming. Multi-turn boundary, one packing step: budget `B` is 120 and the previous tail is 120. Turn S is summarized at 20 tokens and stays in the tail. Its summary grows by 30 tokens (`summary-rewrite`, `tokenDelta` 30) and those previous 20 tokens remain. Turns W, X, Y, and Z are expanded at 10 tokens each and are omitted. The other 60 previous-tail tokens stay. `pressureSource` has the new pin at `tokenDelta` 10 and S at `tokenDelta` 30. `M` is 10, `D` is 30, and `R` is 40, the sum of the four omitted turns. The accounting group is this packing step. The mandatory share is `floor(40 * 10 / 40)` = 10. The discretionary share is 40 - 10 = 30. Span conservation: 10 + 30 = 40 = `R`. Metric 3 is 30/120 = 0.25 and passes ≤ 0.25. Metric 2 numerator is 0. The pin stays expanded. The alternate per-demotion floor is non-conforming: `floor(10 * 10 / 40)` = 2 on each of W, X, Y, and Z, so the mandatory shares sum to 8 and the metric 3 numerator sums to 32. That split still adds to 40, and it is still non-conforming because the floor was not taken once on `R`. The non-conforming rate is 32/120, about 0.2667, and fails ≤ 0.25. No pin, edge bit, safety withdrawal, or phase boundary changes. The summary is regenerated and 90 previous tokens are absent. The trace has a `rendered-change` event with `previousRenderId`, `currentRenderId`, and `originCause` `summary-rewrite` on those 90 tokens. Metric 2 numerator is 0, so the state-flip rate is 0 and passes. Metric 3 is 90/100 = 0.90 and fails ≤ 0.25. The generation is not `mandatory-only`. Reusing T's earlier summarize cause, omitting the event, or passing metric 3 by exclusion is non-conforming. Mixed spans, same retained turn: 30 removed tokens are `summary-rewrite` and 20 removed tokens are `warning-retirement`, out of a 100-token tail. Metric 2 numerator stays 0. Metric 3 numerator is 30, rate 0.30, and fails ≤ 0.25. The 20 marker tokens are `mandatory-token-count` only. One primary `turnCause` for both spans is non-conforming.
- **Candidate-source share** reports four fractions of proposed edges: requirement-graph traversal, referent match, `constraint-fact` scan, and any other fallback (§18.4). Referent match and the constraint scan are quiet-constraint paths. Neither is a fallback. This share is not recall. Recall's denominator is the independent label set in §18.4, including constraints that were never proposed. A falling requirement-graph share with an empty referent-match share and an empty constraint-scan share, or a run that records `constraint-scan-empty` or `constraint-scan-exhausted`, means recovery did not succeed.
- **Edge density per criterion** — edges among turns attributed to one criterion (§18.3). High density with flat progress is a retry loop, not a discovery.
- **Introduced-harm flag precision** is, of turns flagged `introduced`, the fraction operator review confirms as introduced harm. The name is precision of the flag. It is not accuracy: the definition has no true-negative term. **Introduced-versus-revealed agreement** is, of regression classifications, the fraction whose class matches operator review. Report the two separately.
- **Explanation citation rate** is the fraction of explanations that cite at least one checkable referent (§20.1). A falling fraction means explanations are drifting into narration. The rate does not say the referent supports the claim. **Explanation support rate** is, of cited explanations later reviewed, the fraction whose referent supports the claim. The former name "explanation verifiability" is withdrawn; use these two names.
- **Claim-verdict divergence rate** — how often the actor's intent claim and a non-pending HV verdict disagree (§19.3). The rate is descriptive. Agreement is the expected outcome when the claim is accurate and the work is straightforward, so near-zero divergence is not validator failure and is not evidence of capture. Disagreement is not success either. An uncalibrated target rate would reward false adverse verdicts. Do not alert on agreement, and do not alert on disagreement, until an expected disagreement rate has been calibrated on the labeled set below.
- **Adjudication accuracy** — of HV verdicts later checked by operator review, the fraction that matched the reviewed outcome. This is the metric that can distinguish a competent validator from a captured one. Divergence rate may be compared with it only after that calibration exists.
- **HV adjudication cost** — validator calls, targeted test runs, batched suite runs, and latency, reported separately from §18.2's revalidation cost and not averaged into a per-turn figure that hides batching. Per §19.3 an ordinary turn carries a `pending` verdict and does not launch the suite; the phase-exit suite is one batch charge; a targeted run is an explicit extra. If validator calls or suite runs grow with turn count, adjudication has become the default tier, which is the condition WP §10 risk 6 says to avoid.
- **Revalidation cost** — model judgments per turn and their share of turn latency, against the §18.2 cap. WP §10 risk 6 makes this a first-class concern, not a footnote.

## 23. Open questions

A linking run MUST NOT treat open questions 9, 10, 11, and 13 as already decided. Catalog-to-test binding, HV independence, deadlock abandonment, and the per-criterion density cap stay open. A run that assumes any of them is non-conforming for a claim that depends on that answer.

1. **Single-plan attribution is specified; multi-plan attribution is not.** For one plan, §19.3 names the candidate set: test or exercised-code edits, HV-labeled discovery or revealed turns (including turns that never touched the test), and HV-accepted investigation claims. Actor claims alone do not attribute. Referent match and the `constraint-fact` scan (§18.4) can still propose a link for an unattributed quiet constraint, including when the failure does not quote the constraint. Attribution across several slices or plans remains open question 4.
2. **Resolved: introduced-harm is an annotation, not a fourth `projectionState`.** Unpinned turns are `summarized` with the harm marker. Pinned turns stay `expanded` with the same marker (WP §6.2, §20.4). The projector MUST render the marker; ignoring it is non-conforming.
3. **Resolved: the weight-facing reading is the plan vector.** A slice view is a filter of that vector (§19.1). It is not a second progress number and it is not rolled up into another count. Phase-boundary flushes are the `phaseBoundary` flag in WP §9.1, not a second vector.
4. **Multi-plan attribution is unsupported for weight.** One active plan supplies the vector. A turn that also advances another plan does not write a second weight-facing progress number until this question specifies the rule. Until then, packing uses the single plan named on the snapshot.
5. **Resolved: the confidence band is §18.3.** Discretionary admit is `T_admit = 0.80`. Discretionary withdraw is `T_withdraw = 0.60`. The band, the `C = 2` clock, and the behavior after forced invalidation and reconfirmation are specified there. Link admission that has already cleared the band is still a mandatory override in WP §6.1 relative to turn-weight hysteresis. The numbers are provisional only in the sense that an operator may replace them in the run record before the run executes. A run with the cutoffs left unnamed cannot pass or fail. Per-type cutoffs are not used; one band applies to every type in §16.1.
6. **Does revalidation run on seal, on a schedule, or under budget pressure** (compare WP §10 risk 6's mitigation for re-score cost)? Decided in §18.2: reseal and changed evidence void the prior judgment immediately; stale edges are judged once generations since last evaluation reach `S`. The still-open part is whether edges that are not stale, not evidence-changed, and not near the threshold are also judged on a schedule, or only when they later enter the ordering.
7. **Resolved for the overflow case: §16.1 states the final assembly.** The numeric link sub-cap fraction remains operator-adjustable and MUST be fixed before a linking run can pass or fail. When a required source does not fit beside an independently retained target, `invalidates` fails closed and the other types use a dependency-gap marker. Pins are not dropped to pay for the source.
8. **Resolved: an explanation is revised by appending a superseding record.** §18.5 and §20.2 require a new record that names the record it supersedes. The earlier record stays. Effective state is the latest superseding record. In-place rewrite is non-conforming.
9. **Does a passing test prove its criterion, and does the traceability script know the criterion exists?** §19.4's script does not read acceptance catalogs or named test methods. It also does not notice a definition that was deleted. "Covered" means a heading or `TEST-` token that is still present in the requirement documents is listed in the mapping or matrix: a present `## FR-` heading in both, and a present `## TR-` heading or `TEST-` token in the matrix (a failure only with `-StrictTrAndTestCoverage`). It does not mean the mapping or matrix row still has a definition, it does not mean a catalog row names a test, and it does not mean the test is honest. A test bound to `AC-FR-MCP-MEMORY-010-02` can pass while asserting less than the criterion states, and the catalog row can disappear without the script failing. Deleting the `## FR-` heading and leaving the matrix row also passes (§19.4). Catalog-to-test validation and orphan-row detection are open surfaces, not closed gates. Test honesty remains the place §19.3's adjudication is load-bearing rather than supplementary, and it does not close the missing catalog check.
10. **What keeps HV independent in practice?** §19.3 requires a validator blind to the actor's account, but a validator sharing the same model, prompt lineage, or projection may reproduce the actor's blind spots and rubber-stamp them. The hostile-review store records model and effort per run, so independence is at least auditable after the fact; whether a *different* model is required, and what that costs, is unsettled.
11. **When does a deadlock become session abandonment?** BDPv4's answer for a session whose trust has broken is to end it rather than retry (§19.4). A metric loop needs a threshold: how many actor-versus-HV rejection cycles on the same criterion, with scope constant, before the correct action is to discard the session rather than record another regression?
12. **Where does a requirement-to-requirement dependency graph come from?** §18.4 can traverse same-criterion pairs, sibling criteria under one requirement, and FR–TR–TEST co-membership with artifacts that exist at the baseline (`docs/plans/*-ac-catalog.json` where a plan has one, `docs/Project/TR-per-FR-Mapping.md`, `docs/Project/Requirements-Matrix.md`). None of those artifacts records a dependency between requirements. Until one does, and until it declares direction and that the edge is a candidate hint rather than an admission, cross-requirement traversal is out of scope. The absence is a missing input, not an empty result the indexer should paper over.
13. **What is the per-criterion turn-density cap?** §18.3 keeps hysteresis and cooldown as the primary churn defence until this cap exists. The open definition is what is counted (turns, edges, or both), the numeric limit, and the projector's behavior at the cap (refuse new link admissions, stub, or hand the criterion to the deadlock rule in open question 11). A note that density "needs a cap" is not the cap.

## 24. Non-claims

Stated explicitly, because the underlying proposition — that retrospective linking improves outcomes — is attractive enough to be assumed rather than tested.

- **No efficacy claim.** That linked context produces more correct results is a **hypothesis**, not a finding. Nothing here has been built or measured. WP Principle 8 bars presenting it as a benefit until §22's metrics say so.
- **No token-savings claim.** Nothing here is offered as reducing token cost. §18.2 says the opposite: revalidation adds model calls, and the cost must be bounded and reported.
- **No claim that precision is achievable.** §17 hypothesizes that false admissions are costly. §22 predeclares the admission-precision gate. Whether that gate is reachable is unknown, and a negative result is a legitimate outcome. Failing the gate leaves admission off.
- **No scalar-impossibility theorem.** §15 does not claim that a scalar output makes the judge unable to notice joint relevance. WP §5.2 already shows the judge several stubs at once. The claim is narrower: the stored scalar does not persist the pair and does not pack both turns.
- **No universal false-link cutoff.** The withdrawn "60% is worse than no index" sentence is not a result. The adoption rule is the §22 gate.
- **No claim of code readiness.** §21's references are a snapshot of one baseline commit, read for shape rather than verified by building anything.
- **No claim that self-reported signals are trustworthy.** §19.3 removes the actor from adjudication and §20.1 constrains both sides to checkable referents, precisely because the unconstrained versions are not trustworthy. Those constraints are reasoned, not demonstrated.
- **No claim that operational Hostile Validation is available, cheap, or complete.** §19.3 proposes HV as a runtime adjudicator; that is a design proposal. The operational Perplexity HV gate remains blocked on an API key after box reseed and has not been run. A separate secondary document pass, the GrokCode adjudication of 2026-09-26 named in Appendix A, supplied the Pplx P1-01, P2-01, and P3-01 finding list. That pass is not the operational gate and does not qualify the design. Per the standing rule in the README and IMPL §9, the operational Perplexity gate must not be described as done. Astra P2-09 (ledger identity of earlier finding ids) is unchanged.
- **No claim about undisclosed search internals.** §17.1 cites patents, Google's own published posts and documentation, a court exhibit, and a peer-reviewed paper. It does not claim to describe how any production ranking system currently works, and the mapping from web spam to agent context is an analogy — §17.1 states where it breaks rather than where it holds. No claim is made that any of this prior art was designed for, or validates, the design in this paper.
- **No claim about how BDPv4 is practiced.** §19 and §19.4 quote `docs/Development-Process-draft-v4.md`, the plan artifacts in `docs/plans/`, and `scripts/Validate-RequirementsTraceability.ps1` as written. Whether those gates are applied consistently, whether the traceability script runs in CI, and whether the acceptance catalogs stay current were not checked. The process is cited as documented intent, not as observed practice.
- **No claim that scope and progress can be read automatically today.** §19.1 derives them from acceptance-criteria state, which assumes a machine-readable catalog bound to test results. `docs/plans/mcp-memory-002-ac-catalog.json` shows the shape exists for one plan; no such binding was verified across plans, and nothing computes these values.
- **No claim that an adversarial validator is correct.** §19.3 treats HV verdicts as evidence with their own error modes, including false accusation, and open question 10 records that a validator sharing the actor's model or lineage may simply reproduce its blind spots.
- **No claim that retraction rate measures edge precision.** §18.5 and §22 separate churn (retractions, flips) from precision, which needs labels the indexer did not assign.
- **No claim that traceability validation closes criteria gaming.** `scripts/Validate-RequirementsTraceability.ps1` checks present identifiers in the requirement documents. `FR-` and `TR-` present identifiers are headings. `TEST-` present identifiers are tokens. Deleting a definition and leaving the mapping or matrix row passes. It does not read acceptance catalogs, named test methods, or bound tests, and it does not judge test adequacy. Those surfaces are open (§19.4, open question 9).
- **No claim that a documentation review qualifies the design.** Implemented WCP behavior, measured efficacy, operator approval, and independent operational HV / MCP audit closure remain qualification prerequisites. A documentation review does not establish those.
- **No claim that a requirement-to-requirement dependency graph exists.** §18.4 names the traversals the baseline artifacts support and the cross-requirement traversal they do not (open question 12).
- **No claim that actor/HV agreement is capture, or that disagreement is success.** §22 refuses both readings until adjudication accuracy has calibrated an expected disagreement rate.
- **No claim that per-turn progress readings are free.** §19.3's ordinary turn carries a pending verdict. The phase-exit suite is a batch charge and does not attribute itself to turns.
- **No claim that work per generation is O(K), that revalidation cost is bounded by `J` rather than by graph size, that session cheap work is O(turns times (D + K_crit + K_ref)), or that session cheap work is O(G_session times (T_new + K_gen + J + F_max) + E_events).** Those sentences are withdrawn (§18.4). The v0.1.9 formula omitted posting-list reads, did not forbid a walk of E_live, and did not schedule first judgments. The v0.1.10 formula is also withdrawn: it capped each list's length and did not cap how many lists a turn opens, and it omitted `E_events` from the displayed expression. The bound that holds is the procedure stated in §18.4: O(G_session times (T_new + P_open times L + K_attempt + J + F_max) + E_events). `P_open` caps list openings, `K_attempt` caps attempted pairs including rejected and duplicate hits, `inspectionCursor` keeps the unopened keys, `E_events` counts O(1) watermark bumps, and `J_first` with FIFO service is unchanged. An implementation that scans E_live, or that opens every referent list on a turn in one generation, is non-conforming, and that bound does not apply to it.
